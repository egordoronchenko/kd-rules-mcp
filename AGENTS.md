# kd2-rules-mcp — правила для агентов-разработчиков

Цель проекта — MCP-сервер, с которым агент сам строит правила обмена «Конвертации данных 2»
(ПравилаОбмена формата 2.01), правила регистрации (ПравилаРегистрации) и правила корреспондента
по структурам метаданных двух конфигураций. Сначала — КД 2; модель делается так, чтобы потом
добавить другие форматы (КД 3 / EnterpriseData) отдельным сериализатором.

Принцип: **MCP детерминированный** — парсит, предлагает кандидатов сопоставления, сериализует,
проверяет. Смысловые решения (что во что конвертировать) принимает агент, и они видны в диффе.

Инструкция для человека — `README.md`. Устройство сервера (слои, поток данных, инварианты, как добавить
инструмент или проверку) — `docs/architecture.md`.

Если рядом лежит `AGENTS.private.md` — прочитайте его: это локальные правила команды (проекты, базы, процесс),
в открытый репозиторий они не входят.

## Ключевые модули КД (эталон поведения)

Ссылки `reference/kd2-cfg/…:N` в коде — строки выгрузки КД 2.1.8.2:

- `DataProcessors/ВыгрузкаКонвертации` — запись ПравилаОбмена в XML.
- `DataProcessors/ЗагрузкаКонвертации` — чтение ПравилаОбмена обратно в КД.
- `DataProcessors/ВыгрузкаРегистрации` / `ЗагрузкаРегистрации` — правила регистрации.
- `DataProcessors/ЗагрузкаСтруктурыМетаданных` — загрузка выгрузки MD83Exp.
- `DataProcessors/АвтонастройкаПравилКонвертацииОбъектов` / `…Свойств` — автосопоставление.

Читатель правил на стороне БСП (что реально принимается) — обработка
`DataProcessors/КонвертацияОбъектовИнформационныхБаз` в выгрузке любой конфигурации на БСП
(ссылки `БСП:N` — строки её модуля объекта в БСП 3.1.12) и `…/ЗагрузкаПравилРегистрацииОбъектов`.

## Входные данные

1. **Основной вход** — XML-выгрузки конфигураций и расширений из репозиториев проектов. MCP сам собирает из
   них модель, эквивалентную выгрузке MD83Exp, накладывая только явно перечисленные расширения.
2. **Вход по готовой структуре** — XML MD83Exp для конфигураций без исходников.

## Стек и соглашения

- Python 3.12 (uv), официальный MCP SDK, lxml, SQLite-кэш структур, pytest; деплой — Docker.
- **Идентификаторы кода — на английском, комментарии и docstring — на русском.**
  Имена тегов и объектов 1С в коде — как в 1С (кириллица), не транслитерировать.
- Сообщения пользователю и документация — на русском.
- Ответы инструментов MCP компактные: выгрузки типовых конфигураций огромные, наружу — только запрошенное.
- Файлы — UTF-8, концы строк LF. Тексты с обратной косой (пути Windows) правьте инструментами редактирования,
  а не строками Python в скрипте: `\1`, `\r` превращаются в управляющие символы.

## Когда задача готова

Задача по коду считается выполненной только когда на итоговом состоянии:
1. `ruff format` и `ruff check` чистые. Хук `.claude/hooks/ruff_on_edit.py` прогоняет их после каждой правки
   `.py` (подключён в `.claude/settings.json`); замечания исправлять, а не подавлять.
   `# noqa` — только с причиной в том же комментарии.
2. `pyright` без ошибок (режим `standard`, настройки в `pyproject.toml`).
3. `uv run pytest` зелёный; если менялись парсер или сериализатор — и round-trip на корпусе
   (`KD2_CORPUS_DIRS`, см. README).
4. Каждый новый факт о формате КД подтверждён ссылкой на файл и строку эталона (`reference/kd2-cfg/…:N`
   или `БСП:N`).

Не прогнанная проверка — это не пройденная проверка: в отчёте так и пишем.

## Сервер `kd2-rules-mcp`

Контейнер `kd2_rules_mcp`, порт 8060. Настройки машины — `projects.local.yaml`; `scripts/setup_local.py`
генерирует из него `docker-compose.override.yml`, `.mcp.json` и `.cursor/mcp.json`. Проекты, конфигурации,
базы и серверы кода — `projects.yaml`. Все инструменты с параметрами, ответами и кодами ошибок — `docs/tools.md`
(после изменения инструментов — `uv run python scripts/dump_tools.py --write`, он же пересобирает копию
в скилле); история и переменные — `docs/research/mcp-service.md`.

- Пути передаются как на машине агента: сервер видит папки проектов только на чтение и пишет только в рабочую
  папку (`workspace\`) и в папки живых правил проектов (`rules_dir` в `projects.yaml`, подключаются на запись).
- Структуры: `project_list`, `structure_load_project`, `structure_load_xml`, `structure_load_md83exp`;
  запросы — `structure_list`, `structure_objects`, `structure_object`, `structure_values`,
  `structure_plan_content`, `structure_compare`. После ручной правки XML выгрузки — `force: true`.
- Кандидаты — `match_objects`, `match_properties`, `match_values`; пары с `auto: false` и класс «по синониму»
  применяются только решением агента.
- Правила: `rules_open` / `rules_create` → `rules_list`, `rules_get` → `rule_create`, `rule_update`,
  `rule_delete`, `pko_create_from_candidates` → `rules_validate` → `rules_save`; ZIP для загрузки в БСП —
  `rules_pack` (папка комплекта или файлы). Проекты правил переживают перезапуск контейнера: снимки в
  `workspace\.projects\`, идентификатор — имя файла и хеш пути; закрыть — `rules_close`. Что изменилось между
  двумя версиями правил или проектом и файлом — `rules_diff` (по адресам правил, без шума XML).
- Код обработчиков — `handlers_export`, синтакс-чекер, `handlers_locate`.
- Правила регистрации — `registration_build`; черновик обратного направления — `correspondent_draft`.
- Обмен через универсальный формат (правила КД 3) — пока только чтение и проверка: `ed_open` → `ed_overview` →
  `ed_list`, `ed_get`, `ed_locate` → `ed_validate` (связность модуля: обработчики, ветки диспетчера, ссылки
  правил; с `schema_id` и `structure_id` — ещё и правила против схемы формата и структуры конфигурации) →
  `ed_close`. Модуль менеджера обмена читается без исполнения BSL; формы генератора —
  `src/kd2_rules_mcp/ed/forms.py` со ссылками `reference/kd3-cfg/…:N`; исполнитель — общий модуль
  `ОбменДаннымиXDTOСервер` БСП (ссылки `XDTO:N`, обозначения — `docs/checks.md`). Схема формата — пакеты XDTO
  выгрузки: `ed_schema_open` → `ed_schema_types`, `ed_schema_type` → `ed_schema_close`. Чистые читатели без
  инструментов (пока): маршруты версий формата — `ed/routes.py`.
- Ошибка инструмента — JSON с полем `code`.

MCP-серверы 1С (код и метаданные проектов, граф, справка, БСП, шаблоны, проверка кода, сервер данных базы) —
правило `docs/rules/mcp-1c.md`: прочитать перед первым их вызовом в задаче, не раньше.

Скиллы: `.claude/skills/kd2-rules-build` — как строить правила через сервер (порядок и чек-лист; справочники по
видам правил — `references/`, каждый факт со ссылкой на строки БСП или эталона);
`.claude/skills/kd2-exchange-pitfalls` — грабли живых обменов с доказательствами по коду БСП, новые — туда же,
только универсальные; `.claude/skills/kd2-ed-rules` — обмен через универсальный формат: разбор и проверка модуля
менеджера обмена, что БСП делает с правилами (`references/executor.md`) и грабли (`references/pitfalls.md`) — факт
туда попадает только с процедурой и строками исполнителя;
`.claude/skills/kd2-install` — установка агентом (человеческая версия — `docs/INSTALL.md`,
менять вместе).

Знания пользователя — `.claude/skills/kd2-*` и `docs/rules/`; это единственный источник. Cursor и OpenCode читают
`.claude/skills` сами — копий в `.cursor/skills` нет (тест `tests/test_skills.py`). В `references/` скилла
`kd2-rules-build` лежат копии `docs/rules/mcp-1c.md`, `docs/checks.md`, `docs/tools.md`, `docs/glossary.md`:
после правки источника — `uv run python scripts/build_packs.py --write` (тест `tests/test_build_packs.py`).
Тексты скиллов `kd2-rules-build`, `kd2-exchange-pitfalls` и `kd2-ed-rules` переносимы — в чужом проекте нет ни этого
репозитория, ни его путей: ссылки только внутри скиллов или URL открытого репозитория, серверы 1С — ролями и
именами из `project_list`. В проект 1С скиллы ставит `scripts/build_packs.py --dest <папка> --client claude`.
