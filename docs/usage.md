# Работа с сервером: вход, постановка задачи, ограничения

Что дать серверу на входе, как ставить задачу агенту, чего сервер не делает и как передавать файлы, если сервер
на другой машине. Установка —
[INSTALL.md](INSTALL.md), возможности — [features.md](features.md), проверки перед переносом —
[checks.md](checks.md), если что-то не так — [troubleshooting.md](troubleshooting.md).

## 1. Что нужно на входе

Полная выгрузка базы (данные) **не нужна** — только метаданные конфигураций:

| Вход | Когда | Инструмент |
|---|---|---|
| Проект из `projects.yaml` — XML-выгрузка конфигурации и расширений из его репозитория | исходники в git | `structure_load_project` — по имени проекта |
| Произвольная XML-выгрузка по путям | разовая, вне проектов | `structure_load_xml` |
| Файл обработки MD83Exp («Выгрузка структуры метаданных» из поставки КД) | исходников нет | `structure_load_md83exp` |

Код модулей для обработчиков агент смотрит через серверы кода проектов (или в той же XML-выгрузке):
выгрузочные обработчики — против конфигурации-источника, загрузочные — против приёмника. В MD83Exp кода нет.

**Если выгрузка изменилась.** Сервер замечает изменение при повторной загрузке — по `Configuration.xml` и
`ConfigDumpInfo.xml`, которые Конфигуратор переписывает при каждой выгрузке; неизменённая берётся из кэша за доли
секунды. XML правили руками — загрузить с `force: true`. Что обновление сломало в правилах — загрузить новую
выгрузку под новым идентификатором, `structure_compare` со старой и `rules_validate` правил против новой.

## 2. Как ставить задачу агенту

Пишите обычным языком, называя план обмена, направление и структуры:

- **Добавить объект в обмен**
  > Через kd-rules-mcp добавь в правила обмена `ОбменЗарплата3Бухгалтерия3` (БП → ЗУП) перенос справочника
  > «Должности»: ПКО с ПКС по кандидатам и ПВД. Структуры: источник `bp-full`, приёмник `zup-full`. Сохрани в
  > `workspace\zup\ПравилаОбмена.xml`, прогони чек-лист проверок, отчёт — что включил, что выключил и почему.
- **Проверить готовые правила**
  > Проверь правила `…\Templates\ПравилаОбмена\Ext\Template.txt` против структур `bp-full` / `zup-full`,
  > разбери замечания: что дефект правил, что расхождение конфигураций.
- **Разобрать проблему живого обмена** (скилл `kd2-exchange-pitfalls`)
  > В ДО задваиваются контрагенты из БП. Вот правила, выгруженные из обеих баз: `…\bp.zip`, `…\do.zip`.
  > Найди причину по правилам и коду БСП, предложи минимальную правку.
- **Разобрать обмен через универсальный формат** (скилл `kd3-rules`)
  > Через kd-rules-mcp разбери, почему в обмене через универсальный формат из БП в ЗУП не переносится реквизит
  > «Комментарий» справочника «Должности»: найди правила в модулях менеджеров обеих сторон, проверь связность и
  > свойство в схеме формата версии обмена. Что проверено чтением, а что нет — скажи отдельно.
- **Правила регистрации**
  > Пересобери правила регистрации плана `ОбменЗарплата3Бухгалтерия3` по ПВД его правил обмена, сравни с макетом.
- **Обратное направление**
  > Построй черновик правил корреспондента для ПКО «Сотрудники»; перечисли обработчики для ручного переноса.

Агент **не переносит** результат в проект 1С сам — это отдельный шаг по правилам проекта (захват в хранилище,
замена `ExchangePlans\<План>\Templates\…\Ext\Template.txt`, обновление базы).

Перед переносом — проверки: команды и что считается успехом — [checks.md, «Коротко»](checks.md#коротко-проверки-перед-переносом).

## 3. Как это выглядит

Два примера на синтетических данных из `tests/data`. Ответы инструментов настоящие, сокращены до сути.

### Добавить справочник в правила КД 2

Источник — выгрузка `tests/data/xmldump/main`, приёмник — она же с расширением `tests/data/xmldump/ext`: у
справочника «Номенклатура» в приёмнике есть реквизит расширения, которого нет в источнике.

> Через kd-rules-mcp добавь справочник «Номенклатура» в правила обмена из `src` в `dst`, проверь и сохрани.

1. **Кандидаты.** `match_objects` сопоставляет справочники по имени; `match_properties` для «Номенклатуры» —
   реквизиты и табличные части, у реквизита расширения пары нет:

   ```text
   нет пары  →  КомментарийРасш (Реквизит, «Комментарий расширения», Строка)
   ```

2. **ПКО по кандидатам** — `pko_create_from_candidates`. Сервер собирает ПКО с ПКС, выключает свойства без пары и
   предупреждает о том, что решать агенту:

   ```text
   disabled:   КомментарийРасш, Товары/Аналитика, Спецификация
   unresolved: Владелец: нет однозначного ПКО для «СправочникСсылка.Контрагенты»
   warning:    СинхронизироватьПоИдентификатору включено по умолчанию … если данные уже заведены
               в обеих базах, при первой синхронизации поиск только по GUID даст дубли: нужны поля
               поиска и ПродолжитьПоискПоПолямПоискаЕслиПоИдентификаторуНеНашли
   ```

3. **Проверка** — `rules_validate` против обеих структур:

   ```text
   Ошибок: 1, предупреждений: 1
   ошибка  structure.pko_missing  ПКО «Номенклатура» / ПКС Владелец
           Нет ПКО для типов СправочникСсылка.Контрагенты: значения этих типов не выгрузятся
           (свойство пропускается) — создайте ПКО или укажите правило конвертации в ПКС
   ```

4. **Исправление.** Агент добавляет ПКО «Контрагенты» тем же инструментом и проверяет снова: `Ошибок нет,
   предупреждений: 2`. Оба предупреждения — `structure.pko_ref_only`: справочники уходят только ссылкой, без ПВД.
   Для справочников, которые приёмник находит по полям поиска, это штатная схема; так это или нет — решает агент и
   пишет в отчёте.

5. **Сохранение и дифф.** `rules_save` пишет файл в рабочую папку, `rules_diff` двух версий показывает изменения
   по адресам правил, без шума XML:

   ```text
   pko: added 1, removed 0, changed 0
   ПКО «Контрагенты» — added
   ```

В отчёте агента — что включено, что выключено и почему, оставшиеся предупреждения и решения по ним, в том числе по
полям поиска: сервер подсвечивает риск дублей, но решение не принимает.

### Проверить модуль обмена через универсальный формат

Модуль менеджера обмена `tests/data/ed/manager_v3.bsl`, `ed_open` → `ed_validate` без схемы формата и структуры:

```text
Ошибок: 6, предупреждений: 2; не выполнены проверки: ed.schema, ed.structure — результат неполный
ошибка          ed.handler.missing  ПКО/Заказ
                Для события «ПослеЗагрузкиВсехДанных» правило называет «ПКО_Заказ_ПослеЗагрузкиВсехДанных»:
                ветки диспетчера нет, процедура в модуле есть. Добавьте ветку диспетчера. Обмен не
                прерывается, объект записывается повторно.
предупреждение  ed.reference.property_rule_missing  ПКО/Заказ/ПКТЧ/Products/ПКС/Product
                ПКС ссылается на отсутствующее правило «Товар»; проверены ПКО и ПКПД.
```

Чего сервер не проверил, он говорит сам: со схемой формата (`schema_id`) и структурой конфигурации
(`structure_id`) та же проверка сверит правила ещё и с ними.

## 4. Ограничения

- Для КД 3 сервер пишет собственный модуль правил и расширение-надстройку над типовым, но не правит типовой
  модуль на месте. Собственные типы формата (свой пакет XDTO) строятся только в собственном модуле правил; в
  надстройке над типовым поля без места в формате идут через `AdditionalInfo`.
- Код обработчиков пишет агент; сервер проверяет его область видимости, сравнения перечислений формата и
  обязательные свойства, синтакс-чекер — синтаксис; смысл проверяет только живой обмен в песочницах. В переносе
  84 правил три дефекта нашлись только обменом.
- Установка расширения и правил регистрации в базу — за человеком (или агентом с доступом к конфигуратору);
  сервер пишет комплект и инструкцию.
- Правила КД 2 в базу загружает человек. `rules_pack` собирает ZIP и в `load_with` пишет, чем грузить. В БСП
  3.1.12 и новее (БП 3.0.207, ЗУП 3.1.38 и новее) формы регистра `ПравилаДляОбменаДанными` файл больше не
  принимают. Для полного комплекта (обмен, корреспондент, регистрация) есть расширение
  [`kd2-rules-file-load.cfe`](https://github.com/egordoronchenko/kd-rules-mcp/releases/latest/download/kd2-rules-file-load.cfe)
  из релиза: Администрирование → Расширения → «Добавить из файла», перезапуск, затем в форме «Загрузить
  правила синхронизации» — кнопка «Загрузить комплект из файла...». Расширение одно для любой конфигурации на
  БСП 3.1.12+, пару файлов без правил регистрации оно не грузит. В песочнице сервера то же делает
  `live_rules_install`. Подробнее — [INSTALL.md, «Загрузка правил КД 2 в базу на БСП 3.1.12 и новее»](INSTALL.md#загрузка-правил-кд-2-в-базу-на-бсп-3112-и-новее).
- Черновик корреспондента — основа (около двух третей пар совпадает с ручными правилами); обработчики и
  асимметричные решения — за агентом.

## 5. Сервер на другой машине

Сервер можно поставить не на ту машину, где работает агент: например, на отдельный хост рядом с другими
серверами MCP для 1С. Тогда сервер видит свои папки, а агент — свои: правила, которые сервер сохранил
(`rules_save`, `rules_pack`, `registration_build`, `ed_authoring_build`), лежат на машине сервера, а файл агента
серверу не виден. Признак — путь из ответа сервера на машине агента не открывается.

Файлы передаются по короткоживущим ссылкам HTTP, мимо модели: содержимое не попадает в ответ инструмента и не
набирается агентом заново.

| Что нужно | Инструмент | Команда на машине агента |
|---|---|---|
| Забрать файл с сервера | `download_link(path)` — путь из ответа `rules_save`, `rules_pack` и других | `curl.exe -fsS -o "<file_name>" "<url>"` |
| Отдать свой файл серверу | `upload_link(name)` — только имя файла, без папок | `curl.exe -fsS -T "<свой файл>" "<url>"` |

- **Что отдаёт сервер.** `download_link` — ссылку `url`, путь, имя файла, размер, SHA-256, время окончания
  ссылки и готовую команду (`command.windows`, `command.posix`). `upload_link` — ссылку, путь, по которому ляжет
  файл, предел размера и команду; на закачку сервер отвечает JSON с путём, размером и SHA-256.
- **Сверка хеша.** После скачивания агент сравнивает SHA-256 файла с ответом: `Get-FileHash -Algorithm SHA256`
  в Windows (без учёта регистра букв) или `sha256sum` в Linux. Не совпал — файл изменили после выдачи ссылки или
  он скачался не целиком: новая ссылка.
- **Куда ложится закачанный файл.** Во входящую папку `inbox\` рабочей папки сервера
  ([workflow.md](workflow.md#1-что-где-живёт)). Путь из ответа `upload_link` сразу годится для `rules_open`,
  `rules_diff`, `rules_pack` и `ed_open`. Без `overwrite=true` существующий файл не перезаписывается.
- **Что можно скачать.** Только файлы рабочей папки и папок живых правил (`rules_dir`). Выгрузки конфигураций
  по ссылке не отдаются — они есть у агента в репозитории проекта. Папку целиком ссылкой не отдать: комплект
  правил для загрузки в базу — ZIP через `rules_pack`, комплект `ed_authoring_build` — по файлу.
- **Срок и доступ.** Ссылка — на один файл и одно действие, действует 10 минут (параметр `ttl_seconds` — до
  часа). Токен MCP для неё не нужен: доступ даёт подпись в ссылке, поэтому ссылку не пересылают и не пишут в
  отчёты. Предел закачки — 64 МБ (`KD2_UPLOAD_MAX_MB`).
- **Windows PowerShell 5.** Там `curl` — это псевдоним `Invoke-WebRequest`, поэтому в командах — `curl.exe`.

Как настроить сервер для агентов на других машинах (`bind`, `token`, `server_url`) и проверить передачу файлов —
[INSTALL.md, шаг 4](INSTALL.md#4-настройки-машины--projectslocalyaml). Сервер на той же машине, что агент, — ссылки
не нужны: файлы лежат по путям из ответов.
