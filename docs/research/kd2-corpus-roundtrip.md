## Как устроены импорт и экспорт

- Схема (`schema.py`) выписана из писателей КД построчно: для каждого вида элемента — атрибуты,
  простые теги и вложенные элементы **в порядке вывода** и политика вывода
  (`ADD` — как `ДобавитьЭлемент` ВК:83-95; `IF_TRUE` — как `ВыгрузитьБулевоЗначениеТолькоЕслиИстина`
  ВК:740-748; `ALWAYS`/`IF_NOT_EMPTY` — для контейнеров).
- Импорт типизирует значения (строка, целое, булево) и складывает их по именам тегов 1С; экспорт
  идёт по схеме, поэтому порядок тегов всегда как у КД, а значения по умолчанию не выводятся.
- Стиль исходника (BOM, XML-объявление, CRLF/LF, отступ, перевод строки в конце) определяется при
  импорте и повторяется при экспорте; для новых файлов — стиль КД: BOM, без объявления, CRLF, табуляция.
- Экранирование — только `&amp; &lt; &gt;` в тексте (плюс `&quot;` в атрибутах), без CDATA; в корпусе
  других сущностей нет.

## Расхождения, найденные на корпусе

1. **Маркеры доработок текстом между элементами** — `//xx_N` … `//xx_K` в трёх файлах
   доработанного плана обмена БП ↔ ЗУП (обмена — 3 пары, корреспондента — 6, регистрации — 2),
   внутри групп ПКО/ПКС и контейнеров. Это смешанное содержимое: читатель БСП его молча пропускает
   (в циклах разбора правил нет ветки `Иначе`, например `ЗагрузитьПравилоКонвертации` БСП:5751-6035),
   но для авторов доработки маркеры значимы. Модель хранит текст как `leading_text` следующего узла и
   `trailing_text` родителя, экспорт выводит его отдельной строкой на том же отступе — эти файлы
   воспроизводятся побайтно. Правило К2.
2. **`Отключить="false"` у групп ПКО** — `Обмен1С_КАМИН_ЗарплатаБухгалтерия30`, оба файла, 8 групп.
   КД 2.1.8.2 этот атрибут у группы ПКО не выводит (ВК:870-883); схема принимает его и выводит только
   «истину». Правило К6.
3. **Пустые обработчики** `<ПередЗагрузкой></ПередЗагрузкой>`, `<ПослеЗагрузки></ПослеЗагрузки>`,
   `<ПередВыгрузкойДанных></ПередВыгрузкойДанных>` — доработанный план обмена кадровыми данными, корреспондент,
   7 тегов. Писатель КД пустой обработчик не выводит (ВК:750-758). Правило К4.
4. **Другой порядок полей ПКО** — тот же файл: `ПослеЗагрузки`, `ПоследовательностьПолейПоиска`
   стоят после флагов, а не перед ними, как в ВК:808-829 (обработчики 808-817, флаги 819-829). Читатель БСП разбирает поля правила
   циклом по имени узла (БСП:5751), порядок полей смысла не несёт. Экспорт пишет порядок КД. Правило К8.
5. **Пустые разделы с переводом строки внутри** (`<ПравилаКонвертацииОбъектов>⏎\t</…>`) и
   отсутствующие `Алгоритмы`/`Запросы` — все три файла того же плана обмена кадровыми данными. Экспорт
   пишет пустые разделы как `<Раздел/>`, как КД (ВК:1449-1497). Правило К4.
6. **Сбитый отступ одного блока** — `ПоОрганизации/ПравилаРегистрации`: одно `Правило` смещено на
   уровень вправо. Только пробелы. Правило К2.
7. **XML-объявление** есть у трёх файлов (план обмена кадровыми данными — корреспондент,
   ЗУП КОРП `АвтономнаяРабота` и `ОбменВРаспределеннойИнформационнойБазе` — регистрация), перевод строки
   в конце — у одного. Стиль сохраняется, на смысл не влияет.
8. **Булево через `ДобавитьЭлемент` выводится и при «ложь»**: `<Авторегистрация>false</…>` —
   10 721 раз, `<ЭтоСтрокаКонстанты>false</…>` — 2 324 раза (ВР:112, ВР:330). Значит, `ЗначениеЗаполнено`
   для булева даёт «истину» при любом значении, и пропуск «ложных» флагов в КД делается только
   явным `ВыгрузитьБулевоЗначениеТолькоЕслиИстина`. Уточнение к дайджесту §2.1: «ложные флаги не
   попадают» верно только для флагов из этого списка. В схеме такие теги — `ValueType.BOOL` с
   политикой `ADD` (выводятся всегда), `Непосредственно` у ПОД (ВК:985) — так же.
9. **`РежимСовместимости` у `ВерсияФормата`**: СБСП20 — 20 файлов, СБСП21 — 9, пустой — 3,
   атрибута нет — 2. Модель сохраняет наличие атрибута как есть; читатель БСП его не читает
   (дайджест §3.1).

## Правила канонизации

Каноническая форма (`canonical.py`) строится прямо по XML, без модели, чтобы экспорт проверялся
независимо. Каждое правило покрыто тестом в `tests/test_canonical.py`.

| Правило | Суть | Основание | Тесты |
|---|---|---|---|
| К1 | Порядок атрибутов не важен | XML | `test_k1_*` |
| К2 | Пробельный текст между элементами не значим; непробельный (маркеры) значим на своём месте; текст листьев — как есть | расхождения 1, 6 | `test_k2_*` |
| К3 | Переводы строк → LF в тексте и атрибутах | CRLF в корпусе | `test_k3_*` |
| К4 | Лист без атрибутов с пустым или пробельным текстом = отсутствует | ВК:83-95, ВК:750-758; расхождения 3, 5 | `test_k4_*` |
| К5 | Флаги «только если истина» со значением `false` = отсутствуют | ВК:740-748 и вызовы ВК:410-924 | `test_k5_*` |
| К6 | Атрибуты `Отключить`, `Поиск`, `Обязательное` = `false` → отсутствуют | ВК:619-629, 693-695; расхождение 2 | `test_k6_*` |
| К7 | `Порядок`, `ПриводитьКДлине` = `0` → отсутствуют | ВК:83-95 | `test_k7_*` |
| К8 | Порядок простых полей записи не важен, порядок элементов списков важен | БСП:5751; расхождение 4 | `test_k8_*` |

Не канонизируется (сравнивается строго): порядок правил, групп, свойств, значений, параметров,
элементов состава и отборов; пробелы по краям в тексте листьев (например, `Ид` с хвостовыми
пробелами); булевы теги, которые КД выводит всегда (`Авторегистрация`, `ЭтоСтрокаКонстанты`,
`Непосредственно`).

## Ограничения

- Неизвестные теги сохраняются, но при экспорте выводятся в конце своего элемента, а не на
  исходном месте. В корпусе таких нет; если появятся — сработает К8 для полей, но не для списков.
- Комментарии XML при импорте отбрасываются, текст по обе стороны комментария склеивается.
  В корпусе комментариев нет.
- Значения по умолчанию для новых узлов заданы только для атрибутов, которые писатель выводит
  всегда (`Attr.default`); `РежимСовместимости` для новых правил пока не задаётся — решим при
  создании правил с нуля (`rules-authoring.md`, 6.1).
