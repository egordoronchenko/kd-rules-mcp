# Составление правил: обоснование и результаты

Дата: 27.09.2026. Этап 6: составление правил. Код — пакет `src/kd2_rules_mcp/authoring/`.

Ссылки «КД:…» — модули эталона `reference/kd2-cfg/`.

## 6.1. Рабочий проект правил

Код: `src/kd2_rules_mcp/authoring/workspace.py` (`RulesWorkspace`: `open_rules`, `create_exchange`, `save`, `get`),
тесты: `tests/test_authoring_workspace.py`; ошибки `WorkspacePathError`, `ProjectNotFoundError` в `errors.py`.

- Проекты живут в памяти по идентификатору; открыть можно XML правил обмена или регистрации по любому пути.
- Пустые правила для пары структур: заголовок как у `ВыгрузитьКонвертацию` (КД:`ВыгрузкаКонвертации`, 374–422) —
  `Ид` (GUID, дополненный до длины кода 40), `Наименование` «источник --> приёмник», `ДатаВремяСоздания`,
  `Источник`/`Приемник` с именем, синонимом и версией конфигурации из структуры. Версии платформы в структуре нет —
  атрибут пишется пустым, как у КД при незаполненном приложении; `РежимСовместимости` — значение заполнения
  справочника `Конвертации` (`РежимСовместимостиСБСП20`). Строки эталона — в docstring модуля.
- Запись только внутрь рабочей папки: путь проверяется после `resolve` (`..`, символические ссылки, junction);
  вне её — `WorkspacePathError` с разрешённым каталогом; существующий файл — только с `overwrite=True`.

Тест ссылки наружу сначала пропускался (на Windows без прав символическую ссылку не создать); ссылка заменена
на junction каталога — тест выполняется и проходит.

## 6.2. Кандидаты сопоставления

Код: `src/kd2_rules_mcp/authoring/candidates.py` (`object_candidates`, `property_candidates`, `value_candidates`,
`auto_allowed`), тесты: `tests/test_authoring_candidates.py`. Для поиска объекта по `Вид.Имя` или имени
типа в `structures/queries.py` добавлена публичная `find_object`.

Алгоритм повторяет автонастройку КД (строки — в docstring модуля):

- объекты — по имени и виду (`АвтонастройкаПравилКонвертацииОбъектов`, 139);
- свойства — по имени и виду на одном уровне дерева, иначе по аналогу `Номер↔НомерДок`, `Дата↔ДатаДок`
  (`СинхронизироватьСвойство`, 577–630; КД:`CommonModules/ОбщегоНазначения`, 1628–1659); реквизиты табличной части —
  только внутри сопоставленной табличной части;
- значения — по имени (`СинхронизироватьЗначение`, 335–348);
- «примитив → объектная ссылка» (`ОпределитьМожноАвтоматическиСопоставитьЭлементы`, 517–564): пара возвращается
  в своём классе, но с `auto = False` и пометкой. КД сравнивает один тип свойства (`Максимум(Тип)`), здесь — наборы
  типов: запрет, если все типы источника примитивные, а приёмник допускает объектную ссылку;
- «по синониму» — собственный класс: однозначная пара несопоставленных элементов одного вида с одинаковым синонимом,
  всегда `auto = False`;
- имена и синонимы сравниваются без учёта регистра, как ключи 1С.

Сверка с правилами доработанного плана обмена БП ↔ ЗУП (`ПравилаОбмена`, БП → ЗУП; структуры `bp-ext` и
`zup-full`): у включённых ПКС с совпадающими именем и видом (или аналогом КД) 401 пара найдена в классе «точно», пар
«синоним КД» в макете нет. Не найдены 2 ПКС и 2 ПКО — реквизиты и справочники доработки, которых нет в ЗУП КОРП:
приёмник правил — доработанная конфигурация ЗУП, её выгрузки нет (та же подмена, что в 5.2). Остальные 19 включённых ПКС макета
связывают свойства с разными именами или видами — это ручные решения автора правил, автонастройка КД их тоже не
предлагает. Ни одна из 401 пары не попала под запрет «примитив → ссылка».

## 6.3. Точечные правки правил

Код: `src/kd2_rules_mcp/authoring/edits.py` (`create_rule`, `update_rule`, `delete_rule`,
`create_pko_with_properties`, результат `EditResult`), тесты: `tests/test_authoring_edits.py`; ошибки `RuleEditError`
и наследники (`UnknownFieldError`, `DuplicateRuleError`, `RuleNotFoundError`, `DanglingReferenceError`) в `errors.py`.

- Адресация: ПКО, ПВД, ПОД — `Код`; алгоритм, запрос, параметр — `Имя`; ПКС и группа ПКС — код ПКО и путь
  `группа/…/свойство-приёмник`; ПКЗ — код ПКО и имя значения источника. Изменение пишет только переданные поля; при
  отказе узел восстанавливается.
- Отказы: неизвестное поле, повтор кода/имени, висячая ссылка на ПКО (с перечнем ПКО для этого типа), удаление или смена
  кода ПКО, на которое ссылаются; со структурами сторон — объект, свойство или значение, которых нет. Без структуры
  проверки стороны не выполняются и перечислены в `skipped`.
- Массовое создание ПКО по кандидатам 6.2: ПКС для пар «точно» и «синоним КД» с `auto`, группа ПКС для табличной части,
  выключенные ПКС для свойств приёмника без пары, `Порядок` с шагом 50 (КД: `СохранитьПравилаКС`, 796–864); пары без
  `auto` и «по синониму» — в `not_applied`; `КодПравилаКонвертации` — только при единственном ПКО с этой парой типов,
  иначе свойство в `unresolved`.

## 6.4. Правила регистрации из состава плана обмена

Код: `src/kd2_rules_mcp/authoring/registration.py` (`build_registration_rules` и спецификации `RegistrationObject`,
`PlanFilter`, `ObjectFilter` с группами), тесты: `tests/test_authoring_registration.py`.

- Заголовок, `ПланОбмена`, `Конфигурация`, `СоставПланаОбмена` (тип и авторегистрация из структуры источника), ПРО,
  отборы по плану и по объекту, таблицы свойств и обработчики — в порядке и с правилами вывода писателя КД
  (`ВыгрузкаРегистрации`, строки — в docstring модуля); `СоставПланаОбмена` пишется, хотя читатель БСП его пропускает (дайджест §4.2).
- Выбор объектов: явный список агента или по умолчанию объекты ПВД (`ОбъектВыборки`, иначе `Источник` ПКО по
  `КодПравилаКонвертации`). Явный объект вне состава плана — ПРО создаётся с предупреждением «добавить в состав плана в
  конфигурации» (сценарий спецификации); объект по умолчанию вне состава или отсутствующий в структуре — ПРО не
  создаётся, предупреждение с перечнем.

Проверка: правила регистрации доработанного плана обмена БП ↔ ЗУП, пересобранные по ПВД его `ПравилаОбмена` против
`bp-ext`, проходят проверку 5.3 без ошибок и формат без ошибок. Набор объектов ПРО совпал с макетом полностью —
26 объектов; из состава плана без ПВД остаётся только `РегистрСведенийЗапись.СоответствияОбъектовИнформационныхБаз`,
ПРО на него нет ни в макете, ни в пересборке.

Собственный поиск объекта в структуре заменён на `queries.find_object` (добавлена в 6.2).

## 6.5. Черновик правил корреспондента

Код: `src/kd2_rules_mcp/authoring/correspondent.py` (`mirror_rules(rules, codes, target_structure)`), тесты:
`tests/test_authoring_correspondent.py`; построитель маленьких структур для тестов вынесен в `tests/sqlite_structure.py`.
В КД механизма нет (дайджест §2.9, §6), поэтому результат — черновик: `Комментарий` заголовка
и признак `draft` в ответе.

- Заголовок: `Источник` ↔ `Приемник`, новый `Ид`, `Наименование` «приёмник --> источник». События конвертации,
  параметры, обработки, ПВД, ПОД, алгоритмы и запросы не переносятся: они относятся к направлению исходных правил.
- ПКО, стороны ПКС (с атрибутом `Тип`) и ПКЗ меняются местами; признак `Поиск` остаётся на ПКС и после обмена сторон
  относится к свойству нового приёмника.
- Обработчики ПКО, ПКС и групп ПКС снимаются и возвращаются списком с кодом и пометкой «перенести вручную»; варианты
  поиска ПКО снимаются вместе с `ПоследовательностьПолейПоиска`.
- `КодПравилаКонвертации` на ПКО вне выборки очищается (иначе висячая ссылка 5.1).
- Со структурой нового приёмника ПКС выключается, если у зеркального ПКС нет свойства приёмника, свойства нет у объекта
  или его ссылочного типа нет в структуре; такие ПКС перечисляются в ответе.

Сверка: доработанный план обмена БП ↔ ЗУП, прямые правила БП → ЗУП против реальных `ПравилаОбменаКорреспондента`
(ЗУП → БП) того же плана. Выборка — 38 из 48 ПКО, у которых в правилах корреспондента есть ПКО с обратной парой типов;
структура нового приёмника — `bp-ext`. Черновик проходит проверку формата без ошибок.

- Совпали 350 включённых пар ПКС (имя источника, имя приёмника).
- Только в реальных правилах — 160 пар: правила корреспондента составлены независимо и переносят больше свойств
  (целиком `НачислениеОценочныхОбязательствПоОтпускам`, `РезервыПоОплатеТруда`, ставки `СправкиПоНДФЛ…`), а в
  ведомостях заполняют табличную часть `Зарплата` без источника (обработчиками).
- Только в черновике — 11 пар: свойства, которые прямые правила выгружают, а обратные не загружают (`Бухгалтер`,
  `ЗарплатаОтраженаВБухучете`, `ПометкаУдаления` ведомостей, `Родитель`/`ЭтоГруппа`), и односторонние ПКС прямых
  правил (`Банк`, `ТекстНазначения` у `БанковскиеСчета`, `ГоловнаяОрганизация`), которые в корреспонденте сопоставлены
  с обеих сторон.
- Выключено 13 ПКС — все без свойства приёмника: в прямых правилах табличную часть `Зарплата` ведомостей заполняет
  обработчик. Ложных выключений по структуре нет.
- Снято 20 обработчиков (по 4 `ПередВыгрузкой`, `ПриВыгрузке`, `ПоследовательностьПолейПоиска`, 2 `ПослеЗагрузки` и
  события конвертации); одна ссылка на ПКО вне выборки очищена (`Организации` → `РегистрацииВНалоговомОргане`).

Вывод: зеркалирование даёт основу, совпадающую с ручными правилами корреспондента примерно на две трети пар; остальное —
решения автора правил обратного направления, которые агент принимает сам.
