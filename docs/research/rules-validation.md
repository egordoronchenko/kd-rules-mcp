## 5.1. Проверка формата

Код: `src/kd2_rules_mcp/validation/format.py` (`check_format(document)`), тесты: `tests/test_validation_format.py`.
Ссылки на строки читателей выборочно сверены.
Решения по уровням с обоснованием — в docstring модуля и таблице `_KIND_TAGS`. Кратко:

- неизвестный тег верхнего уровня `ПравилаОбмена` — ошибка (читатель: протокол 7, `ObjectModule.bsl:16489`);
  в ПКО, ПКС, ПКЗ, ПВД, ПОД, списках и группах — тоже ошибка: веток `одПропустить` там нет, вложенные узлы
  читаются как поля родителя; в алгоритмах, запросах, сторонах ПКС и всех узлах правил регистрации — предупреждение
  (читатель пропускает); теги, которые писатель КД не выводит, но читатель разбирает (`ПоляПоиска`,
  `ИмяТипаПриемника` …), замечаний не дают;
- пустые `Код`/`Имя`/`Источник`/`Приемник`/`ОбъектМетаданныхИмя` — предупреждение: читатель загружает такое правило;
- повтор кода ПКО и имени алгоритма, запроса, параметра, обработки — ошибка (соответствие перезаписывает первое);
  повтор кода ПВД, ПОД, ПРО — предупреждение (оба правила остаются);
- `КодПравилаКонвертации` ПВД/ПКС и `ПравилоКонвертации` параметра без ПКО — ошибка (протокол 45).

Корпус (60 макетов): ошибок нет, 64 предупреждения — 22 пустых `Источник` ПКО (выгрузка из обработчиков, приём
правил корреспондента), 42 повтора кода (1 ПВД и 41 ПРО в `ПоОрганизации` и планах ЗУП КОРП: читатель ПРО код не читает).

## 5.2. Проверка по структурам метаданных

Код: `src/kd2_rules_mcp/validation/structure.py` (`check_structures(rules, source, target)`).
Тесты: `tests/test_validation_structure.py` (синтетика этапа 4: источник `main`+`ext`, приёмник `main`);
тест на реальных правилах (маркер `structures`) в репозиторий не входит.

### Проверки и обоснование

| Проверка | Уровень | Обоснование |
|---|---|---|
| `structure.pko_source` / `pko_target` — тип ПКО есть в структуре | ошибка | имена типов в правилах и в структуре — одна нотация КД; ПКО с пустым источником (выгрузка из обработчиков) не проверяется |
| `structure.pks_source` / `pks_target` — свойство ПКС есть у объекта | ошибка | путь `группа.свойство`; у группы ПКС сверяется и вид: по нему исполнитель берёт коллекцию — ТЧ или набор движений (Исп:11752-11766). У обычного свойства вид исполнителем не используется и не сверяется. Отключённые ПКС пропускаются |
| `structure.pko_missing` — ссылочный тип источника без ПКО | ошибка, если у свойства все типы ссылочные и ни для одного нет ПКО; предупреждение для составного типа или если свойство упомянуто в обработчике ПКО | без `КодПравилаКонвертации` ПКО ищется по типу значения (Исп:7080-7085, 6977-6999); не нашёлся — свойство молча пропускается (Исп:13152-13161); ссылку в примитив исполнитель тоже не ставит (Исп:12495 и далее) |
| `structure.pks_type` — примитив → объектная ссылка | ошибка | запрет автонастройки КД (`rules-authoring.md`, 6.2) |
| `structure.pks_type` — ПКО из `КодПравилаКонвертации` другого типа, чем свойство | предупреждение | |
| `structure.pkz_source` / `pkz_target` — значение ПКЗ есть у объекта | ошибка | |
| `structure.pkz_coverage` — значения перечисления без ПКЗ | предупреждение | при непустом соответствии значений значение без ПКЗ выгружается пустой ссылкой с ошибкой 71 в протоколе (Исп:740-772); ПКО перечисления без ПКЗ соответствия не строит (Исп:738) и не проверяется |
| `structure.pvd_object` — объект выборки ПВД есть в источнике | ошибка | |
| `structure.pvd_pko` — объект выборки ≠ источник ПКО ПВД | предупреждение | |
| `structure.pod_object` — объект выборки ПОД есть в приёмнике | ошибка | ПОД выполняются при загрузке, до чтения данных (УО:12022-12023); исполнитель БСП их только загружает |

ПКС с обработчиками выгрузки не проверяются на типы: значение может вычислить код.
Без структуры одной из сторон проверки по ней отмечаются невыполненными (`structure.source`/`structure.target`).

### Разбор: доработанный план обмена БП ↔ ЗУП

`ПравилаОбмена` — БП (`bp-ext`, MD83Exp песочницы БП с расширениями) → ЗУП; `ПравилаОбменаКорреспондента` — обратно.
Настоящий приёмник — отдельная доработанная конфигурация ЗУП; её выгрузки нет, вместо неё
структура ЗУП КОРП (`main` + 3 расширения).

| Замечание | Правила | Класс | Разбор |
|---|---|---|---|
| ПКО двух справочников доработки (номенклатурные группы, аналитика затрат): типа нет в ЗУП (`pko_target`/`pko_source`, `pvd_object`) | оба | подмена приёмника | справочники доработки, в ЗУП КОРП их нет |
| ПКС двух реквизитов доработки (номенклатурная группа, аналитика затрат; в том числе в ТЧ `НачисленнаяЗарплатаИВзносы`, `ОценочныеОбязательства`): нет свойства в ЗУП | оба | подмена приёмника | реквизиты той же доработки |
| ПКО «СправкиПоНДФЛДляРасчетаПоНалогуНаПрибыль» / ПКС `Сотрудники/СтатусНалогоплательщика`: нет ПКО для `СправочникСсылка.СтатусыНалогоплательщиковПоНДФЛ` | оба | **реальная ошибка** | ПКО с таким источником в макетах нет (`Template.txt:1449` и `:3371` — только сама ПКС); статус налогоплательщика не переносится |
| ПКО «НДФЛСтавки»: без ПКЗ `Ставка18`, `Ставка20`, `Ставка22` | оба | **реальное** | в `Enums/НДФЛСтавки.xml` выгрузки БП 14 ставок, в правилах 11 ПКЗ — нет ставок прогрессивной шкалы; такие документы уйдут с пустой ставкой и ошибкой 71 |
| ПКО «ВидыРезервовПоОплатеТруда»: без ПКЗ `ВознаграждениеЗаВыслугуЛет` | корреспондента | **реальное** | значение ЗУП появилось после составления правил |

Первый прогон дал ложное замечание: у документов ЗУП есть одноимённые ТЧ и набор движений
(`ОценочныеОбязательства`), и индекс по пути терял одну из них. Индекс переделан на пару «путь, вид родителя»,
группа ПКС ищется с учётом вида.

### Прогон по корпусу (только сторона источника)

Все `ПравилаОбмена` БП КОРП с доработками (источник — `bp-ext`) и ЗУП КОРП (источник — `zup-full`), 10 файлов:
ни одного ложного «свойство/объект не найден». Ошибок 5: три — уже разобранная ПКС `СтатусНалогоплательщика`
(она же в `ОбменЗарплата3Бухгалтерия3` БП и ЗУП), две — ОКПД2:
- ПКО «УведомлениеОбОстаткахПрослеживаемыхТоваров» (УТ 10.3): ПКС `КодОКПД2`, `КодОКПД2ПослеИзменения` —
  в БП `СправочникСсылка.КлассификаторОКПД2`, в УТ строка, ПКО нет — **реальная**: ссылка в строку без ПКО не
  выгружается (Исп:12495 и далее).

Предупреждения: `pkz_coverage` 22 — новые значения перечислений, которых не было при составлении правил
(ставки НДС `НДС22`, `НДС5`, `НДС7`; ставки НДФЛ; виды операций, например `ОплатаСчетаЧерезСБП`);
`pko_missing` 12 — составные типы (`Владелец` банковского счёта — `ФизическиеЛица`, основания документов),
и ПКС `ВидОперации` ПКО «ПоступлениеТоваровУслугВНТТ»: ПКО для перечисления нет, но значение ставит обработчик
ПКО (`Объект.ВидОперации = …`, УТ `Template.txt:6371`) — поэтому предупреждение, а не ошибка.

## 5.3. Проверка правил регистрации

Код: `src/kd2_rules_mcp/validation/registration.py` (`check_registration(rules, structure)`), тесты:
`tests/test_validation_registration.py` (синтетика `tests/data/registration/`, реальные правила — маркер `structures`).
Обоснование каждой проверки — ссылки на читатель
`ЗагрузкаПравилРегистрацииОбъектов` и исполнитель `ОбменДаннымиСобытия` в docstring функций. Главное:

- правила с `Отключить=true` или `Валидное=false` читатель не загружает (`:282-293`) — не проверяются;
- объект ПРО берётся из `ОбъектМетаданныхИмя` (вид — префикс до точки), должен быть в структуре и в составе плана;
- `СвойствоПланаОбмена` — реквизит шапки плана или `ТабличнаяЧасть.Реквизит`; точки дальше — разыменование в
  запросе исполнителя, а не имя реквизита (первая версия дала ложную ошибку на `Сотрудник.Ссылка`);
  таблицы свойств отборов читатель не разбирает — путь берётся из строки;
- расхождение блока `СоставПланаОбмена` со структурой — одно сводное предупреждение на вид расхождения (читатель
  блок пропускает, это признак устаревших правил; у плана `Полный` и его доработанной копии расходятся ~1800 типов).

Правила регистрации БП КОРП с доработками против `bp-ext`: 45 ошибок, все сверены с XML-выгрузкой основной конфигурации и
зафиксированы в `EXPECTED_ERRORS` теста: 23 — объект удалён из конфигурации (21 в `ПоОрганизации`), 20 — объект
есть, но не входит в состав плана, 2 — реквизит отбора переименован или отсутствует
(`ВедомостьНаВыплатуЗарплаты.МестоВыплаты` → `ВидМестаВыплаты`; `ЭтоГруппа` у неиерархических `Пользователи`).

## 5.4. Вынос обработчиков в BSL-обёртки

Код: `src/kd2_rules_mcp/validation/handlers.py` (`export_handlers(rules, out_dir)`, `locate(export, file, line)`),
тесты: `tests/test_validation_handlers.py`.

Эталон — обработка КД `reference/kd2-cfg/DataProcessors/ВыгрузкаОбработчиков`, которая выгружает обработчики во
внешнюю обработку для режима отладки БСП: имена процедур как у неё, параметры — области макета
`Templates/ПараметрыОбработчиков` (тест сверяет таблицу с макетом). Тот же набор параметров передаёт исполнитель БСП
в режиме отладки (например, 17 параметров `ПередКонвертациейОбъекта`, `КонвертацияОбъектовИнформационныхБаз`
`ObjectModule.bsl:489-507`). Файл-обёртка: переменные модуля из шапки `ОбщиеПроцедурыФункции` (`Параметры`,
`Алгоритмы`, `Запросы`, `УзелДляОбмена`, `ОбщиеПроцедурыФункции`), процедура обработчика с телом без изменений,
затем общие процедуры макета (`ВыгрузитьПоПравилу`, `ВыгрузитьРегистр` …) — без них синтакс-чекер не найдёт вызовы.
Карта строк переводит строку файла в адрес правила, событие и строку внутри обработчика.

Табличный макет V8Exchan83 (`УниверсальныйОбменДаннымиXML/Templates/ПараметрыОбработчиков`) расходится с текстовым
макетом КД в пяти областях (например, `ПКС_ПередВыгрузкой` без `ВыгрузитьОбъект`); взят макет КД — его использует
режим отладки БСП.

Макет доработанного плана обмена БП ↔ ЗУП: 42 обработчика → 42 файла (алгоритмов в макете нет).
Прогон 27.09.2026: MCP-синтакс-чекер на bsl-analyzer 0.2.80, инструмент `syntaxcheck`, обёртки
перегенерированы текущим кодом. Скрипт прогона, обёртки и ответы чекера в репозиторий не входят.

- 42 файла, ошибок разбора (`ParseError`) нет. Замечания стиля и сопровождения: 379 предупреждений (334 —
  `UnusedParameters`: обёртка получает все параметры события), 486 информационных, 91 подсказка.
- Одно `Critical` — `ExecuteExternalCode` на `Выполнить(Алгоритмы.ВедомостьНаВыплатуЗарплатыПослеЗагрузки)` в
  ПКО `ВедомостьНаВыплатуЗарплатыРаздатчиком` / `ПослеЗагрузки`: правило запрета `Выполнить` на сервере, не синтаксис.
  Это та же строка, что находит проверка 5.5 (алгоритма нет).
- Намеренная ошибка (`НеизвестнаяФункция(1;` второй строкой `ПередВыгрузкой` ПКО `БанковскиеСчета`) даёт
  `ParseError` в строке 9 файла; `locate` возвращает ПКО «БанковскиеСчета» / `ПередВыгрузкой`, строка 2.
  Замечание на объявлении переменной модуля (`UnusedLocalVariable Алгоритмы`, строка 2) `locate` не адресует — верно.
- **Ограничение:** bsl-analyzer не сообщает о необъявленных переменных и неизвестных процедурах вовсе — проба
  `Результат = НеобъявленнаяПеременная + НеизвестнаяФункция(1); НеизвестнаяПроцедура();` замечаний такого рода не дала.
  Поэтому «нет ложных „переменная не определена“» выполнено, но что контекстные переменные объявлены верно, чекер
  не доказывает: это покажет только синтаксический контроль платформы.

## 5.5. Ссылки обработчиков на алгоритмы

Код: `src/kd2_rules_mcp/validation/algorithms.py` (`check_algorithm_refs(rules)`), тесты:
`tests/test_validation_algorithms.py`. Отдельная проверка, а не часть `check_format`: читатель
файл принимает, ошибка возникает только при выполнении обработчика. Синтакс-чекер 5.4 её не находит —
`Алгоритмы` в обёртке объявлена переменной модуля.

- алгоритмы лежат в структуре `Алгоритмы` (Исп:37, Исп:14664), ключ — `Имя` после `СокрП`, регистр не важен;
- `ЗагрузитьАлгоритм` кладёт в структуру только алгоритмы текущего режима (Исп:6455–6468): при загрузке — с
  `ИспользуетсяПриЗагрузке`, при выгрузке — без него;
- фаза обработчика — по месту вызова в исполнителе (список строк — в docstring модуля);
  `ПоследовательностьПолейПоиска` выполняется при загрузке (`НайтиОбъектПоСсылке`, Исп:8947), при выгрузке
  проверяется только наличие обработчика (Исп:13010); у `ПослеЗагрузкиПравилОбмена` и ПОД проверяется только наличие
  алгоритма;
- нет алгоритма — ошибка `algorithm.missing`; алгоритм только другого режима — ошибка `algorithm.wrong_mode`.

Корпус (34 макета правил обмена): 3 ошибки `algorithm.missing`, несоответствий режима нет. Во всех трёх ПКО
`ВедомостьНаВыплатуЗарплатыРаздатчиком` в `ПослеЗагрузки` вызывает `Алгоритмы.ВедомостьНаВыплатуЗарплатыПослеЗагрузки`,
которого в файле нет: в БП — доработанный план обмена БП ↔ ЗУП и `ОбменЗарплата3Бухгалтерия3`
(`ПравилаОбмена`, в первом — строка 5716 макета), в ЗУП — `ОбменЗарплата3Бухгалтерия3` (`ПравилаОбменаКорреспондента`).
Это дефект правил: при загрузке такой ведомости обработчик упадёт. Находки зафиксированы в тесте корпуса.

## Параметры объекта в обработчике поиска

`src/kd2_rules_mcp/validation/search.py`, входит в `rules_validate`. Добавлено 30.09.2026 по дублю
контрагентов в ДО при обмене из БП (рабочие правила обмена БП → ДО, ПКО «Контрагенты», `ТехПараметр1`).

Загрузка ищет объект сразу по узлу `<Ссылка>` (БСП:10735–10757), в узел ссылки выгрузка пишет только
свойства поиска (БСП:790–826). Параметр ПКС (`ИмяПараметраДляПередачи`) с флагом «Поиск» уходит в ссылку
узлом `<ЗначениеПараметра>` (БСП:12691) и попадает в `ПараметрыОбъекта` до поиска (БСП:8228–8291); без флага —
в свойствах объекта, которые читаются после поиска (БСП:10705).

- `search.param_not_in_search` (предупреждение) — `ПоследовательностьПолейПоиска` читает
  `ПараметрыОбъекта["X"]` / `.Получить("X")`, а ПКС параметра `X` без «Поиск».
- `search.param_not_passed` (предупреждение) — параметр `X` не передаёт ни одно включённое ПКС верхнего уровня.

Корпус макетов проектов (34 файла правил обмена): замечаний нет. Рабочие правила БП → ДО: одно —
`search.param_not_in_search` у ПКО «Контрагенты». Разбор случая и другие грабли — скилл
`.claude/skills/kd2-exchange-pitfalls`.
