# Рабочая папка, проекты правил и несколько агентов

Как сервер хранит то, с чем работает агент, — честно, как есть сейчас, — и соглашения, которые снимают
путаницу. Устройство сервера — [architecture.md](architecture.md), инструменты — [tools.md](tools.md).

## 1. Что где живёт

| Что | Где | Переживает перезапуск сервера |
|---|---|---|
| Структуры метаданных | кэш SQLite (`KD2_CACHE_DIR`; в контейнере — том `kd2_structures_cache`) | да |
| Рабочие проекты правил (`rules_open`, `rules_create`, `registration_build`, `correspondent_draft`) | память процесса и снимок `workspace\.projects\<id>\` | да, пока не `rules_close` |
| Карта строк BSL-обёрток для `handlers_locate` | `handlers.json` в снимке проекта | да, вместе с проектом |
| Сохранённые правила, обёртки обработчиков, архивы | файлы в рабочей папке (`workspace\` репозитория сервера, в контейнере `/data/workspace`) или в `rules_dir` проекта | да |

Для переноса в конфигурацию источник правды — файл `rules_save`. Несохранённые правки лежат в снимке и
переживают перезапуск контейнера (обновление образа, `docker compose up -d --build`, перезагрузка машины).
`rules_close` удаляет снимок; записанный файл не трогает.

## 2. Проекты правил: как есть

- **Идентификатор по файлу.** `rules_open` даёт `<имя>-<хеш>` (`src/kd_rules_mcp/authoring/workspace.py:113`):
  имя файла без расширения, если оно целиком из латинских букв, цифр, `_`, `.` и `-`; иначе латинский префикс
  вида правил (`exchange` или `registration`) — кириллица в идентификатор не входит. Хеш — 4 шестнадцатеричных
  знака SHA-256 нормализованного пути сервера; если такой идентификатор уже занят другим путём — 6, затем 8
  знаков. Повторный `rules_open` того же пути без `private` возвращает тот же проект (`reused: true`), документ не
  перечитывается. Если с момента открытия у файла изменились время или размер — в ответе ещё
  `source_changed: true`: в проекте прежняя копия. Перечитать файл — `rules_close` и снова `rules_open`
  (идентификатор от пути тот же).
- **Идентификатор без файла.** `rules_create` и `registration_build` принимают необязательный `project_id`,
  черновик корреспондента — `new_project_id` (имя `project_id` там уже занято исходным проектом). Пусто —
  `new-<источник>-<приёмник>`, `reg-<план>`, `corr-<исходный проект>`; занятый получает суффикс `-2`, `-3`.
  Имя плана или структуры вне латиницы заменяется коротким хешем, чтобы каталог снимка оставался латинским.
  Явный занятый идентификатор — ошибка `duplicate_project` со списком открытых проектов.
- **Снимок.** После открытия, создания, успешной правки, сохранения и `handlers_export` сервер пишет
  `<рабочая папка>\.projects\<id>\`: `rules.xml` (текущие правила), `meta.json` (вид, пути, признак правок,
  время и размер исходного файла, у приватной копии — `private: true`), `handlers.json` (карта строк
  последнего экспорта). Это одна последняя версия, не история — история живых правил остаётся в git
  `rules_dir`. Отказ правки снимок не меняет.
- **Восстановление.** При старте сервер читает только `meta.json`: проекты сразу видны в `rules_projects`,
  `rules.xml` разбирается при первом обращении к проекту. Битый снимок даёт `rules_format` с путём снимка и
  исходного файла только для этого проекта; остальные работают.
- **Список общий для всех клиентов.** Сервер один; все подключённые агенты видят один `rules_projects` и
  правят один и тот же проект. Владельца у проекта нет. Два клиента, открывшие один файл без флага, работают
  с одним проектом и видят правки друг друга, а `rules_save` любого переписывает общий `saved_path`. Своя
  копия того же файла — `rules_open` с `private: true`, когда два агента правят один файл параллельно: всегда
  новый проект `<идентификатор>-p<N>` (`N` — первое свободное число), документ читается с диска, `reused`
  всегда `false`. Копия — такой же проект (снимок, `rules_save`, `rules_close`, `rules_diff`), `source_path`
  тот же. Правки ведите в копии, общий проект не трогайте. Повторный `rules_open` без флага по-прежнему
  возвращает общий проект и копии не находит.
- **Правки сериализованы.** Вызовы, которые трогают проекты, идут по одному под общей блокировкой
  (`src/kd_rules_mcp/service/base.py:34`): два агента не испортят дерево правил одновременно, но и не узнают о
  чужих правках, пока не перечитают правило (`rules_get`).
- **`handlers_locate` — после `handlers_export`.** Карта строк хранится в проекте и в снимке
  (`src/kd_rules_mcp/service/checks.py:72`); после перезапуска повторный экспорт не нужен. Если экспорта не было —
  отказ `rejected` «сначала handlers_export». Правка обработчика после экспорта сдвигает строки —
  экспортируйте заново перед следующим прогоном чекера.
- **`handlers_export` убирает свои прежние обёртки.** Перед записью из папки удаляются `.bsl` верхнего уровня,
  которые записала прошлая выгрузка (узнаются по заголовку модуля); чужие файлы и подпапки не трогаются
  (`src/kd_rules_mcp/validation/handlers.py`, `export_handlers`). В ответе `removed` — сколько удалено.

**Как работать.** Перед началом — `rules_projects`: нет ли уже открытого проекта с тем же `source_path`.
Повторный `rules_open` того же файла вернёт его (`reused: true`). `source_changed: true` значит, что файл на
диске изменился, а проект держит свою копию — перечитать можно только через `rules_close` и `rules_open`.
Закончили этап — `rules_save`. Проект больше не нужен — `rules_close` (снимок исчезнет, сохранённый файл
останется). После перезапуска сервера проекты на месте: `rules_projects`, затем `rules_get`. Параллельно
с другим агентом над тем же файлом откройте свою копию (`rules_open` с `private: true`) и правьте только её,
не трогая общий проект.

## 3. Соглашение имён в рабочей папке

Рабочая папка — общая для всех задач; без правила в ней быстро копятся папки, по которым не понять, что это.

```
workspace\
  <проект>-<план>-<задача>\          одна папка — одна задача над одним планом обмена
    ExchangeRules.xml                правила обмена (стороны «этого» проекта)
    CorrespondentExchangeRules.xml   правила корреспондента (для комплекта БСП)
    RegistrationRules.xml            правила регистрации
    handlers\                        обёртки обработчиков для синтакс-чекера (handlers_export)
  <проект>-<план>-<задача>.zip       архив для БСП: rules_pack без path кладёт <имя папки>.zip в корень
```

- `<проект>` — идентификатор проекта из `project_list`, чьи правила (сторона «этого узла») правятся;
  `<план>` — имя плана обмена (можно сократить, но однозначно); `<задача>` — короткое слово или номер задачи
  (`pilot`, `dup-fix`, `issue-12`). Латиница, цифры и дефис — без пробелов.
- Файлы — **под именами комплекта БСП**: тогда `rules_pack(folder=…)` соберёт ZIP без перечисления файлов, а
  состав сразу проверяется на загрузку в БСП (два файла — пара правил конвертации, три — комплект).
- Тот же порядок — в `rules_dir` проекта: папка на план обмена, файлы под именами комплекта (README, §1
  «Правила прямо в репозитории проекта»). Тогда рабочую папку для живых правил не нужно вовсе: открыть из
  `rules_dir`, сохранить туда же, обёртки обработчиков — в рабочую папку (`<…>\handlers\`), чтобы не
  коммитить их в проект.
- `rules_save` не перезаписывает существующий файл без `overwrite: true`; относительный путь пишется от корня
  рабочей папки.

## 4. Чистка рабочей папки

Рабочая папка не попадает ни в git, ни в образ (`.gitignore`, `.dockerignore`). Кэш структур — в отдельном томе.
Снимки открытых проектов лежат в `workspace\.projects\` — это состояние сервера, не мусор задачи.

- Можно удалять: папки законченных задач, перенесённых в проект; `handlers\` (пересоздаётся
  `handlers_export`); ZIP после загрузки в базу; разовые проверки.
- `.projects\` удалять только через `rules_close` по каждому проекту. Ручное удаление каталога обрывает
  несохранённые правки так же, как раньше обрывал перезапуск.
- Перед удалением файлов задачи: результат перенесён в проект или в `rules_dir`, а проекты, которые на них
  ссылаются (`source_path`, `saved_path` в `rules_projects`), закрыты. Удаление файла само проект не закрывает.
- Не трогать: папки задач и снимки, которые ещё нужны другому агенту (смотрите `rules_projects`).

## 5. Планируется

- **Владелец проекта** (имя клиента MCP) — понадобится, когда на одном сервере одновременно будут работать
  несколько клиентов; пока не делается.
