# Рабочая папка, проекты правил и несколько агентов

Как сервер хранит то, с чем работает агент, — честно, как есть сейчас, — и соглашения, которые снимают
путаницу. Устройство сервера — [architecture.md](architecture.md), инструменты — [tools.md](tools.md).

## 1. Что где живёт

| Что | Где | Переживает перезапуск сервера |
|---|---|---|
| Структуры метаданных | кэш SQLite (`KD2_CACHE_DIR`; в контейнере — том `kd2_structures_cache`) | да |
| Рабочие проекты правил (`rules_open`, `rules_create`, `registration_build`, `correspondent_draft`) | память процесса сервера | **нет** |
| Карта строк BSL-обёрток для `handlers_locate` | память процесса сервера | **нет** |
| Сохранённые правила, обёртки обработчиков, архивы | файлы в рабочей папке (`workspace\` репозитория сервера, в контейнере `/data/workspace`) или в `rules_dir` проекта | да |

Источник правды — файл: всё, что не сохранено `rules_save`, теряется при перезапуске контейнера (обновление
образа, `docker compose up -d --build`, перезагрузка машины).

## 2. Проекты правил: как есть сейчас

- **Идентификатор — счётчик.** Каждый `rules_open`, `rules_create`, `registration_build` и `correspondent_draft`
  создаёт новый проект с номером `1`, `2`, `3`… (`src/kd2_rules_mcp/authoring/workspace.py:109-113`). Повторный
  `rules_open` того же файла даёт **второй** проект с тем же содержимым — правки в одном не видны в другом.
  После перезапуска счётчик начинается заново: номер `1` может оказаться совсем другим проектом.
- **Список общий для всех клиентов.** Сервер один; все подключённые агенты (разные сессии, разные клиенты)
  видят один `rules_projects` и могут править один и тот же проект. Владельца у проекта нет.
- **Правки сериализованы.** Вызовы, которые трогают проекты, идут по одному под общей блокировкой
  (`src/kd2_rules_mcp/service.py:214`): два агента не испортят дерево правил одновременно, но и не узнают о
  чужих правках, пока не перечитают правило (`rules_get`).
- **`handlers_locate` — только после `handlers_export` в этом же запуске сервера.** Карта строк хранится в памяти
  по идентификатору проекта (`src/kd2_rules_mcp/service.py:605`); после перезапуска или для проекта, у которого
  экспорта не было, — отказ `rejected` «сначала handlers_export». Правка обработчика после экспорта сдвигает
  строки — экспортируйте заново перед следующим прогоном чекера.
- **`handlers_export` убирает свои прежние обёртки.** Перед записью из папки удаляются `.bsl` верхнего уровня,
  которые записала прошлая выгрузка (узнаются по заголовку модуля); чужие файлы и подпапки не трогаются
  (`src/kd2_rules_mcp/validation/handlers.py`, `export_handlers`). В ответе `removed` — сколько удалено.

**Как работать сейчас.** Перед началом — `rules_projects`: нет ли уже открытого проекта с тем же `source_path`.
Открыли — запишите номер в свои заметки вместе с путём источника. Закончили этап — `rules_save`. Потеряли номер
или перезапустили сервер — `rules_projects` / `rules_overview`, иначе снова `rules_open` сохранённого файла. Один
проект правит один агент; второму — `rules_open` того же файла даёт отдельную копию, сливать результат вручную.

## 3. Соглашение имён в рабочей папке

Рабочая папка — общая для всех задач; без правила в ней быстро копятся папки, по которым не понять, что это.

```
workspace\
  <проект>-<план>-<задача>\          одна папка — одна задача над одним планом обмена
    ExchangeRules.xml                правила обмена (стороны «этого» проекта)
    CorrespondentExchangeRules.xml   правила корреспондента (для комплекта БСП)
    RegistrationRules.xml            правила регистрации
    handlers\                        обёртки обработчиков для синтакс-чекера (handlers_export)
  <проект>-<план>-<задача>.zip       архив для БСП: rules_pack без path кладёт <имя папки>.zip в корень
```

- `<проект>` — идентификатор проекта из `project_list`, чьи правила (сторона «этого узла») правятся;
  `<план>` — имя плана обмена (можно сократить, но однозначно); `<задача>` — короткое слово или номер задачи
  (`pilot`, `dup-fix`, `issue-12`). Латиница, цифры и дефис — без пробелов.
- Файлы — **под именами комплекта БСП**: тогда `rules_pack(folder=…)` соберёт ZIP без перечисления файлов, а
  состав сразу проверяется на загрузку в БСП (два файла — пара правил конвертации, три — комплект).
- Тот же порядок — в `rules_dir` проекта: папка на план обмена, файлы под именами комплекта (README, §1
  «Правила прямо в репозитории проекта»). Тогда рабочую папку для живых правил не нужно вовсе: открыть из
  `rules_dir`, сохранить туда же, обёртки обработчиков — в рабочую папку (`<…>\handlers\`), чтобы не
  коммитить их в проект.
- `rules_save` не перезаписывает существующий файл без `overwrite: true`; относительный путь пишется от корня
  рабочей папки.

## 4. Чистка рабочей папки

Рабочая папка не попадает ни в git, ни в образ (`.gitignore`, `.dockerignore`). Удалять можно всё, что не нужно
как результат: сервер не хранит там ничего своего, кэш структур — в отдельном томе.

- Можно удалять: папки законченных задач, перенесённых в проект; `handlers\` (пересоздаётся
  `handlers_export`); ZIP после загрузки в базу; разовые проверки.
- Перед удалением: результат перенесён в проект или в `rules_dir`, а открытые проекты правил, которые ссылаются
  на эти файлы (`source_path`, `saved_path` в `rules_projects`), больше не нужны — удаление файла не закрывает
  проект в памяти.
- Не трогать: папки задач, которые ещё идут у другого агента (смотрите `rules_projects`).

## 5. Планируется

Не реализовано; описано, чтобы не строить на текущем поведении долгих привычек.

- **Идентификатор по файлу.** `rules_open` того же пути возвращает тот же проект (`reused: true`), идентификатор —
  имя файла плюс короткий хеш пути; у `rules_create`, `registration_build`, `correspondent_draft` — свой
  необязательный идентификатор.
- **Снимок после каждой правки** в рабочей папке (`.projects\<id>\` — правила и сведения об источнике), включая
  карту строк `handlers_export`; после перезапуска сервер восстанавливает проекты из снимков. Это одна последняя
  версия, не история — история живых правил остаётся в git `rules_dir`.
- **Владелец проекта** (имя клиента MCP) — понадобится, когда на одном сервере одновременно будут работать
  несколько клиентов; пока не делается.
