# MCP-серверы 1С в работе с правилами обмена

Правило читается по мере надобности, а не в каждой сессии: перед первым вызовом сервера 1С (код, метаданные,
справка, БСП, проверка кода, сервер данных базы) в задаче — когда пишутся или разбираются обработчики и
алгоритмы, нужен API конфигурации или запрос в песочнице. Ссылки — `AGENTS.md`, скиллы `kd2-rules-build`
и `kd2-exchange-pitfalls`; для Cursor — `.cursor/rules/mcp-1c.mdc`.

Серверы экосистемы MCP для 1С (поиск по коду и метаданным, граф, справка платформы, БСП, шаблоны, проверка кода,
сервер данных базы — см. README, «С чем работает в паре») нужны там, где правила касаются кода 1С: обработчики
и алгоритмы, разбор чужих обработчиков, вопросы к API конфигураций, запросы в песочнице. Сопоставление объектов
и реквизитов — инструменты `kd2-rules-mcp` (`structure_*`, `match_*`): они знают расширения и формат КД.

## Какой сервер — для какой базы

- **Серверы кода проекта** подключены с префиксом проекта: `<проект>-1c-code-metadata-mcp`,
  `<проект>-1c-graph-metadata-mcp` и т. п. (список — `code_mcp` в `project_list`). Проект выбирает **фаза
  обработчика**: выгрузочные — проект-источник, загрузочные — проект-приёмник (таблица фаз — скилл
  `kd2-rules-build`, раздел про обработчики). Не искать API приёмника в коде источника.
- **Общие** (без префикса): `1c-syntax-checker-mcp`, `1c-code-check-mcp`, `1C-docs-mcp`, `1c-ssl-mcp`,
  `1c-templates-mcp`.
- **Сервер данных базы** `<проект>-1c-data-mcp` — только у песочниц (`data_mcp` в `project_list`).

## Потребность → инструмент

| Нужно | Сервер и вызов |
|---|---|
| Есть ли объект, реквизит, табличная часть; стандартные реквизиты; поля виртуальных таблиц регистра для запроса | `<проект>-1c-code-metadata-mcp`: `metadatasearch(query, names_only=true, object_type="Справочники")` → `get_metadata_details(object_name="Справочник.Контрагенты", sections="attributes,tabular_parts,standard_attributes")`; для регистра — `sections="virtual_tables"` |
| Код процедуры конфигурации, которую зовёт обработчик | `search_function(name, include_body=false)` → то же с телом (`max_body_chars`); модуль целиком — `get_module_structure(module_path)`; по тексту — `codesearch(query)` |
| Паспорт объекта, где используется | `<проект>-1c-graph-metadata-mcp`: один раз `list_graph_projects` → `project_id`, дальше **в каждом вызове**: `get_object_dossier(object_name, sections=[…], project_id)`, `find_usages_of_object`, `search_code(query, search_type="fulltext"\|"semantic", project_id)` |
| Функция БСП: сигнатура и что возвращает | `1c-ssl-mcp`: `ssl_search(query="ОбщегоНазначения.ЗначенияРеквизитовОбъекта", detail="full")` — имя ищется точно (`lane=exact`, строка `Signature:`); версию БСП в ответе сверить с конфигурацией, код — сервером кода проекта |
| Метод или тип платформы | `1C-docs-mcp`: известно имя — `docinfo(name="Массив.Найти")`, иначе `docsearch(query, detail_level="compact")`; `since` в ответе сверить с режимом совместимости конфигурации (`CompatibilityMode` в `Configuration.xml` выгрузки) |
| Стандарты кода | `1C-docs-mcp`: `standards()` — каталог, `standards(name=…)` — правило целиком |
| Образец кода | `1c-templates-mcp`: `templatesearch(query)` → `get_template(template_id)` |
| Проверка кода обработчика | см. ниже |
| Запрос или код в живой базе | `<проект>-1c-data-mcp`, см. ниже |

## Проверка кода обработчиков

1. `handlers_export` — каждый обработчик отдельным `.bsl` с обёрткой из переменных события (как у КД).
2. По каждому изменённому файлу — `syntaxcheck(code=<текст файла>, file_name="<имя>.bsl")`. **Не**
   `syntaxcheck_file` и не `files=` у `check_1c_code`: эти серверы видят только смонтированные у них корни
   исходников, рабочая папка `kd2-rules-mcp` и папки правил им не видны.
3. Логика и производительность — `check_1c_code(code=…)`; стиль и ИТС — `review_1c_code(code=…)`, по мере
   надобности. Синтаксически битый код в них не отправлять.
4. Номер строки из ответа → `handlers_locate` (обработчик и строка в правилах).

Чекер не ловит необъявленные переменные и вызовы несуществующих методов объектов конфигурации — это проверять
серверами кода проекта. Замечания стиля вроде `CodeOutOfRegion` для текста обработчика — шум.

## Сервер данных базы (песочница)

`validatequery(querytext)`, `vcexecutequery(querytext)` — запрос **в одну строку**, параметры прямо в тексте.
`vcexecutecode(bslcode)` — результат возвращается через переменную `Результат`. Грабли:

- код — **одной строкой**: многострочный не выполняется, ответ пустой (без ошибки);
- нельзя объявлять `Процедура` / `Функция` — код идёт через `Выполнить`;
- нельзя вызвать метод у `Новый Тип(…)` («Неопознанный оператор»): сначала в переменную
  (`З = Новый Запрос(…); Т = З.Выполнить()…`);
- оборачивать в `Попытка … Исключение Результат = ПодробноеПредставлениеОшибки(ИнформацияОбОшибке());
  КонецПопытки;` — иначе ошибка теряется; последняя ошибка журнала — `vcloggetlasterror`;
- запись в базу — только в песочнице и с согласия пользователя; живая проверка обмена целиком —
  `kdbase/exchange_check.py`, не руками.

Сервер не подключился (например, клиент пробует OAuth и получает 404 на базе с пользователями) — это не
отсутствие сервера: заголовок Basic с логином базы пишет `scripts/setup_local.py`, после его запуска клиент
нужно перезапустить. Сам сервис проверяется прямым HTTP-вызовом (`tools/list`).

## Когда сервера нет

Недоступный сервер — не пройденная проверка и не доказательство, что API нет: в отчёте так и писать
(«не проверено: синтаксис — нет 1c-syntax-checker-mcp»). Код и метаданные конфигурации можно читать прямо из
выгрузки проекта (папка из `projects.local.yaml` + `dump` из `project_list`).

## Если в проекте стоит набор правил comol

Подробности по каждому серверу (режимы, формат ответов, коды ошибок) — `<папка проекта>/.claude/skills/
mcp-1c-tools/docs/<сервер>.md` (набор `ai_rules_1c`). Там, где он предполагает исходники проекта (пути файлов
для проверок, единственный проект графа), действует это правило.
