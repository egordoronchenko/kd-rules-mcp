# Архитектура kd2-rules-mcp

Обзор для разработчика и агента, который впервые открывает репозиторий: из каких частей состоит сервер, как
через них идут данные, на каких правилах всё держится, чего сервер не делает и как его развёртывать. Инструкция
для пользователя — [README](../README.md), установка — [INSTALL.md](INSTALL.md), список инструментов —
[tools.md](tools.md), проверки — [checks.md](checks.md), термины — [glossary.md](glossary.md).

Ссылки `src/…:N` — строки кода на момент написания (01.10.2026); `reference/kd2-cfg/…:N` — строки XML-выгрузки
конфигурации «Конвертация данных» 2.1.8.2 (эталон формата, в репозитории его нет — см. README, «Разработка»);
`БСП:N` — строки модуля объекта обработки `КонвертацияОбъектовИнформационныхБаз` в БСП 3.1.12.

## 1. Принцип

Сервер **детерминированный**: разбирает выгрузки конфигураций и файлы правил, предлагает кандидатов
сопоставления, точечно правит, пишет XML и проверяет. Что во что конвертировать, решает агент; его решения видны
в ответах инструментов и в диффе файла правил. Источник правды — XML-файл правил: всё, что живёт в памяти
сервера, — временное состояние до `rules_save`.

## 2. Слои и модули

Слои зависят только от нижележащих: формат не знает о SQLite, структуры — о правилах, проверки принимают модель
правил и соединения со структурами, сервис собирает всё вместе, транспорт — только регистрирует инструменты.

Пути модулей — от `src/kd2_rules_mcp/`, кроме `kdbase/`, `scripts/` и знаний агента.

Связность модуля менеджера: снимок `ed_open` → индекс ссылок `ed/refs.py` (один раз на проект, рядом со снимком)
→ отчёт `validation/ed_links.py` в `ed_validate`. Снимок документа остаётся тем же. `ed_close` освобождает снимок
и оба индекса.

В `ed_validate` сервис дополнительно собирает снимок структуры из существующего кэша и профиль
из открытой схемы: версия, базовый URI и явно активные расширения. Профиль один раз индексирует
эффективные свойства каждого типа и свойства по идентификатору; разрешение тысяч ПКС использует
эти индексы, публичное разрешение пути сохраняет прежний результат. Чистые проверки схемы и
структуры возвращают отчёты; сервис объединяет их со связностью, сортирует замечания по исходным
координатам, устраняет дубли двух направлений и добавляет `profile`/`coverage`. Пропуски сохраняются
при отборе и пагинации. Профиль содержит SHA-256 снимков для воспроизводимости отчёта.
DTO структуры хранится в памяти по её идентификатору и отпечатку входа с версиями загрузчика и схемы
кэша; изменённый вход перестраивает DTO. Чтение DTO и чистые проверки выполняются вне общей блокировки
сервиса. Общий контекст проверок в `validation/ed_structure_snapshot.py` агрегирует пропуски и покрытие
по уникальным экземплярам «проверка × декларация», устраняя повтор направления.
Реестр схем не содержит снимков структуры и не пишет новый дисковый кэш.

Маршруты версий формата читает `ed/routes.py` в профиль одной основной выгрузки. Сервис вызывает
`select_route` до загрузки схем и передаёт в `compare_routes` схему только под её собственным URI.
Ошибка чтения пакета становится пропуском проверки, статус отчёта сервис не повышает. Снимки живут
в памяти процесса, отдельного закрытия нет. Эти инструменты не входят в `ed_validate` и не читают
версию узла.

## 3. Поток данных

```
XML-выгрузка конфигурации + расширения ── structures/xmldump → xmlbuild ──┐
                                                                          ├─→ structures/store: SQLite,
файл MD83Exp ───────────────────────────── structures/md83exp ───────────┘    одна структура = один файл
                                                                                     │ structures/queries
projects.yaml + projects.local.yaml ── projects ──→ project_list, structure_load_project
                                                                                     │
XML правил (макет плана обмена, файл комплекта) ── kd2/rules_io ──→ модель (kd2/model, kd2/schema)
                                                                     │               │
                       authoring/candidates ←───────────────────────┼───────────────┘
                       authoring/edits · registration · correspondent ┤  (рабочий проект в памяти,
                                                                     │   authoring/workspace)
                       validation/format · structure · algorithms · search · registration
                                                                     │   → validation/report
                       validation/handlers → .bsl-обёртки → синтакс-чекер (вызывает агент)
                                                                     │
                       kd2/rules_io.dump_rules ──→ XML в рабочей папке или rules_dir проекта
                                                                     │
                       authoring/pack ──→ ZIP для загрузки в БСП
                                                                     │
       kdbase: kd_check (база КД) · bsp_check (песочница, без записи) · exchange_check (живой обмен)

server.py (MCP, streamable HTTP /mcp) ──→ service/ (Kd2Service, PathMap, Settings) ──→ всё выше
```

Вызов инструмента: клиент → `server.py` (схема параметров, `call` в рабочем потоке,
`src/kd2_rules_mcp/server.py:144`) → метод `Kd2Service` → модули слоёв → словарь ответа. Любое исключение
превращается в JSON с полем `code`: `Kd2Error` и `ValueError` — по таблице `ERROR_CODES`
(`src/kd2_rules_mcp/server.py:49`, `:126`), прочие — код `internal`, трассировка в логгер `kd2_rules_mcp`.
Каждый вызов даёт строку лога INFO (инструмент, миллисекунды, итог); уровень — `KD2_LOG_LEVEL`.

## 4. Инварианты

- **Применимость ED.** Ложные условия не применяются, неизвестные дают `skipped`, не успешную
  проверку. Imports не активируют расширения. BSL условий и обработчиков не исполняется;
  допустимы только известные сравнения версии и логические формы. Покрытие направлений остаётся
  отдельным от покрытия строк читателя. Ноль новых замечаний проверяется в том же профиле.

- **Детерминизм.** Сервер не принимает смысловых решений: кандидаты с `auto: false` и класс «по синониму» —
  только подсказка; ПКС без пары создаются выключенными, как в КД.
- **Схема из писателей КД.** Порядок тегов и политика «выводить только не-дефолт» выписаны из строк
  `ВыгрузкаКонвертации` и `ВыгрузкаРегистрации`, у каждого слота схемы — ссылка `ВК:N`/`ВР:N`
  (`src/kd2_rules_mcp/kd2/schema.py:1-8`). Новый тег без ссылки на эталон не добавляется.
- **Смысловое равенство, не побайтовое.** Round-trip проверяется канонической формой К1–К8
  (`src/kd2_rules_mcp/kd2/canonical.py:8-30`), каждое правило канонизации покрыто тестом
  (`tests/test_canonical.py`); стиль исходника (BOM, объявление, отступы, концы строк) хранится отдельно
  (`kd2/xmlstyle.py`). Смысловой дифф (`kd2/diff.py`) пользуется теми же правилами нормализации:
  концы строк, пустые и дефолтные значения не становятся изменениями.
- **Неизвестное не теряется.** Теги вне схемы хранятся как lxml-элементы и выводятся обратно
  (`src/kd2_rules_mcp/kd2/model.py:1-5`); их судьбу у читателя БСП оценивает `validation/format.py`.
- **Каждый факт о формате — со ссылкой** `reference/kd2-cfg/…:N` или `БСП:N`; без неё — пометка «(вывод)».
  Это пункт 4 «Когда задача готова» в `AGENTS.md`.
- **Источник правды — файл.** Проекты правил — временное состояние в памяти; запись — только в рабочую папку и
  в `rules_dir` проектов, всё остальное смонтировано на чтение. Пути агента переводятся `PathMap`
  (`src/kd2_rules_mcp/service/paths.py:13`).
- **Кэш структур самоинвалидируется.** Ключ — отпечаток выгрузки (`Configuration.xml` и `ConfigDumpInfo.xml`,
  без него — полный обход) плюс хеш исходников загрузчика: `LOADER_VERSION` и `BUILDER_VERSION`
  (`src/kd2_rules_mcp/structures/store.py:36-37`). Изменился код загрузчика — структура пересобирается при
  следующей загрузке.
- **Отказ правки — с откатом.** Правка, после которой правило ссылается на отсутствующее правило, объект или
  свойство, отклоняется целиком; полуприменённых правил нет (`authoring/edits.py`).
- **Компактные ответы.** Списки постраничные (`offset`, `limit` ≤ 200, `has_more`); XML правил в ответ не
  попадает, тексты обработчиков в `rules_get` обрезаются до 2000 символов (`TEXT_LIMIT`,
  `src/kd2_rules_mcp/kd2/diff.py`; сервис импортирует предел оттуда).
- **Лестница проверок.** Каждая следующая проверка доказывает то, чего не может предыдущая: `rules_validate` →
  синтакс-чекер → `kd_check` → `bsp_check` → `exchange_check`. Подробно — [checks.md](checks.md).
- **Статус маршрута не повышается.** `ed_route_compare` отдаёт статус, который посчитали проверки.
  Пропуск не превращается в совместимость. Снимки маршрутов
  живут только в памяти процесса.
- **Авторинг ED.** `authoring/ed` и `validation/ed_authoring.py` не импортируют сервис и транспорт.
  Новые замечания выбранных профилей и относящиеся к операции непроведённые проверки блокируют
  выпуск. Перед write сверяются входы, хеш preview и подтверждения каждой операции. Каталог
  комплекта — только `workspace/ed-authoring/<name>-<uuid8>`, с запретом ссылок и чужих файлов;
  подготовка рядом, сверка прежних байтов и переименование под общей блокировкой сервиса.

## 5. Состояние сервера

| Что | Где живёт | Переживает перезапуск контейнера |
|---|---|---|
| Структуры метаданных | SQLite-файлы в каталоге кэша (`KD2_CACHE_DIR`, в контейнере — том `kd2_structures_cache`) | да |
| Рабочие проекты правил | память `RulesWorkspace` и снимок `<рабочая папка>/.projects/<id>/` (`rules.xml`, `meta.json`; `src/kd2_rules_mcp/authoring/workspace.py:245`) | да, пока не `rules_close` |
| Проекты ED | неизменяемые снимки, индексы адресов и индекс ссылок в памяти `EdMixin`, под той же блокировкой сервиса | нет; после перезапуска нужен `ed_open` |
| Схемы формата ED | неизменяемые снимки замыкания импортов в памяти `EdSchemaMixin`, реестр и публикация под общей блокировкой сервиса, разбор вне неё | нет; после перезапуска нужен `ed_schema_open` |
| Профили маршрутов ED | снимки выгрузок в памяти `EdRoutesMixin`; разбор вне общей блокировки | нет; после перезапуска нужен `ed_routes`. До 32 снимков и 128 МиБ, вытеснение по давности, отдельного закрытия нет |
| Входы авторинга ED | кэш прочитанных входов по хешам в `EdAuthoringMixin`, до 32 записей и 128 МиБ исходных текстов; отдельного хранимого проекта авторинга нет | нет; прежние решения читаются из manifest комплекта |
| Комплект доработки ED | XML/BSL, инструкция, manifest и полный отчёт в рабочей папке | да; обновляется только собственное неизменённое содержимое |
| Карта строк обёрток обработчиков (`handlers_locate`) | поле проекта и `handlers.json` снимка (`src/kd2_rules_mcp/authoring/workspace.py:239`, `src/kd2_rules_mcp/service/checks.py:72`) | да |
| Сохранённые правила, обёртки, архивы | файлы в рабочей папке (`KD2_WORKSPACE`) и `rules_dir` проектов | да |

При старте рабочая папка читает только `meta.json` снимков
(`src/kd2_rules_mcp/authoring/workspace.py:376`): проекты сразу есть в списке, `rules.xml` разбирается при
первом `get` (`src/kd2_rules_mcp/authoring/workspace.py:161`). Битый снимок даёт ошибку формата с путём снимка и исходного файла только
при обращении к этому проекту. Снимок пишется после открытия, создания, успешной правки
(`src/kd2_rules_mcp/service/base.py:65`), сохранения и экспорта обработчиков: во временный файл того же каталога и
`os.replace`, под той же блокировкой, что и правки. `rules_close` удаляет проект из памяти и каталог снимка,
файлы `rules_save` не трогает (`src/kd2_rules_mcp/authoring/workspace.py:262`).

Вызовы, которые трогают проекты правил, сериализованы одной блокировкой `threading.RLock`
(`src/kd2_rules_mcp/service/base.py:34`): правки идут по одному, загрузка большой структуры параллельно им не мешает.
Все клиенты одного сервера видят общий список проектов. Как с этим работать — [workflow.md](workflow.md).

Схемы XDTO не записываются в SQLite или рабочую папку. Повторный `ed_schema_open` возвращает
`reused=true`; при изменении любого прочитанного источника `source_changed=true`, прежний снимок
сохраняется до `ed_schema_close` и нового открытия. Пределы: 32 MiB на файл, 128 MiB и 128 файлов
на схему, 256 открытых схем или 512 MiB исходных байтов. Автоматического вытеснения нет.

## 6. Границы: что сервер делает и чего не делает

Делает: читает и пишет `ПравилаОбмена` 2.01 и `ПравилаРегистрации`, собирает структуры метаданных, предлагает
кандидатов, правит правила по адресу, строит правила регистрации и черновик корреспондента, проверяет правила
по формату и структурам, готовит код обработчиков к внешнему синтакс-чекеру, собирает ZIP для БСП,
читает модуль менеджера, схему и маршруты версий EnterpriseData.

Не делает:

- **Произвольные изменения КД 3 / EnterpriseData.** Первый срез авторинга добавляет прямую ПКС
  шапки существующего ПКО перехватчиком в расширении. Обработчики, таблицы, ссылки, изменение
  карты версий, автоматическое слияние чужого расширения и установка в базу в него не входят.
- **Версия узла и живой обмен в маршрутах.** `ed_routes` и `ed_route_compare` не читают версию узла,
  не накладывают расширения конфигурации, не исполняют обмен и не входят в `ed_validate`. Отчёт —
  статическая совместимость декларативных карт. Предупреждение о более новом пакете вне карты —
  подсказка, не требование обновить маршрут.
- **Исполнение обмена.** Выгрузку и загрузку данных делает платформа по готовым правилам; сервер только готовит
  и проверяет правила. Живой обмен в песочницах запускает `kdbase/exchange_check.py`, а не сервер.
- **Запись в исходники проектов 1С.** Сервер не пишет в макеты планов обмена (`Templates\…\Ext\Template.txt`):
  перенос туда — отдельный шаг агента или человека по правилам проекта (захват в хранилище, обновление базы).
  Исключение — папка живых правил проекта (`rules_dir`), заведённая специально под файлы правил.
- **Редактирование в КД.** Сервер не работает с базой «Конвертации данных» и не синхронизируется с ней; база КД
  нужна только для финальной проверки `kd_check`.
- **Смысл обработчиков.** Синтакс-чекер ловит синтаксис, но не смысл; смысл проверяет только живой обмен.
- **Внешние проверки как инструменты MCP.** `kd_check`, `bsp_check`, `exchange_check` по-прежнему не инструменты
  сервера. Толстый клиент и COM нужны `kd_check` и COM-ветке `bsp_check`; ветка сервера данных и
  `exchange_check` ходят в песочницу по HTTP.
- **Вызов синтакс-чекера.** Сервер выносит обработчики в файлы и отдаёт карту строк; проверку запускает агент
  своими серверами MCP для 1С.

## 7. Решения, которые стоит знать

Краткая выжимка проектных решений (полностью — в спецификациях проекта).

| № | Решение | Почему так |
|---|---|---|
| Д1 | Python 3.12, официальный MCP SDK, streamable HTTP, `lxml`, SQLite, pytest; порт 8060 | потоковый XML и тесты удобнее на Python; `lxml` контролирует вывод (порядок атрибутов, экранирование) |
| Д2 | Одна модель структуры с двумя входами — XML-выгрузка с расширениями и MD83Exp; ключ — имена (`Тип.Имя`, путь свойства), GUID файла только внутри файла | у MD83Exp GUID случайные на каждый прогон; эталон сборщика — MD83Exp той же базы |
| Д3 | Кэш: одна структура — один файл SQLite, повторная загрузка с тем же отпечатком — без разбора | выгрузка типовой конфигурации — около гигабайта, в памяти её не держать |
| Д4 | Модель правил — дерево, повторяющее XML; смысловое равенство через каноническую форму; стиль исходника запоминается | генерация шаблонами без модели не даёт точечных правок и проверок |
| Д5 | Источник правды — XML-файл; рабочий проект в памяти; запись в рабочую папку и `rules_dir` | запись прямо в макеты обходит захват объектов в хранилище |
| Д6 | Адресация: ПКО, ПВД, ПОД, алгоритмы, запросы — по коду или имени; ПКС — код ПКО + путь `группа/…/свойство-приёмник`; ПКЗ — код ПКО + значение источника | правки принимают частичные изменения полей, а не правило целиком |
| Д7 | Кандидаты — по алгоритму автонастройки КД («точно», «синоним КД») плюс класс «по синониму» только как подсказка | автоматическое сопоставление не должно делать смысловых ошибок |
| Д8 | Черновик корреспондента — зеркалирование ПКО, ПКС, ПКЗ; обработчики не переносятся, отдаются списком | обработчики привязаны к направлению; в КД такого механизма нет |
| Д9 | Правила регистрации — из состава плана обмена структуры-источника, объекты по умолчанию — по ПВД | блок `СоставПланаОбмена` пишется, как у КД, хотя читатель БСП его пропускает |
| Д10 | Код обработчиков проверяется внешним синтакс-чекером по BSL-обёрткам с контекстными переменными | сервер не связывается с другими контейнерами |
| Д11 | Финальная сверка — штатной загрузкой в базу КД на копии базы в толстом клиенте | модуль `ЗагрузкаКонвертации` работает только в толстом клиенте |

## 8. Развёртывание и безопасность

### 8.1 Контейнер

Образ — `python:3.12-slim` в две стадии, зависимости строго по `uv.lock`; сервер работает от пользователя
uid 1000, корень нужен только точке входа, чтобы отдать тома (`Dockerfile:40-52`). Базовый
`docker-compose.yml` не содержит путей машины; папки проектов, `rules_dir` и перевод путей дописывает
`scripts/setup_local.py` в `docker-compose.override.yml`.

| Путь в контейнере | Откуда | Доступ |
|---|---|---|
| `/config/projects.yaml` | `projects.yaml` репозитория | только чтение |
| `/structures` | `structures\` репозитория (файлы MD83Exp) | только чтение |
| `/projects/<проект>` | папка проекта из `projects.local.yaml` | только чтение |
| `/rules/<проект>` | `rules_dir` проекта, если папка существует | **запись** |
| `/data/workspace` | `workspace\` репозитория (рабочая папка) | **запись** |
| `/data/cache` | именованный том `kd2_structures_cache` (`KD2_CACHE_VOLUME`) | запись (кэш структур) |

`scripts/setup_local.py` пишет `.env` в каталоге репозитория (compose читает его сам) по полям `bind`, `port` и
`instance` в `projects.local.yaml`. Нет ни одного из них — файла нет, действуют умолчания. Внутри контейнера
порт процесса не меняется (в образе `KD2_PORT=8060`); `port` — только публикуемый порт хоста.

| Переменная | Когда пишется | Умолчание в `docker-compose.yml` |
|---|---|---|
| `KD2_BIND` | задан `bind` | `127.0.0.1` |
| `KD2_PUBLISHED_PORT` | задан `port` | `8060` |
| `KD2_CONTAINER` | задан `instance` | `kd2_rules_mcp` |
| `KD2_CACHE_VOLUME` | задан `instance` | `kd2_structures_cache` |
| `COMPOSE_PROJECT_NAME` | задан `instance` | `kd2-rules-mcp` |

`instance` — суффикс второго экземпляра (`[A-Za-z0-9_-]+`): контейнер `kd2_rules_mcp_<instance>`, том
`kd2_structures_cache_<instance>`, проект `kd2-rules-mcp-<instance>`. Имя проекта в файле —
`${COMPOSE_PROJECT_NAME:-kd2-rules-mcp}`; заданная переменная его перекрывает. `port` — целое 1…65535.
После правки — снова `setup_local.py` и `docker compose up -d`.

Переменные окружения (`Settings.from_env`, `src/kd2_rules_mcp/service/paths.py:88-114`): `KD2_HOST`, `KD2_PORT`,
`KD2_TOKEN` (общий секрет; пусто — заголовок не проверяется), `KD2_CACHE_DIR`, `KD2_WORKSPACE`,
`KD2_PATH_MAP` (`путь_агента=путь_сервера;…`), `KD2_PROJECTS_FILE`, `KD2_PROJECT_DIRS`, `KD2_RULES_DIRS`,
`KD2_LOG_LEVEL` (уровень лога, по умолчанию `INFO`). `KD2_IN_CONTAINER` читает `main()`
(`src/kd2_rules_mcp/server.py:798`): её ставит образ, см. §8.2. Без Docker сервер запускается
`uv run kd2-rules-mcp`; тогда папки проектов берутся из
`projects.local.yaml` рядом с `projects.yaml`, а `rules_dir` — от них.

### 8.2 Сеть и авторизация

- `docker-compose.yml` публикует порт как `${KD2_BIND:-127.0.0.1}:${KD2_PUBLISHED_PORT:-8060}:8060`
  (`docker-compose.yml:30`): по умолчанию сервер виден **только своей машине** на 8060. Клиент —
  `http://localhost:8060/mcp`. Другой порт — `port` в `projects.local.yaml` и тот же порт в `server_url`.
  Второй экземпляр на машине — `instance` (свои контейнер, том и проект compose, §8.1).
- В образе `KD2_HOST=0.0.0.0` (`Dockerfile:35`) — это адрес **внутри контейнера**. Наружу порт отдаёт compose,
  не процесс. Образ ставит `KD2_IN_CONTAINER=1` (`Dockerfile:39`).
- Проверка «хост вне петли без токена» в `main()` смотрит `KD2_HOST` только когда `KD2_IN_CONTAINER` **не**
  задана (`server.py:798`). Иначе контейнер с `KD2_HOST=0.0.0.0` не стартовал бы никогда, хотя снаружи порт
  закрыт петлёй. Без Docker `uv run kd2-rules-mcp` слушает `127.0.0.1` (значение по умолчанию `Settings.host`,
  `service/paths.py:77`) и этой переменной нет: хост не петлевой (петля — `127.0.0.1`, `localhost`, `::1`)
  без `KD2_TOKEN` — `SystemExit`. Это вторая линия; `setup_local.py` такую конфигурацию не создаёт.
- Командный сервер: в `projects.local.yaml` поля `bind` (адрес интерфейса) и `token`. `bind` вне петли без
  `token` — `load_local` отказывает (`ProjectConfigError`). `setup_local.py` пишет `KD2_BIND` в `.env` и
  переменную `KD2_TOKEN` в override, а в `.mcp.json` и `.cursor/mcp.json` — заголовок
  `Authorization: Bearer <token>`. Пустой `bind` с `token` допустим: токен проверяется и на петле. Если порт в
  `server_url` не равен публикуемому, скрипт предупреждает.
- При заданном `KD2_TOKEN` запрос к `/mcp` без этого заголовка или с другим токеном — HTTP 401, тело
  `{"error": "unauthorized"}` (`create_app`, `server.py:764`). Сравнение — `hmac.compare_digest`. Пустой токен —
  проверка выключена.
- Пути контейнера в ответах переводятся в пути агента. Если файл по переданному пути не найден, в тексте
  остаётся путь агента и подсказка, что путь не входит в подключённые папки проектов (`project_list`);
  внутренний путь не показывается (`service/base.py:143`).

### 8.3 Рекомендации

- **Один разработчик на своей машине** — не задавайте `bind` и `token`. Порт уже на петле, клиенты на той же
  машине подключаются к `http://localhost:8060/mcp`.
- **Сервер для команды** — `bind` и длинный `token` в `projects.local.yaml`, затем `setup_local.py`. `server_url`
  — адрес, по которому коллеги достучатся (не `localhost`: скрипт об этом предупредит). Кто знает токен,
  вызывает любые инструменты, в том числе запись в `rules_dir`.
- Не публикуйте порт на внешний интерфейс без токена: `setup_local.py` откажется, запуск вне контейнера — тоже.

## 9. Как добавить

### 9.1 Новый инструмент

Метод в нужном миксине пакета `service/` (`src/kd2_rules_mcp/service/<модуль>.py`) — логика без транспорта:
принимает пути агента, переводит их через `_read_path` / `_writable` (`service/base.py`), правки проектов —
под `self._lock`, ответ — компактный словарь (списки — через `slice_rows`/`page_view` в `service/views.py`).
Затем функция с `@server.tool()` в `create_server` (`src/kd2_rules_mcp/server.py:128`):
каждый параметр — `Annotated[…, Field(description=…)]`, docstring — описание инструмента для агента; вызов —
`await call(service.<метод>, …)`. Новый вид отказа — подкласс `Kd2Error` в `errors.py` и строка в
`ERROR_CODES` (подклассы раньше базовых). Тесты: имя — в `EXPECTED_TOOLS` и вызов в `tests/test_server.py`
(проверяет описания всех параметров), содержательные — отдельным файлом; затем `uv run python
scripts/dump_tools.py` обновляет [tools.md](tools.md), а ключи ответа дописываются в его ручную часть. Если
инструмент меняет порядок работы — `INSTRUCTIONS` сервера и скилл `kd2-rules-build`.

### 9.2 Новая проверка правил

Для ED чистая функция в `validation/` принимает неизменяемые снимки документа, схемы/структуры
и индекс `ed/address.py`; новая проверка подключается в `service/ed.py`, идентификатор и причины
пропуска документируются в [checks.md](checks.md). Уровень и последствие подтверждаются строками
`XDTO:N`; непрозрачный источник не превращается в доказанную потерю. `ValidationReport` остаётся
общим для всех форматов. Тесты фиксируют нарушение, чистую границу, адрес, сообщение, пропуск и
профильный результат корпуса; статический отчёт не доказывает живой обмен.

Модуль или функция в `validation/` возвращает `ValidationReport` (`validation/report.py`); идентификатор
проверки — константа вида `"<группа>.<суть>"` (`format.*`, `structure.*`, `algorithm.*`, `search.*`,
`registration.*`), адрес — через `validation/address.py`. В docstring модуля — обоснование уровня (ошибка или
предупреждение) строкой читателя БСП (`БСП:N`); без строки — «(вывод)». Подключение — в
`Kd2Service.rules_validate` (`src/kd2_rules_mcp/service/checks.py:21`). Тесты: синтетические нарушения и «чистый»
случай в `tests/test_validation_<группа>.py`, прогон без исключений на корпусе (`corpus_params`), строка в
таблице идентификаторов [checks.md](checks.md).

### 9.3 Новый тег схемы

Слот в виде элемента `kd2/schema.py` — на том месте, где его выводит писатель КД, с политикой, повторяющей
писатель, и комментарием `ВК:N` или `ВР:N`. Если читатель БСП обращается с тегом не так, как с остальными
полями вида, — решение `TagRule` в `validation/format.py` со строкой `БСП:N`. Если писатель опускает значение
по умолчанию по-особому — правило канонизации в `kd2/canonical.py` и тест в `tests/test_canonical.py`. Тесты:
разбор и вывод в `tests/test_rules_io.py`, проверка формата в `tests/test_validation_format.py`; изменение
парсера или сериализатора требует round-trip на корпусе (`KD2_CORPUS_DIRS`, README «Разработка»).
