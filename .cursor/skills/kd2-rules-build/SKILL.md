# Правила обмена КД 2 через `kd2-rules-mcp`

Сервер — `kd2-rules-mcp` из `.mcp.json` (его пишет `scripts/setup_local.py`). Он детерминированный:
разбирает, предлагает кандидатов, пишет XML и проверяет. Что во что конвертировать, решает агент — и пишет
это в отчёт. Пути передаются как на этой машине; сервер пишет только в рабочую папку
(`workspace\` репозитория). Перенос результата в `Templates\…\Ext\Template.txt` проекта 1С — по правилам того
проекта (захват в хранилище, его проверки), не этим сервером.

## 0. Структуры

1. `project_list` — проекты из `projects.yaml`: конфигурации, базы (роль «песочница»/«боевая»), серверы кода,
   обмены (какой план между какими проектами).
2. **В начале каждой задачи** — `structure_load_project(project)` для обеих сторон обмена (структура
   `<проект>-full`): сервер сам знает папку проекта, выгрузку и активные расширения. Изменение выгрузки он видит
   только при загрузке — по `Configuration.xml` и `ConfigDumpInfo.xml`, которые Конфигуратор переписывает при
   каждой выгрузке; неизменённая берётся из кэша за доли секунды (`reused: true`), изменённая собирается заново
   (БП ~1 мин, ЗУП ~35 с, ДО ~12 с). После ручной правки XML выгрузки без Конфигуратора — `force: true`.
   Выгрузка вне проектов — `structure_load_xml` по путям или `structure_load_md83exp` (файл MD83Exp).
3. **Что изменилось после обновления конфигурации:** загрузить новую выгрузку под новым идентификатором
   (`zup-2026-10`), `structure_compare` со старой, затем `rules_validate` правил против новой структуры — это
   список ПКО/ПКС, которые сломало обновление (удалённые и переименованные реквизиты, сменившиеся типы).
4. Приёмник без выгрузки подменять похожей конфигурацией можно только осознанно: все замечания про объекты,
   которых нет в подмене, заранее известны и не считаются ошибками правки (пилот: типовой ЗУП вместо
   доработанной конфигурации-приёмника дал 6 «чужих» ошибок).

## 1. Правила

- Доработка: `rules_open` макета проекта → `rules_validate` со структурами **до правок** — запомнить исходные
  замечания, чтобы потом сравнивать только новые.
- Новые правила: `rules_create(source, target)` — пустой заголовок как у КД.
- Смотреть: `rules_list` (раздел, `text`), `rules_get` — одно правило; перед созданием своего откройте
  1–2 похожих существующих ПКО/ПВД/ПКС и оформите так же (флаги ПКО, `Поиск` у ключевых ПКС).

## 2. Порядок построения: ПКО → ПКС → ПВД → ПРО

1. **Выбор объекта.** `match_objects` **всегда с `text`** (и `kind`): стандартных объектов в двух типовых
   конфигурациях сотни, без фильтра ответ не влезает в лимит клиента. Или `structure_objects(text=…)` по обеим
   структурам. Проверьте, что ПКО для объекта ещё нет (`rules_list pko`).
2. **ПКО с ПКС** — `pko_create_from_candidates`: включены пары «точно» и «синоним КД», свойства приёмника без
   пары — выключенные ПКС. Разберите ответ:
   - `unresolved` — ссылочные свойства без однозначного ПКО: задать код существующего ПКО (`rule_update`
     поля `КодПравилаКонвертации`), создать нужное ПКО или выключить (`Отключить: true`) с причиной;
   - `not_applied` — пары с `auto: false` («примитив → ссылка», «по синониму»): только решением агента;
   - составные ссылочные поля с десятками типов (доп. реквизиты, наборы доступа БСП) обычно выключаются.
   Флаги ПКО (`СинхронизироватьПоИдентификатору`, `ПродолжитьПоискПоПолямПоискаЕслиПоИдентификаторуНеНашли`)
   и `Поиск` у ключевых ПКС — по образцу соседних ПКО правил. Обработчик `ПоследовательностьПолейПоиска` —
   с оглядкой на скилл `kd2-exchange-pitfalls` (параметры при поиске, варианты, пустой ИНН).
3. **ПКЗ** для перечислений — `match_values` и `rule_create kind=pkz` (owner — код ПКО).
4. **ПВД** — `rule_create kind=pvd`: `ОбъектВыборки` (тип источника), `КодПравилаКонвертации` (новое ПКО),
   `СпособОтбораДанных` — по образцу существующего ПВД; обработчик — только если он действительно нужен.
5. **ПРО** — `registration_build(structure_id источника, exchange_plan, rules_project_id=…)`: объекты берутся
   из ПВД; объект вне состава плана обмена — предупреждение «добавить в состав плана в конфигурации». Отборы
   (`plan_filters`, `object_filters`) — через `objects`. Правила регистрации — отдельный проект, свой `rules_save`.
6. Обратное направление — `correspondent_draft`: только черновик; обработчики из списка переносит агент,
   выключенные ПКС разбирает.

### Код обработчиков — против какой конфигурации писать

Обработчик выполняется в базе своей фазы: **выгрузочные** (ПВД, ПКО `ПередВыгрузкой`/`ПриВыгрузке`/
`ПослеВыгрузки`/`ПослеВыгрузкиВФайл`, все ПКС и группы ПКС, события конвертации выгрузки) — в базе-источнике;
**загрузочные** (ПКО `ПередЗагрузкой`/`ПриЗагрузке`/`ПослеЗагрузки`/`ПоследовательностьПолейПоиска`, события
конвертации загрузки, `ПослеЗагрузкиПараметра`) — в базе-приёмнике; алгоритм — в базе по флагу
`ИспользуетсяПриЗагрузке`. Отсюда источники:

1. Доступные переменные события — `handlers_export` (обёртка с точным набором параметров, как у КД).
2. API своей конфигурации — серверы кода проекта `<проект>-…` из `.mcp.json` (список — `code_mcp` в
   `project_list`): для выгрузки — проекта-источника, для загрузки — проекта-приёмника.
3. Образцы — обработчики типовых правил того же плана обмена в обеих конфигурациях (`rules_open` макета →
   `handlers_export`), затем корпус макетов проектов.
4. Платформа и БСП — `1C-docs-mcp`, `1c-ssl-mcp`, шаблоны — `1c-templates-mcp`.

Проверка: `handlers_export` → `1c-syntax-checker-mcp` по файлам → `handlers_locate`; ревью —
`1c-code-check-mcp`. Запрос или вызов API из обработчика можно проверить в живой песочнице своей фазы —
сервер данных базы (`data_mcp` в `project_list`, например `do-1c-data-mcp`): `validatequery`, `vcexecutequery`,
`vcexecutecode` без записи (`Записать`, `Удалить`, транзакции — только с согласия пользователя). Смысл
проверяет только живой обмен в песочницах.

Ответы правок: `address` — что изменено; `skipped` — «правка применена, проверка по структуре не выполнена»
(передайте `source_structure`/`target_structure`, чтобы проверка была); ошибки — JSON с `code`
(`dangling_reference` — ссылка на несуществующее ПКО, `duplicate_rule`, `unknown_field` …).

## 3. Чек-лист проверок (все — до переноса в проект)

- [ ] `rules_validate` с обеими структурами: **нет новых** ошибок относительно шага 1 (формат, структуры,
      ссылки на алгоритмы и их режим загрузки/выгрузки).
- [ ] Добавлялся код обработчиков — `handlers_export` → синтакс-чекер (`1c-syntax-checker-mcp`) по файлам →
      строка ошибки → `handlers_locate`. Чекер не ловит необъявленные переменные — только синтаксис.
- [ ] `rules_save` в рабочую папку; `format_check` в ответе без ошибок.
- [ ] База КД принимает файл штатной загрузкой:
      `uv run python kdbase/kd_check.py check <файл>` → `ИТОГ OK`, число ПКО/ПВД как ожидалось.
- [ ] Типовая БСП принимает пару правил (без записи в базу):
      `uv run python kdbase/bsp_check.py <правила> <правила корреспондента> --plan <план обмена> --project <проект> --base <песочница>` → `ИТОГ OK`.
- [ ] Правились поиск или ПКО, по которым жалуются на дубли/несвязанные объекты, и есть две песочницы с
      сервером данных — живой обмен одного объекта:
      `uv run python kdbase/exchange_check.py run --plan <план> --source <проект>.<база> --target <проект>.<база> --object <Документ.Имя> --ref <идентификатор> --source-rules <ZIP> --target-rules <ZIP> --query "<запрос>" --expect-rows N`
      → `ИТОГ OK` (узлы — один раз `setup`). Старые правила на другом объекте должны воспроизвести проблему.
- [ ] Правила регистрации пересобирались — `rules_validate` проекта ПРО со структурой источника.
- [ ] Отчёт: выбранные объекты и почему, решения по `unresolved`/`not_applied`/выключенным ПКС, замечания
      до и после, путь файла.

Проекты правил живут в памяти сервера до перезапуска контейнера — результат сохраняйте `rules_save`.
