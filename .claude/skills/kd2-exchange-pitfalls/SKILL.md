# Грабли обменов КД 2 через БСП

Справочник проверенных случаев, не привязанных к конкретной конфигурации. Каждый подтверждён кодом
исполнителя правил БСП — обработки `КонвертацияОбъектовИнформационныхБаз`, модуль объекта
(`DataProcessors/КонвертацияОбъектовИнформационныхБаз/Ext/ObjectModule.bsl` в выгрузке любой конфигурации
на БСП), а для настроек обмена — общих модулей `ОбменДаннымиСервер` и `ОбщегоНазначения` той же БСП (так и
указано у ссылки). Ссылка — имя процедуры и строки в БСП **3.1.12**; в другой версии и в конфигурации с
доработками строки сдвигаются, процедуры — те же (обработка сверена с 3.1.2). `РПО, стр. N` — модуль менеджера
регистра `ПравилаДляОбменаДанными` той же БСП. `УОД:N` — модуль объекта универсальной обработки
`УниверсальныйОбменДаннымиXML` («Универсальный обмен данными в формате XML») из той же выгрузки, версия обработки
1.0.5.234; в другой версии обработки строки сдвинуты.

## Как разбирать жалобу

Ответ человеку: диагноз — со ссылкой на процедуру и строки БСП (из этого скилла или из выгрузки конфигурации
приёмника), а не только на строку файла правил; строки, которые прочитаны, но в ответ не попали, доказательством
для человека не служат.

0. **Есть текст ошибки обмена** — где лежит протокол, что значит код и как от строки дойти до правила —
   `references/protocol.md`.
1. **Направление и база.** Обработчики загрузки в базе Б при обмене из А — из правил направления А → Б, но
   исполняет их **копия в Б** — файл правил корреспондента (`CorrespondentExchangeRules.xml`) комплекта Б.
   Ошибка загрузки в Б правится в `ExchangeRules.xml` комплекта А **и** в правилах корреспондента Б, загружаются
   оба комплекта. Доказательства и исключение (внешнее соединение) —
   `kd2-rules-build/references/handlers.md`, «Где лежат правила загрузки».
2. **Живые правила из обеих баз** (ZIP «Сохранить правила конвертации в файл»): `rules_open` →
   `rules_validate` с обеими структурами — часть граблей ловится проверкой (код в скобках у заголовка).
3. **ПКО проблемного объекта** — `rules_get`: флаги (`СинхронизироватьПоИдентификатору`,
   `ПродолжитьПоискПоПолямПоискаЕслиПоИдентификаторуНеНашли`, `НеЗамещать`), ПКС с `search: true`,
   обработчик `ПоследовательностьПолейПоиска`. Как объект вообще уходит: ПВД и их обработчики, ПКС других
   ПКО с его `КодПравилаКонвертации`.
4. **Сравнить с типовым макетом** плана обмена (`rules_open` макета) — что доработано. Макет лежит в выгрузке
   конфигурации (`dump` в `project_list`): `<dump>\ExchangePlans\<план>\Templates\ПравилаОбмена\Ext\Template.txt`,
   правила корреспондента — `…\Templates\ПравилаОбменаКорреспондента\Ext\Template.txt`. Макет действует, только
   если правила в базе взяты из него: правила, загруженные из файла, обновление из макетов не перекрывает, а без
   обоих макетов конвертации записи из макетов нет вовсе — живые правила брать из базы, не из макета
   (`kd2-rules-build/references/live-rules.md`, «Какие правила действуют в базе»).
5. **Данные** — в песочнице через сервер данных базы (`data_mcp` в `project_list`), только чтение и только с
   согласия человека в этой задаче: спросить одной строкой, какой запрос и зачем; нет согласия — «не проверено».
   Правилам и коду верить больше, чем словам «1С не даст записать»: проверять по модулю объекта.
   Серверы кода, БСП и данных — по правилу `kd2-rules-build/references/mcp-1c.md` (прочитать перед первым
   вызовом).
6. **Правка** — по скиллу `kd2-rules-build` (`kd2-rules-build/references/live-rules.md`): `rules_open` живого
   `ExchangeRules.xml` источника → `rule_update` в этом проекте правил → `rules_validate` → `rules_save` в
   `ExchangeRules.xml` источника и в правила корреспондента приёмника (шаг 1); коммит — спросить одной строкой.
   Правила конвертации (`ExchangeRules.xml`, `CorrespondentExchangeRules.xml`) правятся только сервером, руками
   (инструментом редактирования, `sed`) — нет: шум концов строк и канонической формы, см. `live-rules.md` там же,
   шаг 5. Правила регистрации (`RegistrationRules.xml`) — сервером (`registration_build`), а то, чего он не пишет
   (обработчики), — правкой файла по `kd2-rules-build/references/pro.md`, «Ручная правка
   файла»: загрузка БСП не сверяет ни `Ид`, ни версию, но читает файл потоково — важны порядок элементов,
   `Валидное="true"` у каждого правила, булевы `true`/`false`, тексты обработчиков экранированным текстом без
   CDATA и комментариев. Правка — побайтово (не `sed -i`), после неё `rules_validate` и `bsp_check`.

## Поиск существующего объекта при загрузке

Загрузка ищет объект сразу, как прочитала узел `<Ссылка>` (`ПрочитатьОбъект`, стр. 10735–10757), по шагам
`kd2-rules-build/references/search.md` (`НайтиОбъектПоСсылке`, стр. 8702–8711, 8761–8830, 9018–9024): регистр
соответствий и уникальный идентификатор — только если в `<Ссылка>` есть `{УникальныйИдентификатор}` (флаг ПКО
`СинхронизироватьПоИдентификатору`), между ними — имя предопределённого; затем обработчик
`ПоследовательностьПолейПоиска` или поля поиска — сразу, если идентификатора нет, а с ним — только когда по нему не
нашли и у ПКО стоит `ПродолжитьПоискПоПолямПоискаЕслиПоИдентификаторуНеНашли` (без флага поиск кончается на
идентификаторе, стр. 8856–8858). В узел `<Ссылка>` выгрузка пишет **только свойства поиска** ПКО
(`ВыгрузитьПоПравилу`, стр. 790–826).

### Параметр объекта в обработчике поиска не виден (`search.param_not_in_search`)

- **Симптом:** объект задваивается, хотя обработчик `ПоследовательностьПолейПоиска` «должен» выбрать поиск
  по параметру (например, по виду лица — ИНН + КПП для юрлиц); срабатывает ветка `ПараметрыОбъекта = Неопределено`.
- **Причина:** обработчик читает `ПараметрыОбъекта["X"]`, а ПКС, передающее `X` (`ИмяПараметраДляПередачи`),
  без флага «Поиск». Такой параметр идёт в свойствах объекта и читается после поиска (`ПрочитатьОбъект`,
  стр. 10705).
- **Исправление:** флаг «Поиск» у ПКС параметра. Параметр уйдёт в `<Ссылка>` узлом `<ЗначениеПараметра>`
  (`СоздатьСложнуюИнформациюДляЗаписиВXML`, стр. 12691) и попадёт в `ПараметрыОбъекта` до поиска
  (`ПрочитатьСвойстваПоискаИзФайла`, стр. 8228–8291). ПКС с «Поиск» и пустым приёмником допустимо
  (`ЗагрузитьПКС`, стр. 5494); как условие запроса параметр не используется (`ЗагрузитьПравилоКонвертации`,
  стр. 6079–6082) — он только выбирает строку полей.
- Параметр нельзя сделать «полем поиска» в строке `СтрокаИменСвойствПоиска`: условие строится только по
  свойствам поиска (`НайтиЭлементПоСвойствамПоиска`, стр. 8566–8577), параметра среди них нет — он молча
  пропускается.
- Воспроизведено живым обменом в песочницах: без флага — второй объект с теми же ИНН/КПП, с флагом —
  документ ссылается на существующий (заведённый в приёмнике вручную, с другим наименованием).

### Наименование в полях поиска

- **Симптом:** дубль при совпадающих ИНН и КПП.
- **Причина:** поиск «ИНН, КПП, Наименование» — условие запроса по **каждому** имени строки полей
  (`НайтиЭлементПоСвойствамПоиска`, стр. 8559–8576), строка ограниченной длины сравнивается на точное равенство
  `Наименование = &Наименование` (`НайтиЭлементЗапросом`, стр. 8440–8446); одно расхождение в наименовании — не
  найден, создаётся новый. Расходится оно часто: в двух базах наименование пишут по-разному (ручной ввод в одной,
  заполнение по ИНН из ФНС в другой — порядок слов, кавычки, сокращения формы собственности) — (вывод).
- **Исправление:** для юрлиц с ИНН — без наименования (ИНН + КПП), наименование — только когда ИНН пуст.

### Варианты поиска должны различаться

- Обработчик вызывается с `НомерВариантаПоиска` = 1, 2, … до 10, перебор идёт, только пока он возвращает
  **новую** строку полей: та же строка, что в прошлом варианте, `ПрекратитьПоиск` или найденный объект —
  конец (`НайтиОбъектПоСсылке`, стр. 8940, 8974–8976). Обработчик, который не смотрит на
  `НомерВариантаПоиска`, даёт одну попытку.
- Пустая строка полей **в первом вызове** (ни одна ветка не сработала; начальное значение — пустая строка,
  стр. 8913) — поиск по **всем** свойствам поиска ПКО (`НайтиЭлементПоСвойствамПоиска`, стр. 8559–8561). Между
  вызовами строка не сбрасывается (стр. 9014): со второго вызова несработавшая ветка оставляет прошлую строку —
  перебор кончается без поиска, и после цикла — «не найден», шаг 7 `search.md` (стр. 9050–9063). Поиск по всем свойствам
  на позднем варианте — только явным присвоением пустой строки.
- Типовой образец для контрагентов: при заполненном ИНН 1 — ИНН, КПП, Наименование; 2 — ИНН, КПП; 3 — ИНН,
  Наименование; без ИНН — Наименование (у всех — ещё `ЭтоГруппа`). Так — обработчик
  `ПоследовательностьПолейПоиска` ПКО `Контрагенты` в типовом макете `ПравилаОбмена` плана
  `ОбменБухгалтерияПредприятияДокументооборот20` (Бухгалтерия предприятия 3.0.205, `Ext/Template.txt`,
  стр. 1308–1321); в другом плане и версии — сверить с его макетом (`rules_open` → `rules_get`).

### Пустой ИНН в поиске по ИНН

- **Симптом:** объект источника связался в приёмнике с чужим объектом (без ИНН); документы «висят» не на том
  контрагенте. Хуже дубля — не видно сразу.
- **Причина:** пустое значение приходит `<Пусто/>` и читается пустой строкой (`ПрочитатьСвойство`,
  стр. 8060–8063), попадает в поля поиска (стр. 8290); запрос — `ВЫБРАТЬ Ссылка ИЗ … ГДЕ ИНН = &ИНН И КПП = &КПП`
  без пропуска пустых и без упорядочивания, берётся первая строка (`НайтиЭлементЗапросом`, стр. 8425–8463).
- **Исправление:** перед поиском без наименования проверять `ЗначениеЗаполнено(СвойстваПоиска["ИНН"])`
  (так делает типовой обработчик). То, что таких объектов сейчас нет, не защищает: типовой модуль объекта
  контрагента запись без ИНН не запрещает (иностранные, физлица). Исправление проверено живым обменом:
  юрлицо без ИНН создаётся отдельно и не цепляется к чужому объекту без ИНН; само ошибочное связывание
  (без проверки) живым обменом не воспроизводилось.

### Ключ поиска свёлся к `ЭтоГруппа`

- **Симптом:** разные элементы источника в приёмнике «находят» один и тот же существующий элемент (группы —
  одну группу) и по очереди перезаписывают его; новые объекты не создаются.
- **Причина:** из свойств поиска (без GUID и имени предопределённого) в условии осталось одно `ЭтоГруппа`: у ПКО
  нет других ПКС с «Поиск»/«Обязательное», или обработчик задаёт строку «ИНН, КПП, ЭтоГруппа», а `ИНН` и `КПП` не
  свойства поиска — они молча выпадают (`НайтиЭлементПоСвойствамПоиска`, стр. 8565–8574). Условие —
  `ЭтоГруппа = &ЭтоГруппа` (у элемента Ложь, `ПрочитатьСвойстваПоискаИзФайла`, стр. 8282–8286), берётся первая
  строка без упорядочивания (`НайтиЭлементЗапросом`, стр. 8424–8450, 8465–8468), `ОбъектНайден = Истина`
  (стр. 9067–9070), свойства `<Объект>` пишутся в найденный (`ПрочитатьОбъект`, стр. 10711). Без `ЭтоГруппа` в
  строке те же имена дали бы пустое условие и «не найден» (стр. 8452–8454). При идентификаторе без
  `ПродолжитьПоиск` до полей не доходит (стр. 8856–8858). (вывод по цепочке кода, живым обменом не проверялось)
- **Проверка:** `rules_get` ПКО — ПКС с `search: true`; каждое имя из строк обработчика должно быть среди них.
- **Исправление:** флаг «Поиск» у ПКС ключевых реквизитов; `ЭтоГруппа` — только вместе с настоящим ключом.

### У ПКО нет ключей поиска

- **Симптом:** при каждом обмене в приёмнике новый экземпляр одного и того же объекта.
- **Причина:** у ПКО нет ни свойств поиска, ни `СинхронизироватьПоИдентификатору` — узел `<Ссылка>` не
  пишется (`ВыгрузитьПоПравилу`, стр. 788–791), искать приёмнику нечем (`ПрочитатьОбъект`, стр. 10617–10671).
- **Исправление:** ключи поиска или флаг синхронизации (`kd2-rules-build/references/search.md`, «Рецепт»).

## Загрузка: ошибки и транзакции

### После ошибки обмена часть объектов уже в приёмнике

- **Симптом:** сообщение не загрузилось (ошибка в обработчике), а в приёмнике появились объекты из него —
  например, контрагент есть, документа на него нет; повторный обмен после исправления работает с ними.
- **Причина:** транзакцией загрузки управляет константа приёмника `КоличествоЭлементовВТранзакцииЗагрузкиДанных`
  (`ОбменДаннымиСервер.КоличествоЭлементовВТранзакцииЗагрузкиДанных`, стр. 686–690): обработка получает
  `ИспользоватьТранзакции = (значение <> 1)` (`ОбменДаннымиСервер`, стр. 5653–5654). При 1 транзакции нет,
  каждый объект пишется сам и не откатывается; при 0 — всё сообщение одной транзакцией, откатывается целиком
  (`ВыполнитьЗагрузкуДанных`, стр. 2496–2522); при N — фиксация каждые N объектов (стр. 16583–16588).
  `ПродолжитьПриОшибке` выключает транзакции (стр. 2470–2472).
- **Проверка:** значение константы в приёмнике; после неудачного обмена — объекты по реквизитам сообщения.
- **Исправление:** это настройка, не ошибка правил; при разборе жалобы «задвоилось после сбоя» учитывать, что
  первая неудачная попытка уже могла создать объекты.

### Обработчик падает в новом приёмнике: `Если Реквизиты.Флаг Тогда`

- **Симптом:** в новой или пустой базе приёмника обмен падает на первом объекте ПКО с «Преобразование значения
  к типу Булево не может быть выполнено» в `ПослеЗагрузки` (или в типовом `ПередЗаписью` объекта); на рабочей
  базе те же правила работают.
- **Причина:** `ОбщегоНазначения.ЗначенияРеквизитовОбъекта` по пустой ссылке (или несуществующему объекту)
  возвращает структуру с `Неопределено` в каждом поле (стр. 275–282, 306–307), и `Если … Тогда` на ней падает.
  Типично: реквизиты шаблона или вида документа, которые в рабочей базе всегда заполнены настройкой.
- **Проверка:** обработчик ПКО (`rules_get`) — обращения к результату `ЗначенияРеквизитовОбъекта` без
  проверки заполненности ссылки; в приёмнике — есть ли шаблоны/виды, на которые рассчитан код.
- **Исправление:** в правилах — `Если ЗначениеЗаполнено(Ссылка) И Реквизиты.Флаг = Истина Тогда`; для
  проверки в песочнице — завести недостающие настройки, а не править правила.

### Документ в приёмнике не проведён после обмена

- **Симптом:** документ пришёл и записан, но не проведён; протокол обмена без ошибок.
- **Причина:** при загрузке документ пишется непроведённым и встаёт в очередь, которую проводят после фиксации
  транзакции загрузки (`ВыполнитьЗагрузкуДанных`, стр. 2496–2536). Дальше одно из:
  - проведение из очереди не прошло (исключение или `ПроверитьЗаполнение()` = Ложь): откат транзакции документа,
    предупреждение «Не удалось провести документ…» в журнале регистрации, проблема «Непроведенный документ» в
    результатах обмена; документ остаётся непроведённым, прежние движения уже удалены (`ОбменДаннымиСервер`,
    стр. 6347–6388, 8614–8656); обмен не прерывается, в протокол обмена не пишется (вывод);
  - загрузка сообщения упала — очередь не проводится вовсе (стр. 2528–2535);
  - у ПКО нет ПКС `Проведен` (отключено, ушло в параметр): новый документ записывается непроведённым, найденный
    сохраняет `Проведен` приёмника — непроведённый таким и остаётся (вывод; `ПрочитатьОбъект`, стр. 11065–11083);
  - режим задан явно: атрибут `РежимЗаписи` от отправителя или `Объект.Проведен`/`РежимЗаписи` в `ПослеЗагрузки`.
- **Проверка:** журнал регистрации приёмника — «Не удалось провести документ» с текстом ошибки; ПКО документа —
  ПКС `Проведен` включено, `ПослеЗагрузки` и `ПередВыгрузкой` не трогают `Проведен`/`РежимЗаписи`.
- **Исправление:** ошибка проведения — данные и настройки приёмника (или дозаполнение в `ПослеЗагрузки`), не
  флаги правил. Механизм — `kd2-rules-build/references/handlers.md`, «Проведение документов в приёмнике».

### Обработчик сам проводит документ — проведён дважды или загрузка упала

- **Симптом:** в `ПослеЗагрузки` ПКО (или в `ПослеЗагрузкиДанных`) `Объект.Записать(РежимЗаписиДокумента.Проведение)`;
  побочные действия проведения выполняются дважды, или ошибка 21 и откат всего сообщения.
- **Причина:** в `ПослеЗагрузки` у объекта ещё нет `ОбменДанными.Загрузка` и регистрация не отключена (их ставят
  после обработчика: `ЗаписатьОбъектВИБ`, стр. 1761; `ОтменитьПроведениеОбъектаВИБ`, стр. 1814; стр. 11112, 11140)
  — документ проводится с полной логикой в транзакции загрузки; затем исполнитель видит `Проведен = Истина`,
  распроводит его (удаляет движения) и ставит в очередь (стр. 11068–11070, 11135–11156) — второе проведение.
  Исключение — ошибка 21 и прерывание загрузки (стр. 11013–11017, 2520–2529). `ПослеЗагрузкиДанных` тоже идёт в
  транзакции и до очереди (стр. 2510, 2535). (вывод по порядку кода)
- **Исправление:** не проводить самому — управлять `Объект.Проведен` или строкой в `РежимЗаписи`
  (`kd2-rules-build/references/handlers.md`, «Проведение документов в приёмнике»).

## Как проверить исправление живым обменом

`rules_validate`, `kd_check` и `bsp_check` подтверждают, что правила читаются, но не то, что поиск в приёмнике
найдёт нужный объект. Это проверяет `exchange_check` (скрипт из клона сервера) — штатный обмен одного объекта
между двумя песочницами; старые правила воспроизводят дубль, исправленные — нет, на разных объектах. Команды,
шаги обмена и что подготовить в данных — `kd2-rules-build/references/checks.md`, раздел `exchange_check`.
Исправление до проверки вносится шагом 6 «Как разбирать жалобу»: правила конвертации — сервером, не правкой XML
руками; правила регистрации — как сказано там же.

## Выгрузка объектов

### Объект не выгружается сам — «ждём, пока выгрузится»

- **Причина:** включённого ПВД на тип объекта нет (выборка изменений берёт только типы включённых ПВД,
  `ВыполнитьВыгрузку`, стр. 17931–17942; `ВыполнитьВыгрузкуЗарегистрированныхДанных`, стр. 18236), объект не
  зарегистрирован на узле, или `ПередВыгрузкойОбъекта` ПВД / глобальный ставит `Отказ = Истина`
  (`ВыгрузкаОбъектаВыборки`, стр. 13626–13628). Объект уходит только значением свойства других объектов
  (например, контрагент — только как реквизит договора). Часто это рабочая схема, а не ошибка — уточнить у
  владельца правил. `Отказ` в `ПередОбработкойПравила` ПВД в обмене через план не проверяется (стр. 18369–18404),
  `Отключить` у группы ПВД не читается (`ЗагрузитьПравилаВыгрузки`, стр. 6868–6888).
- **Проверка:** `rules_get kind=pvd` — обработчики ПВД; регистрация на узле; кто ссылается на ПКО объекта — ПКС
  других ПКО с его `КодПравилаКонвертации`, их `ПередВыгрузкой` (`ВыгрузитьОбъект = Истина` — объект уходит
  целиком). Подробно — `kd2-rules-build/references/pvd.md`.

### Объект по ссылке: целиком или только ссылкой

- Значение ссылочного свойства выгружается объектом целиком, только если у правила регистрации объекта есть
  реквизит-флаг узла (`РежимыВыгрузкиОбъектовОбмена`) со значением «при необходимости» или пустым
  (`ВыгружатьОбъектПоСсылке`, стр. 3393–3437) и объекта ещё нет в регистре соответствий для узла (он добавляется
  туда как «выгружен по ссылке»); иначе — только узлом `<Ссылка>` со свойствами поиска (`ВыгрузитьСвойства`,
  стр. 13170–13196). Ещё путь — `ВыгрузитьОбъект = Истина` в `ПередВыгрузкой` ПКС.
- **Следствие для правил:** у ПКО, которое уходит только ссылкой, исполняются лишь ПКС с флагом «Поиск»;
  остальные ПКС и их замечания (`structure.pko_missing`, `structure.pks_type`) на обмен не влияют, а правка такой
  ПКС ничего не меняет в приёмнике. Сервер предупреждает об этом заранее — `structure.pko_ref_only` в
  `rules_validate`: ПКО ссылочного типа без ПВД, на которое ссылаются только ПКС без `ВыгрузитьОбъект = Истина`.
  Текст замечания называет оба выхода; для классификаторов, которые приёмник находит по полям поиска, это
  штатная схема.

### Реквизит молча не приходит

- **Симптом:** ссылочный реквизит в приёмнике пуст, в протоколе обмена ошибок нет.
- **Причина:** у ПКС нет `КодПравилаКонвертации`, а ПКО для типа значения в правилах нет — значение молча не
  выгружается (`ВыгрузитьСвойства`, стр. 13154–13162). ПКС без источника берёт реквизит источника с именем
  приёмника, ошибка чтения проглатывается (`ПолучитьЗначениеСвойства`, стр. 12128–12156).
- **Исправление:** код ПКО у ПКС или ПКО для типа (`kd2-rules-build/references/pks.md`).

## Перечисления: результат обмена «Ошибка»

- **Симптом:** обмен завершается с ошибкой, в протоколе «Не найдено соответствие для значения Источника»
  (код 71); реквизит-перечисление не пришёл.
- **Причина:** для значения перечисления источника нет ПКЗ — свойство не выгружается, код 71 взводит флаг
  ошибки (`ВыгрузитьПоПравилу`, стр. 748–772; `ЗаписатьВПротоколВыполнения`, стр. 4833–4839). Типично после
  добавления значения в перечисление источника. ПКЗ применяет только отправитель: приёмник получает готовое имя.
- **Исправление:** ПКЗ на каждое значение источника, без аналога — в пустое
  (`kd2-rules-build/references/pkz.md`).

## Удаление объектов

Механизм и строки — `kd2-rules-build/references/handlers.md`, «Получение удаления».

### В приёмнике объект удалился, а не пометился

- **Симптом:** объект удалён в источнике (или перестал проходить отбор регистрации — раздел «Регистрация»), в
  приёмнике он удалён непосредственно, а ждали пометку удаления.
- **Причина:** приёмник находит объект только по GUID из `<УдалениеОбъекта>` (с подменой по регистру
  соответствий; ПКО приёмника и поля поиска не участвуют) и удаляет `Объект.Удалить()` (`ПрочитатьУдалениеОбъекта`,
  стр. 16658–16671; `УдалитьОбъектПоСсылке`, стр. 16603–16654; `УдалитьОбъект`, стр. 7124–7152). Пропускаются
  только предопределённые, объекты под датой запрета загрузки и `Отказ` в `ПриПолученииИнформацииОбУдалении`.
  Флаг конвертации `УдалятьСопоставленныеОбъектыВПриемникеПриИхУдаленииВИсточнике` не используется (стр. 14639,
  16449–16450).
- **Проверка:** `rules_get kind=conversion` правил корреспондента приёмника — есть ли
  `ПриПолученииИнформацииОбУдалении`.
- **Исправление:** в этом событии — пометка и `Отказ = Истина` (вывод; образец — `handlers.md`, «Получение
  удаления»), в правилах корреспондента приёмника и в `ExchangeRules.xml` источника.

### Обработчик получения удаления не сработал после замены правил только в источнике

- **Симптом:** в `ExchangeRules.xml` источника добавили `ПриПолученииИнформацииОбУдалении`, загрузили в источник —
  объект в приёмнике всё равно удаляется.
- **Причина:** загрузочные события приёмник берёт из своей копии правил отправителя
  (`ПравилаЗачитанныеКорреспондента`), правила из сообщения пропускает (`НачатьЧтениеСообщения`, стр. 7485–7492;
  `ОбменДаннымиСервер`, стр. 10052, 10072–10075). Из правил источника сразу меняется только тип в атрибуте
  `ТипПриемника` (из ПКО отправителя, `ОтработатьУдалениеОбъекта`, стр. 13770–13835). (вывод для этого сценария)
- **Исправление:** то же событие в `CorrespondentExchangeRules.xml` комплекта приёмника и загрузка комплекта в
  приёмник (шаг 1 «Как разбирать жалобу»). Исключение — обмен через внешнее соединение (вывод, `handlers.md`).

## Загрузка правил в базу

### Комплект не загружается: «правила предназначены для другой программы»

- **Симптом:** форма загрузки правил синхронизации отклоняет ZIP — «Правила не могут быть загружены, так как они
  предназначены для программы …», только «Закрыть»; или предупреждение «Синхронизация данных может работать
  некорректно…» с «Продолжить» / «Отмена».
- **Причина:** загрузка комплекта из трёх файлов сверяет заголовок `ExchangeRules.xml`, элемент `<Источник>`:
  текст (имя конфигурации) без учёта регистра с `Метаданные.Имя` без «БАЗОВАЯ» — не совпало, отказ; атрибут
  `ВерсияКонфигурации` по первым трём числам — не совпало, предупреждение (РПО, стр. 43–95, 729–735, 961–967).
  Типично: в комплект положен чужой `ExchangeRules.xml` (правила корреспондента) или правила другой конфигурации.
- **Проверка:** `<Источник>` в `ExchangeRules.xml` комплекта — имя конфигурации базы, куда грузят
  (`rules_overview` — стороны правил).
- **Исправление:** `ExchangeRules.xml` — правила этой базы. Проверку выключает настройка плана обмена
  `ПредупреждатьОНесоответствииВерсийПравилОбмена = Ложь` (РПО, стр. 39–41) — это конфигурация, не правила.
  Что ещё сверяется и что нет — `kd2-rules-build/references/live-rules.md`, «Проверка заголовка при загрузке».

## Регистрация

Симптом → где причина; механизм и строки БСП — `kd2-rules-build/references/pro.md`, «Правило» и «Как БСП
применяет ПРО».

- **Правило регистрации не работает** — нет `Валидное="true"`, отключена группа (её `Отключить` не читается)
  или у объекта в составе плана авторегистрация не «Запретить»; у объекта без правил — все узлы плана.
- **Получателю пришло удаление живого объекта** — перепроверка при выгрузке: в режиме «по условию» или «при
  необходимости» объект перестал проходить отбор (отбор по `Проведен`, статусу).
- **Узел ничего не получает** — отбор по табличной части узла, а она пуста; «пусто — значит все» — группа ИЛИ по
  флагу узла (вывод, живым обменом не проверялось).

## Ручной обмен универсальной обработкой — другой исполнитель

- **Симптом:** правила проверили ручной выгрузкой и загрузкой обработкой «Универсальный обмен данными в формате
  XML» — работает, а обмен через план обмена ведёт себя иначе (или наоборот).
- **Причина:** формат один, исполнители разные: обмен через план — `КонвертацияОбъектовИнформационныхБаз` (БСП),
  ручной — `УниверсальныйОбменДаннымиXML` (`УОД`); копия обработки из поставки КД — третий. Вывод об одном на
  другой не переносится:

| Что | Обмен через план (стр. N) | Универсальная обработка (`УОД:N`) |
|---|---|---|
| Кэш выгруженных, `НеЗапоминатьВыгруженные` | только при ссылке объекта на себя; ключ по умолчанию — имя ПКО (`ВыгрузитьПоПравилу`, стр. 388–398, 424, 469–471, 603–653) | у каждого ПКО по умолчанию, ключ `ЗначениеВСтрокуВнутр(Источник)`: объект уходит в файл один раз; флаг выключает; у РС, констант и неопределённого типа — выключен всегда (3842, 3898–3900, 1682–1702, 1767–1799) |
| Свой ключ в `ПередВыгрузкой` ПКО | `ЗапоминатьВыгруженные = Истина` без своего `КлючВыгружаемыхДанных` — у всех объектов ПКО один ключ, со второго возвращается узел первого (вывод: стр. 424, 469–471, 557–595, 607–633) | ключ вычислен до обработчика, кэш проверяется после — замена ключа действует (1693–1702, 1740–1764, 1771–1773) |
| ПКС `Обязательное` | свойство поиска, как «Поиск» (`ЗагрузитьПКС`, стр. 5482–5502) | не читается: обычное свойство, в `<Ссылка>` не идёт (3624–3643); `ЭтоГруппа` только с `Обязательное` — группы приходят элементами (вывод: 6465–6475, 8740–8746) |
| Безопасный режим | по профилю безопасности плана (стр. 2482–2486, 8953–8963) | реквизит `БезопасныйРежим` (1616–1621, 8537–8541, 11249–11254); взводит форма обработки (`ПриСозданииНаСервере`, стр. 21–22 модуля формы); созданная программно без формы — без безопасного режима (вывод) |
| ПВД: способ отбора, `ВыборкаДанных`, `Отказ` в `ПередОбработкой` | не исполняются: только выборка изменений по узлу (стр. 18173, 18236) | стандартная выборка и произвольный алгоритм; `ВыборкаДанных` — запрос, результат, выборка или коллекция; `Отказ` отменяет правило (11166–11186, 11297–11299, 11375–11396) |
| Запись документа | непроведённым, затем очередь отложенного проведения (`kd2-rules-build/references/handlers.md`, «Проведение документов в приёмнике») | без `РежимЗаписи` — «Запись» в режиме загрузки, `Проведен` как пришёл; `РежимЗаписи = "Проведение"` — проводится сразу; очереди нет (9047–9053, 9077–9089) |
| Регистр соответствий | найденный по полям объект записывается в регистр, дальше находится по GUID (стр. 1772–1778, 8320–8363) | нет: каждый раз поиск по полям (имени регистра в модуле нет) |
| События конвертации | выполняются все | `ПередПолучениемИзмененныхОбъектов`, `ПослеПолученияИнформацииОбУзлахОбмена`, `ПередОтправкойИнформацииОбУдалении`, `ПриПолученииИнформацииОбУдалении` читаются и не выполняются (12622–12648) |
| `ОбъектМодифицирован` в `ПослеЗагрузки` | ставится в Истина, не читается — объект пишется всегда (стр. 10624, 10953) | решает, писать ли объект (9001–9017) |
| Отладка обработчиков внешней обработкой | запрещена исключением (`ИнициализироватьОбработки`, стр. 14212–14216) | работает (например 1744–1752) |
| Приоритет объектов, `ПриПолученииДанныхОт…` | есть (стр. 11035–11039) | нет (в модуле не встречается) |
| Объект по ссылке | только `<Ссылка>`; целиком — ПРО «при необходимости» или `ВыгрузитьОбъект` (стр. 1009–1019, 13170–13196) | целиком, если у ПКО нет `НеВыгружатьОбъектыСвойствПоСсылкам` (2046–2050) |
| Откуда правила загрузки | копия правил корреспондента в приёмнике (`handlers.md`) | из файла данных; при `БезопаснаяЗагрузка` — из отдельного файла правил (12047–12053) |

- **Проверка:** чем выполнялся «успешный» обмен; живое поведение плана обмена — только `exchange_check`
  («Как проверить исправление живым обменом»).
- **Исправление:** правила под обмен через план проверять обменом через план; если одни правила служат обоим
  исполнителям — не опираться на строки таблицы, где они расходятся.

## Как пополнять

- Только универсальное: без имён баз, организаций, контрагентов и людей; пример — обезличенный.
- Только с доказательством: процедура и строки БСП (версия — в шапке) или воспроизведение в песочнице;
  что не воспроизводилось на живой базе — так и написать.
- Формат: симптом → причина → проверка → исправление.
- Грабли, которые ловятся по тексту правил без баз, — ещё и проверкой в `rules_validate` (код проверки — в
  заголовке раздела; список проверок — `kd2-rules-build/references/checks.md`, новая — задача в репозитории
  сервера https://github.com/egordoronchenko/kd2-rules-mcp).
