# Регистрация
Читать, когда правило регистрации не срабатывает, получателю пришло удаление живого объекта или узел ничего не получает.

Симптом → где причина; механизм и строки БСП — `kd2-rules-build/references/pro.md`, «Правило» и «Как БСП
применяет ПРО».

- **Правило регистрации не работает** — нет `Валидное="true"`, отключена группа (её `Отключить` не читается)
  или у объекта в составе плана авторегистрация не «Запретить»; у объекта без правил — все узлы плана.
- **Получателю пришло удаление живого объекта** — перепроверка при выгрузке: в режиме «по условию» или «при
  необходимости» объект перестал проходить отбор (отбор по `Проведен`, статусу).
- **Узел ничего не получает** — отбор по табличной части узла, а она пуста; «пусто — значит все» — группа ИЛИ по
  флагу узла (вывод, живым обменом не проверялось).

## Проверить в песочнице: `live_registration_check`

Инструмент сервера за один вызов показывает по каждому плану, в состав которого входит объект: где объект
зарегистрирован сейчас, кому его отдают действующие правила базы (`ОбменДаннымиСобытия.ОпределитьПолучателей`) и
что регистрирует обычная запись в транзакции, которая всегда отменяется (по умолчанию; `write: false` — только
чтение). Правка реквизитов шапки в памяти (`changes`) показывает, куда уйдёт объект после правки. Объяснение по
узлу — какие условия ПРО выполнились; ему верить, только если `explanation.status = ok` и `reference = false`.
Условия, значение которых задаёт алгоритм, считаются так же, как у БСП: алгоритм исполняется до отбора
(`ПолучитьЗначенияАлгоритмовКонстант`, строки 2446–2505).

Порядок разбора:
1. Узла нет в `recipients` — смотреть `explanation`: у узла в `failed` — условия, которые он не
   прошёл; итог отбора по объекту `false` — объект не проходит отбор по своим свойствам; режим узла «Выгружать
   вручную» / «Не выгружать».
2. Запись вызывает подписки и модуль объекта, их действия вне базы (файлы, внешние вызовы, фоновые задания) откат
   не вернёт; если такие подписки есть — `write: false`. Узел в `only_written` у не нового объекта — БСП при записи учитывает и
   версию объекта в базе (`ПроверятьСсылку`, `ОбменДаннымиСобытия`, БСП 3.1.12, строки 1400, 2571–2582), а
   `ОпределитьПолучателей` — нет (строка 1534). Узел в `only_rules` — объект не изменён для плана (выборочная
   регистрация «Модифицированность», строки 1368–1387) или запись отклонена.
3. Признаки плана: `no_rules` — правил для объекта нет, БСП отдаёт его на все узлы плана, кроме своего (строки
   1598–1611), это не «правило выполнилось»; `recipients_skipped` — план не подключён к обмену БСП или объект
   регистрирует платформа (авторегистрация, строка 1389).
4. Проверить новые правила: установить их `live_rules_install` (preview → apply), вызвать инструмент, вернуть прежние
   из снимка. Внутри транзакции не установленные правила не проверить: БСП держит правила в параметре сеанса, а его
   откат не возвращает.

Кэш: сеанс сервера данных живёт между вызовами, а БСП кэширует правила и ответ «какие узлы проходят условие» на
сеанс. Инструмент сбрасывает кэш механизма регистрации своего сеанса до расчёта и после отката; код, который сам
правит узлы или правила через сервер данных, должен делать то же (`ОбменДаннымиСлужебный.
ОбновитьКэшМеханизмаРегистрацииОбъектов`, строки 113–132), иначе ответы будут по старым настройкам.
