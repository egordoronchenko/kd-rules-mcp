# Живые правила в `rules_dir` проекта
Читать, когда правила обмена загружаются в базу из файла и лежат в репозитории проекта 1С: папка `rules_dir`
проекта в `project_list` (писать можно, если `writable`). Правка таких правил — коммит проекта.

Ссылки `РПО, стр. N` — модуль менеджера регистра `ПравилаДляОбменаДанными` (БСП 3.1.12); `ОбменДаннымиСервер,
стр. N` — общий модуль той же БСП; `<файл>.py:N` — строки модулей сервера и скриптов проверки в
[открытом репозитории](https://github.com/egordoronchenko/kd2-rules-mcp) (`workspace.py`, `handlers.py`,
`xmlstyle.py`, `pack.py` — пакет сервера; `bsp_check.py`, `exchange_check.py` — скрипты клона сервера).

## Раскладка

- Папка на план обмена, файлы под именами из архива БСП: `ExchangeRules.xml` — правила этой программы,
  `CorrespondentExchangeRules.xml` — правила программы-корреспондента, `RegistrationRules.xml` — правила
  регистрации; другие имена загрузка из архива отклоняет (РПО, стр. 134–155 — комплект из трёх, 482–498 — пара
  правил конвертации). Тогда `rules_pack(folder=…)` соберёт ZIP без перечисления файлов (`pack.py:13`).
- База Б загружает данные из А по **своей копии** правил А — файлу корреспондента комплекта Б
  (`ОбменДаннымиСервер`, стр. 10001–10083; `handlers.md`, «Где лежат правила загрузки»). Правка направления
  А → Б — два файла: `ExchangeRules.xml` в `rules_dir` проекта А и `CorrespondentExchangeRules.xml` в
  `rules_dir` проекта Б; часто это два репозитория и два коммита (вывод).
- Правила регистрации — только своей базы: загрузка сверяет план обмена правил с планом, для которого они
  грузятся (`ЗагрузкаПравилРегистрацииОбъектов`, стр. 983–987; `pro.md`).

## Порядок

1. `project_list` — `rules_dir` (`path`, `writable`) обеих сторон; `git status` в их репозиториях: чужие
   незакоммиченные правки в `rules_dir` со своими не смешивать — спросить человека.
2. `rules_projects` → `rules_open(<rules_dir>\<план>\ExchangeRules.xml)` → `rules_validate` со структурами до
   правок (`SKILL.md`, §1).
3. Правки инструментами. Обёртки `handlers_export` — в рабочую папку сервера (`workspace`), не в `rules_dir`:
   экспорт удаляет из папки свои прежние `.bsl` (`handlers.py:636-645`), а в коммит проекта обёртки не идут.
4. `rules_save(project_id, <тот же путь>, overwrite: true)` — без `overwrite` существующий файл не заменяется
   (`workspace.py:84-90`). Правка загрузки — тот же проект правил ещё раз `rules_save` в
   `CorrespondentExchangeRules.xml` второго проекта: оба файла пишутся из одного дерева и совпадут (вывод).
5. Дифф до коммита: `git diff --stat` — только нужные правила. Файлы, записанные 1С, — UTF-8 с BOM и
   переводами строк вперемешку; сериализатор берёт один перевод строки по началу файла и ставит его и в текст
   обработчиков (`xmlstyle.py:37`, `:80`), поэтому первый дифф после `rules_save` шумит — смотреть
   `git diff --ignore-cr-at-eol`, шум описать в сообщении или вынести отдельным коммитом. Масштаб шума оценить
   до коммита: `git diff --stat` против `git diff --ignore-cr-at-eol --stat` — в файле с переводами строк
   вперемешку разница бывает в сотни строк при правке в десятки (наблюдение на живом файле правил); в сообщении
   коммита — обе цифры и что остальное — концы строк. Точечная правка без
   сериализатора — побайтово, не `sed -i`: он переписывает переводы строк во всём файле (наблюдение на живом
   файле правил).
6. `rules_pack(folder=<rules_dir>\<план>)` — ZIP из файлов байт в байт (`pack.py:13`) в рабочую папку, не в
   `rules_dir`: `warnings` пусты, `load_with` — форма загрузки (`tools.md`, `rules_pack`).
7. Проверки — чек-лист `SKILL.md`, §3. Комплект в песочницу загружает агент сам: `bsp_check` — без записи в
   базу (`bsp_check.py:13-14`), `exchange_check` — загружает и записывает комплекты в обе песочницы
   (`exchange_check.py:124-132`); оба — из клона сервера и только для баз роли «песочница» (`checks.md`).
   **Боевая база — никогда**: ни загрузки правил, ни обмена, ни записи.
8. Коммит делает агент — в репозитории каждого проекта, где менялись файлы:
   - `git add` только файлов `rules_dir` явными путями (не `git add -A`, не `.`);
   - сообщение — `<план обмена>: <суть правки>`, например «<план>: поиск контрагентов по ИНН и КПП без
     наименования»; без `Co-Authored-By` и подписей генератора;
   - ветка — по правилам проекта, иначе текущая; пуш — только если так принято в проекте и человек согласен.
9. Ничего в проекте 1С вне `rules_dir` не менять: `AGENTS.md`, `CLAUDE.md`, `.claude\`, `.cursor\`, исходники
   и макеты `Templates\…` — по процессу самого проекта (захват в хранилище, его проверки).
10. Отчёт: какие файлы и в каких репозиториях, хеши коммитов, что загружено в какую песочницу, итоги ступеней
    лестницы.
