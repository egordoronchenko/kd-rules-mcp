# Живые правила в `rules_dir` проекта
Читать, когда правила обмена загружаются в базу из файла и лежат в репозитории проекта 1С: папка `rules_dir`
проекта в `project_list` (писать можно, если `writable`). Правка таких правил — коммит проекта.

Ссылки `РПО, стр. N` — модуль менеджера регистра `ПравилаДляОбменаДанными` (БСП 3.1.12), «форма загрузки,
стр. N» и «форма списка, стр. N» — модули его форм `ЗагрузитьПравилаСинхронизацииДанных` и `ФормаСписка`;
`ОбменДаннымиСервер, стр. N`, `ОбменДаннымиПовтИсп, стр. N` — общие модули той же БСП; `исполнитель, стр. N` —
модуль объекта обработки `КонвертацияОбъектовИнформационныхБаз`; `<файл>.py:N` — строки модулей сервера и
скриптов проверки в [открытом репозитории](https://github.com/egordoronchenko/kd-rules-mcp) (`workspace.py`,
`handlers.py`, `xmlstyle.py`, `pack.py` — пакет сервера; `bsp_check.py`, `exchange_check.py` — скрипты клона сервера).

## Раскладка

- Папка на план обмена, файлы под именами из архива БСП: `ExchangeRules.xml` — правила этой программы,
  `CorrespondentExchangeRules.xml` — правила программы-корреспондента, `RegistrationRules.xml` — правила
  регистрации; другие имена загрузка из архива отклоняет (РПО, стр. 669–693 — комплект из трёх в форме загрузки,
  `ЗагрузитьКомплектПравил`, то же в `ЗагрузитьПоставляемыеПравила`, стр. 134–155; 482–498 — пара правил
  конвертации). Тогда `rules_pack(folder=…)` соберёт ZIP без перечисления файлов (`pack.py:13`).
- База Б загружает данные из А по **своей копии** правил А — файлу корреспондента комплекта Б
  (`ОбменДаннымиСервер`, стр. 10001–10083; `handlers.md`, «Где лежат правила загрузки»). Правка направления
  А → Б — два файла: `ExchangeRules.xml` в `rules_dir` проекта А и `CorrespondentExchangeRules.xml` в
  `rules_dir` проекта Б; часто это два репозитория и два коммита (вывод).
- Правила регистрации — только своей базы: загрузка сверяет план обмена правил с планом, для которого они
  грузятся (`ЗагрузкаПравилРегистрацииОбъектов`, стр. 983–987; `pro.md`).

## Какие правила действуют в базе

- Действующие правила плана — запись регистра `ПравилаДляОбменаДанными` (независимый, непериодический; измерения
  `ИмяПланаОбмена`, `ВидПравил` — конвертация / регистрация). Откуда — ресурс `ИсточникПравил`:
  `МакетКонфигурации`, `Файл`, `МенеджерТиповой`, `МенеджерПользовательский` (метаданные регистра).
- В записи конвертации — исходный XML своих правил и правил корреспондента (сжатые) и скомпилированные
  `ПравилаЗачитанные` (режим «Выгрузка») и `ПравилаЗачитанныеКорреспондента` («Загрузка»); у регистрации —
  `ПравилаXML` и `ПравилаЗачитанные` (РПО, стр. 553–558, 572–575, 613–626, 794–809). Обмен XML не разбирает:
  выгрузка берёт `ПравилаЗачитанные`, загрузка — `ПравилаЗачитанныеКорреспондента` (`ОбменДаннымиСервер`,
  стр. 10024, 10038–10041, 10052, 10072–10075); XML нужен для «Сохранить правила в файл» и признака «типовые»
  (РПО, стр. 339–386).
- Нет записи или не `ПравилаЗагружены` — выгрузка отменяется («Не заданы правила конвертации для плана обмена…»),
  загрузка тоже, если у плана `НаличиеПравилКонвертацииОбязательно` (по умолчанию Истина) (РПО, стр. 829–858;
  `ОбменДаннымиСервер`, стр. 895, 10026–10035, 10054–10067).
- Из макетов плана правила конвертации грузятся, только если есть **оба** макета `ПравилаОбмена` и
  `ПравилаОбменаКорреспондента` (имена буквально): с одним записи из макетов нет и обмен падает, пока правила не
  загружены из файла (`ОбменДаннымиСервер`, стр. 11963–11974; `ОбменДаннымиПовтИсп`, стр. 392–394; «падает» —
  вывод по цепочке с пунктом выше). Регистрация — макет `ПравилаРегистрации` или общий модуль-менеджер
  (`ОбменДаннымиСервер`, стр. 11991–12015).
- Макеты перечитывает `ВыполнитьОбновлениеПравилДляОбменаДанными`: при обновлении параметров работы программы
  (после обновления конфигурации — вывод), при создании узла помощником, командой «Обновить все типовые правила»
  (форма списка, стр. 61–63), в подчинённом узле РИБ. Она ничего не делает при выключенной константе
  `ИспользоватьСинхронизациюДанных` (вне разделения) и пропускает план без узлов, кроме этого
  (`ОбменДаннымиСервер`, стр. 2244–2258, 11956–11959). Правка макета до этих событий не действует (вывод).
- **Правила из файла макет не перекрывает:** при `ИсточникПравил = Файл` обновление из макетов пропускает и
  конвертацию, и регистрацию (каждый вид отдельно) и пишет в журнал ошибку о возможной несовместимости
  (`ОбменДаннымиСервер`, стр. 11769–11817, 11966, 11991–11994). Правка макета в такой базе не действует (вывод).
- Вернуться к типовым: «Типовые из конфигурации» в форме загрузки (все три макета; форма загрузки,
  стр. 343–353), команда «Использовать типовые правила» формы списка (по виду правил; форма списка, стр. 69–91),
  программно `ОбменДаннымиСервер.УдалитьПоставляемыеПравила` (стр. 1371–1374); запись перезаписывается
  правилами макета (РПО, стр. 314–329, 638–642).
- Скомпилированные правила помечены версией формата хранения `2` (исполнитель, стр. 15855–15857); не совпала
  после обновления БСП — исключение «Версия формата хранения правил обмена не соответствует ожидаемой…»
  (`ВосстановитьПравилаИзВнутреннегоФормата`, исполнитель, стр. 7032–7038). Из макетов правила перечитает
  обновление, из файла — загрузить заново (вывод).
- После загрузки правил форма сбрасывает кэш механизма регистрации (форма загрузки, стр. 377–379); регистрация
  в сеансах берёт правила из параметра сеанса (`ОбменДаннымиПовтИсп`, стр. 789–795).

## Проверка заголовка при загрузке

Имя и версию конфигурации сверяет только загрузка **комплекта из трёх файлов** формой загрузки правил
синхронизации (`ЗагрузитьКомплектПравил`, РПО, стр. 729–735) и только по `ExchangeRules.xml`, элемент
`<Источник>`: текст — имя конфигурации, атрибут `ВерсияКонфигурации` — версия (`ИнформацияОПравилахИзФайла`,
РПО, стр. 961–967).

| Что | Как сравнивается | Не совпало |
|---|---|---|
| имя | без учёта регистра с `Метаданные.Имя`, из которого вырезано «БАЗОВАЯ» (РПО, стр. 43–60) | **отказ** «Правила не могут быть загружены, так как они предназначены для программы …», только «Закрыть» (форма загрузки, стр. 291–292) |
| версия | первые три числа (РПО, стр. 64–95) | предупреждение «Синхронизация данных может работать некорректно…»: «Продолжить» — загрузка без проверки, «Отмена» — без загрузки (форма загрузки, стр. 293–296, 688–694) |

- Обе проверки выключает настройка плана `ПредупреждатьОНесоответствииВерсийПравилОбмена = Ложь` (по умолчанию
  Истина; РПО, стр. 39–41; `ОбменДаннымиСервер`, стр. 892).
- Не сверяются: `CorrespondentExchangeRules.xml`, `<Приемник>`, `ВерсияФормата`, `Ид` (исполнитель читает их без
  сравнения, стр. 16305–16353). Заголовок не сверяют вовсе отдельные формы правил конвертации (ZIP из двух
  файлов) и регистрации и программная загрузка поставляемого комплекта (РПО, стр. 113–226, 419–630); у правил
  регистрации сверяется только `ПланОбмена/@Имя` (`pro.md`).
- Состав: форма загрузки правил синхронизации — ровно три файла с именами выше (сравнение точное), иначе отказ
  (РПО, стр. 669–693); форма правил конвертации — два файла в любом порядке, один — отказ «старый формат»
  (стр. 480–508); регистрация — XML или ZIP с одним файлом (стр. 518–525). Все три файла разбираются до записи:
  ошибка разбора любого — отказ без записи, сообщения — в журнал регистрации (РПО, стр. 737–811; форма загрузки,
  стр. 370–373).
- При каждой загрузке данных приёмник сравнивает версию источника из своей копии правил корреспондента с
  атрибутом `ВерсияКонфигурацииИсточника` сообщения: расхождение — предупреждение в журнал; исключение — только в
  сеансе с проверкой расхождения версий (интерактивный обмен, помощник сопоставления) при включённой настройке
  выше (`НачатьЧтениеСообщения`, исполнитель, стр. 7463–7471; `ОбменДаннымиСервер`, стр. 12371–12414).

## Порядок

1. `project_list` — `rules_dir` (`path`, `writable`) обеих сторон; `git status --short` по **всему** репозиторию
   каждой стороны, не только по `rules_dir`: чужие незакоммиченные и уже проиндексированные правки запомнить —
   в коммит правил они попасть не должны (шаг 8); чужие правки в самом `rules_dir` со своими не смешивать —
   спросить человека.
2. `rules_projects` → `rules_open(<rules_dir>\<план>\ExchangeRules.xml)` → `rules_validate` со структурами до
   правок (`start.md`, «Правила»).
3. Правки инструментами. Обёртки `handlers_export` — в рабочую папку сервера (`workspace`), не в `rules_dir`:
   экспорт удаляет из папки свои прежние `.bsl` (`handlers.py:636-645`), а в коммит проекта обёртки не идут.
4. `rules_save(project_id, <тот же путь>, overwrite: true)` — без `overwrite` существующий файл не заменяется
   (`workspace.py:84-90`). Правка загрузки — тот же проект правил ещё раз `rules_save` в
   `CorrespondentExchangeRules.xml` второго проекта: оба файла пишутся из одного дерева и совпадут (вывод).
5. Дифф до коммита — сначала смысловой: `rules_diff(left=<проект правил или файл до правки>, right=<файл после
   rules_save>)` — сводка по разделам и список изменений на языке правил (адрес, поле, старое → новое, построчный
   дифф обработчика); в нём должны быть ровно сделанные правки, ничего лишнего. Затем `git diff --stat` — только
   нужные файлы. Файлы, записанные 1С, — UTF-8 с BOM и
   переводами строк вперемешку. Сериализатор берёт один перевод строки по началу файла и ставит его везде
   (`xmlstyle.py:38`, `:81`, `:105`); при записи поверх существующего файла концы строк неизменённых строк
   сохраняются, у новых — конец строки выше (`xmlstyle.py:125`). Проверка до коммита прежняя:
   `git diff --stat` против `git diff --ignore-cr-at-eol --stat` — после записи поверх живого файла цифры
   совпадают; если нет, в сообщении коммита — обе цифры и что остальное — концы строк. Виден ли шум, решают
   настройки репозитория: при `.gitattributes` `* -text` git хранит байты как есть и покажет все строки, при
   `core.autocrlf=true` без `.gitattributes` сведёт концы строк сам — поэтому один и тот же файл в двух
   репозиториях шумит по-разному, проверять нужно оба. Если файл записан не поверх (новый путь) и шум
   неприемлем, собрать файл побайтово: взять исходный файл, перенести в него только изменённые строки (новые —
   с концами строк соседей), сверить `rules_diff` с записанным сервером файлом — пусто, и `git diff --stat`
   равен `git diff --ignore-cr-at-eol --stat`. Точечная правка без
   сериализатора — тоже побайтово, не `sed -i`: он переписывает переводы строк во всём файле (наблюдение на живом
   файле правил).
6. `rules_pack(folder=<rules_dir>\<план>)` — ZIP из файлов байт в байт (`pack.py:13`) в рабочую папку, не в
   `rules_dir`: `warnings` пусты, `load_with` — форма загрузки (`tools.md`, `rules_pack`).
7. Проверки — чек-лист `checklist.md`. Комплект в песочницу загружает агент сам: `bsp_check` — без записи в
   базу (`bsp_check.py:13-14`), `exchange_check` — загружает и записывает комплекты в обе песочницы
   (`exchange_check.py:124-132`); оба — из клона сервера и только для баз роли «песочница» (`checks.md`),
   у которых есть логин и про которые человек знает, что туда грузятся правила; иначе ступень «не прогонялась».
   **Боевая база — никогда**: ни загрузки правил, ни обмена, ни записи.
8. Коммит — в репозитории каждого проекта, где менялись файлы. Человек просил закоммитить — коммитить сразу.
   Не говорил про коммит — в конце работы спросить одной строкой (какие файлы, в каких репозиториях) и
   коммитить после «да»: правило клиента «коммит — только по просьбе» сильнее скилла.
   - коммитить только файлы `rules_dir` явными путями: `git commit -m "…" -- <путь к файлу> [<путь>]` — такой
     коммит берёт только названные файлы и не захватывает чужие правки, уже лежащие в индексе (шаг 1); не
     `git add -A`, не `git add .`, не голый `git commit` после `git add`. После коммита `git show --stat HEAD`:
     ровно файлы правил;
   - сообщение — `<план обмена>: <суть правки>`, например «<план>: поиск контрагентов по ИНН и КПП без
     наименования»; без `Co-Authored-By` и подписей генератора;
   - ветка — по правилам проекта, иначе текущая; пуш — только если так принято в проекте и человек согласен.
9. Ничего в проекте 1С вне `rules_dir` не менять: `AGENTS.md`, `CLAUDE.md`, `.claude\`, `.cursor\`, исходники
   и макеты `Templates\…` — по процессу самого проекта (захват в хранилище, его проверки).
10. Отчёт: какие файлы и в каких репозиториях, хеши коммитов, что загружено в какую песочницу, итоги ступеней
    лестницы.

## Коротко: правка, дифф, коммит

Правила, которые загружаются в базу из файла и лежат в репозитории проекта: открыть из `rules_dir`, сохранить
туда же, правка загрузки — и в файл корреспондента второго проекта; комплект в песочницу загружает агент, боевая
база — никогда. Перед коммитом — `rules_diff` файла до и после (или проекта и файла): в диффе ровно сделанные
правки, без шума XML. Коммит только файлов `rules_dir`: человек просил — сразу; не говорил — в конце работы спросить
одной строкой (какие файлы, в каких репозиториях) и коммитить после «да». Порядок и сообщение коммита —
раздел «Порядок» выше.
