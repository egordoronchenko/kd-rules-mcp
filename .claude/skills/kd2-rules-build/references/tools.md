# MCP tools reference

All tools of `kd-rules-mcp`: groups, purpose, parameter types/defaults and error codes.
Use the `kd2-rules-build` skill for the workflow and [architecture.md](https://github.com/egordoronchenko/kd-rules-mcp/blob/main/docs/architecture.md) for server internals.

Rule abbreviations retain the names used by «Конвертация данных»: ПКО (object conversion rule),
ПКС (property conversion rule), ПВД (data export rule), ПОД (data cleanup rule in KD 2; data processing
rule in EnterpriseData), ПКПД (predefined data conversion rule), ПКЗ (value conversion rule),
ПРО (object registration rule). ПКГС is a property group conversion rule; ПКТЧ is a tabular section
conversion rule. 1C tags, object/procedure names and literal parameter values stay unchanged.

`scripts/dump_tools.py` generates the marked section from tool docstrings and `Field` descriptions
in `src/kd_rules_mcp/server.py`. Run `uv run python scripts/dump_tools.py --write` after editing them;
it also refreshes `.claude/skills/kd2-rules-build/references/tools.md`. `tests/test_tools_doc.py`
checks freshness and the context budget. The manual section below the markers preserves response
details, examples and constraints; update it when the corresponding tool changes.

### Configuration structures and candidates

Metadata kinds include `Справочник`, `Документ` and `Перечисление`.

Project paths and extensions come from `projects.yaml`. XML cache fingerprints use
`Configuration.xml` and `ConfigDumpInfo.xml`; load results contain counters and unresolved types.
The earlier MD83Exp estimate was about one minute per 1 GB, not a performance guarantee.
A cached structure ID can be `zup-full`; object names accept `Вид.Имя`, e.g. `Документ.Ведомость`,
or a KD type name.

Confidence values stay `точно` (exact), `синоним КД` (KD alias), `по синониму` (synonym suggestion),
`нет пары` (unmatched). Two standard configurations may contain hundreds of objects.
Matching follows KD automatic rules.

Private copies also have persistent workspace snapshots.

The default `rules_create` ID is
`new-<source_structure>-<target_structure>`, with `-2`, `-3`, etc. if occupied.
`correspondent_draft` derives a unique ID from `corr-<project_id>`; registration derives one from
`reg-<exchange_plan>`. Unsafe characters in generated labels are normalized or hashed.
Explicit occupied IDs are rejected. See [workflow.md](https://github.com/egordoronchenko/kd-rules-mcp/blob/main/docs/workflow.md) for project lifecycle.

Shared `kind` values are `pko`, `pks`, `pks_group`, `pkz`, `pvd`, `pod`, `algorithm`,
`query`, `parameter`, `conversion`, `pro`. `conversion` is the one set of conversion events per
exchange file; creating/deleting it separately is rejected. `pro` applies to registration projects.

Shared `key` syntax:
- ПКО/ПВД/ПОД: rule code; algorithm/query/parameter: name.
- ПКС: `group/…/target-property`; empty target uses the source name; parameter ПКС uses
  `ИмяПараметраДляПередачи`. Group segments use the same path syntax. Ambiguous siblings add
  `[поиск]`, both names separated by `→`, and only then `#N` as needed. Legacy source-qualified
  and `#N` addresses still identify the same rule.
- ПКЗ: source value name.
- ПРО: metadata object (`ПРО «Справочник.Имя»`, repeats add `#N`) or rule code.
- `conversion`: empty string or `Конвертация`; responses use `Конвертация`.

`owner` is the owning ПКО code for `pks`, `pks_group` and `pkz`; otherwise leave it empty.
`group` is a path of group codes separated by `/`, e.g. `Справочники`; empty means list root.
It applies only to `pko`, `pvd` and `pod`. Supply optional side structures to check objects and
properties; omitting a structure skips its checks.

`fields` maps tags/attributes to values, e.g. `{"Наименование": "…", "ПриВыгрузке": "<code>"}`.
ПКС sides use nested maps: `{"Источник": {"Имя": "…", "Вид": "…", "Тип": "…"}}`.
See the edit tool descriptions above for atomic refusal and conversion-event restrictions.

All targets receive the same nonempty field map, e.g. `{"НеЗамещать": true}`, including nested
side maps above. `keys=null` selects all rules of that kind except `except_keys`; explicit `keys`
select addresses directly. ПКС paths and ПКЗ names use the shared syntax, including `[поиск]`/`#N`
qualifiers.

`rules_overview.counts.conversion` counts filled conversion events; `rules_list` section
`conversion` contains one row, while `pks` lists ПКС across all ПКО.
`rules_get` truncates handler text at 2000 characters; its `limit` caps child ПКС/ПКЗ lists at 200.
Compact child ПКС rows expose nonempty `handlers` (names of `ПередВыгрузкой`, `ПриВыгрузке`,
`ПослеВыгрузки`), nonempty `ИмяПараметраДляПередачи` and true `ПолучитьИзВходящихДанных`.
Absent flags mean empty/false. Standalone ПКС still exposes its stored `fields`/`attrs`;
use `handlers_export` for complete handler code.

### Saving, packing and validation

`rules_save` accepts workspace paths (relative paths start at its root) or absolute paths under
project `rules_dir` from `project_list`. Overwriting preserves line endings of unchanged lines.
Other write paths give `path_outside_workspace` with `workspace` and `writable`.

`rules_pack` accepts a kit directory (e.g. an exchange plan directory under `rules_dir`) with
`ExchangeRules.xml`, `CorrespondentExchangeRules.xml` and optional `RegistrationRules.xml`,
or explicit files. ZIP entries preserve bytes and use the required БСП names.
Two files load through `Правила конвертации объектов`; adding registration uses
`Загрузить правила синхронизации`; `load_with` names the form. Each file is checked for its kind.
`warnings` reports mismatched parts: a non-mirrored correspondent or registration for a different
configuration. The default ZIP is `<folder-name>.zip`, or `<exchange-file-stem>.zip` without a folder,
under the workspace. A supplied path may be in workspace or `rules_dir`.

`rules_validate` returns the result, skipped checks and a page of issues. For registration,
`source_structure` contains the exchange plan. Supplying `exchange_project_id` checks that each
plan-content object has an enabled ПВД; omitting it skips that check. Exchange projects ignore
this parameter. `rules_diff` compares same-kind rules without XML noise, returning section counts
and a page of changes. `detail=null` means full; brief keeps addresses only.
`handlers_export` writes handler/algorithm wrappers for a syntax checker, which the agent calls
separately; `handlers_locate` maps its errors back to rule/event/handler lines.

### Registration and reverse rules

Without explicit `objects`, an exchange project's ПВД can select registration objects.
When replacing selected filters, other rules remain unchanged.

The `objects` parameter table above lists object/filter keys and operators.
Filter groups also support node-attribute constants (`constant=true` with a literal `object_property`)
and tabular-section values (`[ТабличнаяЧасть].Реквизит`).
Unknown comparison/group operators give `invalid_argument`.

Disabled ПКС reasons name missing source/property/type in the reverse target structure; missing
ПКО type references are cleared and reported in notes. `target_structure` is the original source,
now the reverse target. `limit` caps handlers, disabled properties and notes.

### Retargeting registration rules

`registration_retarget` copies an open **registration** project to another exchange plan. It never
edits the source document or its file. Handler code remains unchanged; old names in code must be
reviewed by the agent and acknowledged before writing. Tool messages and notices are in Russian.

The required `source` object selects exactly one configuration dump:

- `{"project": "demo", "configuration": "full"}` uses `project_list` settings; configuration defaults
  to `full`. `extensions: null` or omission uses the configured extensions; `extensions: []` disables them.
- `{"configuration_path": "C:/Demo/Configuration", "extensions": []}` uses an explicit dump directory.
  Only the listed extensions are read, in their given order.

`node_properties` maps old node field names to new names. Keys may be `Name`, `[Table]`, or
`[Table].Name`; values are individual new names, without brackets or paths. `structure_id` is optional:
fields are always checked against the selected dump and its explicit extensions, even without it.
A supplied structure must come from that same dump and extensions and have their current fingerprint.
Omitting `structure_id` does not emit `registration.structure_unchecked`: the dump is required
and supplies the same field and type checks. An unreadable dump refuses the build.
Names are matched case-insensitively; `registration.property_case` reports names normalized to
metadata spelling in the output XML, including the linked node-property tables.
Mappings cannot merge two node fields, including through differences in case.
Absent mapping keys are reported in `unused_keys` and do not participate in collision checks.
`[Table]` without a field always blocks writing: BSP cannot build its query condition.
Existing fields are checked against the comparison's declared constant or object-property type
(boolean, date, number, string, or a named reference). Incompatible types emit a blocking
`registration.attribute_type`; unknown types or unresolved reference dereferences emit
`registration.type_unchecked`, require acknowledgement, and head the “Перенос неполон” instruction
block. Primitive fields cannot be dereferenced. `РеквизитРежимаВыгрузки` must be a header field of
type `ПеречислениеСсылка.РежимыВыгрузкиОбъектовОбмена`.
Composite object-property types need at least one type in common with the node field.

`own_attributes` is an optional list of `{name, type, synonym}`; only `type: "Булево"` is supported.
Supply it together with `extension: {name, prefix}`. Existing fields, prefix violations and attributes
owned by another explicit extension are refused. An own attribute supplies only a header field
without dereferencing, used in a comparison with a verified boolean value. It never supplies a
tabular section or its fields (`[Table]`, `[Table].Name`), a dereferenced path (`Name.Field`),
or `РеквизитРежимаВыгрузки` (which requires unload-mode enumeration values). Other comparison types
or unknown value types block writing. A KD2 constant with no `ТипСвойстваОбъекта` cannot prove a
boolean comparison even if its text is `true` or `false`; a missing constant type blocks writing
also for an existing field because BSP cannot load it. `node_values` is an optional instruction table:
`{source, target, instruction?}`. Without own attributes and extension the kit contains exactly the
rules XML and instruction, with no generated extension. Enabling `deletion_mark_filter` also adds
a kit manifest; extension kits always include one.
Empty rules or rules with every rule disabled or invalid refuse with `registration.empty_rules`: this file
replaces registration for the whole plan.

Each `node_properties` value may also be `null` (remove matching plan-filter leaves),
`{"name": "SendBank", "value": true}` (rename and change the boolean comparison constant), or a
nonempty list of those objects (replace one leaf by their AND at the same position; inside OR, use
a nested AND group). Replacements require `ЭтоСтрокаКонстанты=true`, `ТипСвойстваОбъекта=Булево`,
and a verified boolean target header field. Otherwise `registration.attribute_type` blocks write.
These values cannot replace `РеквизитРежимаВыгрузки`. Empty groups created by removal are removed;
an emptied plan filter remains an empty block. String values retain the existing rename behaviour.
Decisions apply to every matching leaf across rules; different decisions per rule require separate
projects/calls. This mapping does not delete a whole registration rule.
Preview `counts` include `replaced_leaves` and `removed_leaves` (per original leaf), and `changes`
is a paginated list of `{address, leaf, before, after, action}`. The instruction has a “Что заменено”
table. All supplied decisions participate in the preview hash.

Plan membership is always read from the selected dump's `ExchangePlans/<plan>/Ext/Content.xml`,
including explicit extension additions. `registration.plan_membership` requires acknowledgement:
the rule cannot run until its object is added to the target plan. The instruction lists those rules
under “Правила для объектов вне состава плана”. Missing or unreadable content emits acknowledged
`registration.plan_content_unchecked`. Content snapshots participate in the hash; checking against
a structure or directly against the dump produces the same result. Old kits with unchecked content
now need a fresh preview and acknowledgement; the registration XML is unchanged by this check.
A project without a source file refuses with `registration.source_required`; save it with `rules_save`
and reopen the file with `rules_open`. `registration.already_targeted` refuses only when the plan
is already targeted, the mapping is empty and `deletion_mark_filter` is false; old fields may be retargeted,
and explicitly supplied absent keys remain unused.

`deletion_mark_filter: true` adds an object filter `ПометкаУдаления = false`, ANDed with existing
filters, to each enabled rule whose object has that standard property in the target configuration.
The default is false. The standard property is read from metadata. BSP checks the filter at unload
only for catalogs, documents, characteristic/account/calculation charts, business processes and tasks.
Other kinds with the property (such as exchange plans) are skipped as `unsupported_kind`.
With no `structure_id`, the same metadata reader supplies standard properties from the selected dump;
read object files and plan content participate in the preview hash. Disabled rules and objects without
the property are skipped silently. Any existing filter on the property is preserved and reported.
The `deletion_mark_filter` response contains `enabled`, `added`, `skipped` and `skipped_by_reason`
(`disabled`, `invalid`, `unsupported_kind`, `no_deletion_mark`, `existing_filter`, `object_unchecked`).
Enabled previews also return `mode_rules`: the number of active eligible rules with a node unload-mode
field. Each has a paginated `registration.deletion_mode` notice and an instruction-table row with its
rule address and field name. Only `Валидное="true"` rules are active; false or absent is inactive,
like disabled rules (BSP ЗПРО:289–292,1065–1085).
The manifest records `deletion_mark_filter: true` only when enabled. When false, kit bytes and hashes
match the version before this option; the manual kit preserves all notices in its incomplete block.
Instructions explain modes once and list rules/fields; missing-rule objects share one explanation
and object list. Tool notices and acknowledgement IDs remain per rule/object.

Deletion notices are paginated with the other notices. These require acknowledgement before write:
`registration.deletion_missing_rule` (plan member without an enabled rule),
`registration.deletion_partial` (some rules gained the filter, another active rule lacks a proven guard),
`registration.deletion_handler` (preserved handlers or value algorithms may alter filters or recipients),
`registration.deletion_mode` (node unload mode cannot be checked statically),
`registration.deletion_unchecked` (object metadata is missing), and `registration.deletion_existing`
when the existing filter cannot be proven to be a root boolean equality to false. A clear existing
root equality only emits an informational notice. The instruction starts with required notices and
explains conditional unload modes, receiver UID matching, initial unload and closed-period limits.
Static checks do not prove deletion delivery; verify an ordinary catalog item and a posted document
in a test exchange.

Node modes have different deletion behaviour. `По условию` or an empty mode uses the filter.
`Выгружать всегда` bypasses it. `При необходимости` sends the mark as deletion even without this
filter, but unmarking does not register the object until its next change: rewrite it or register it
for sending after unmarking. `Вручную` and `Не выгружать` remove marked objects from registration
without sending deletion; initial unload skips marked objects except for nodes with `Выгружать всегда`
(BSP ОДСоб:2958–2972). Mode notices, the instruction
table and test step 2 explicitly explain the additional rewrite for on-demand catalogs.

Example with fictional names (first open the source using `rules_open`):

```json
{
  "project_id": "demo-registration-1234",
  "exchange_plan": "TargetPlan",
  "node_properties": {"OldDate": "DateStart", "OldFlag": "reg_Flag"},
  "source": {"project": "demo", "configuration": "full"},
  "structure_id": "demo-full",
  "deletion_mark_filter": true,
  "own_attributes": [{"name": "reg_Flag", "type": "Булево", "synonym": "Флаг узла"}],
```

Preview writes nothing. The response contains `counts` (`rules`, `renamed_leaves`, `untouched_leaves`,
`unused_keys`, `code_mentions`), the `unused_keys` list, `files` (`path`, `sha256`, `bytes`),
`preview_hash`, `output_path`, `status`, `message`, `written`, `runtime_verified: false`, and
`required_acknowledgements`. `notices` uses `items`, `total`, `offset`, `limit`, `has_more`;
repeat preview with `offset` and `limit` (1…200) to page through all notices. Paging does not change
the hash. Each notice has a stable `id`, `check`, `address`, `message`, `blocking`, and
`requires_acknowledgement`; field notices also have `leaf` and the full `reference`, missing-field
notices include `property_name`, and code mentions have
`event`, `line`, and `name`. Line numbers refer to the handler or value algorithm, starting at 1.

For write, send the same inputs with `mode: "write"`, `expected_preview_hash: <preview_hash>`, and
`acknowledged_notices: <required_acknowledgements>`. A missing field blocks writing unless an own
header boolean attribute will provide that exact reference and comparison; acknowledgement cannot
override that block. Incompatible types and bare tabular-section references also block writing.
A blocked extension preview has an empty `files` list because delivery refused
to render an unsafe kit. Code mentions and unsaved project edits require their notice IDs and appear
at the start of the instruction, as do acknowledged unknown-type notices. Status is `ready` or
`blocked` in preview, `written` after publication, and `unchanged`
for repeated identical writes (`message: "Без изменений."`). Installation and live exchange remain
separate steps.

The computed output directory is
`workspace/registration-retarget/reg-<owner-hash>/kit`. An atomic ownership receipt sits beside
`kit`, outside the two-file manual kit. It survives server restarts. The owner includes the source
project and source file path, target dump, ordered extension paths, plan and extension identity.
The manifest hashes `input_hashes.source_rules` from the input model in memory and `source_file`
from disk separately. Semantic differences produce `registration.unsaved_changes`; the source stays intact.
Changed or foreign files, extra directories,
symbolic links and junctions are refused, as for ED authoring kits. Source rules and target input
hashes are checked again before publication.

Errors contain `code` and a Russian `message`. Lower-layer refusals carry `failures` with addresses:
`registration.not_registration`, `registration.invalid_name`, `registration.duplicate_target`,
`registration.property_clash`, `registration.invariant`, `registration.retarget`,
`registration.delivery`, `registration.delivery_profile`, `registration.plan_not_found`,
`registration.attribute_clash`, `registration.attribute_prefix`, `registration.extension_clash`.
Service refusals are `registration.snapshot_mismatch`, `registration.missing_attribute`
(`failures` contains blocking notices), `registration.stale` (current `preview_hash` when available),
`registration.ack_required` (`required_acknowledgements`, `preview_hash`),
`registration.owned_content_changed`, `registration.source_required`, `registration.empty_rules`,
`registration.already_targeted`, `registration.path`, and `registration.io`. Invalid parameter
types or fields use `invalid_argument`; unknown project/structure IDs use the usual project/structure codes.

## EnterpriseData: workflow, addresses and responses

Open a manager with `ed_open`, inspect `ed_overview`, use `ed_list`/`ed_get`/`ed_locate`,
then call `ed_validate`. The reader does not execute BSL, traverse adjacent modules or write sources.
Registration managers are unsupported. Snapshots, address indexes and reference indexes stay in
memory. The reference index is built once at the first validation or code-reference request
and remains until `ed_close`. Reopening returns the old snapshot with `reused=true`;
`source_changed` compares current source bytes with the snapshot hash. Reread with close/open;
after a server restart, open again.

The snapshot ID is `ed-<module-name>-<12-character sha256 of server path>`.
For `Ext/Module.bsl`, the name comes from the directory above `Ext`; otherwise it is the file stem.
A short-ID collision uses the full path hash.

### Opening and composing layers

Use exactly one mode: `path` to a UTF-8 manager file
(`…/CommonModules/<Имя>/Ext/Module.bsl`), or `project` + exact `module` name.
Project `configuration` defaults to `full` and can select another configured configuration.
With `path` and nonempty `extensions`, supply the base dump `configuration_path` containing
`Configuration.xml`. Project mode forbids `configuration_path`. In project mode,
`extensions=null` uses settings, `[]` disables extensions, and an explicit ordered list replaces
settings. Path mode without extensions keeps the base-only response shape.

Layer order is part of the reuse key. `source_changed` does not update an issued snapshot.
`ed_routes` provides ready opening arguments with the same layer kit. The tools do not write
modules or install extensions. Extension activation and infobase connection order are unverified.

Short addresses and `Действующее/<address>` select effective entities; children keep that prefix.
`Слой/<id>/…` selects a source revision; ambiguous addresses require qualification.
With layers, normal `ed_list` kinds show effective entities; `layer` lists layer sources,
`change` lists revisions, `hook` lists hooks, `layer_unknown` lists unread code regions without
source text. `layer` filters a layer; `entity_id` with `kind=change` selects history by
`logical_id`. `direction=null` merges contexts and labels them with `contexts`;
`send`/`receive` selects a direction; `headers_only` selects the header-only pass of
manager interface version 3. If fields differ, `ed_get` returns `requires_context` and a
`variants` page: retry with explicit `direction` and `headers_only`.

`include_text` returns only a source-text page of the chosen revision, hook or operation.
For effective rules, `source_declaration=true` marks the source declaration; fields describe the
effective composition. Bindings use `binding/<id>`, dispatcher branches use `case/<id>`;
the ID segment is escaped and may be prefixed with `Действующее/` or `Слой/<id>/`.
Effective fields are not presented as source BSL. `ed_get` returns `state`, `layer_id`,
`origins`, `changed_fields` and `certainty`.

Handler `contexts` match between short and `Слой/<id>/Обработчик/…` addresses: they describe
effective bindings/calls, including calls to lower-layer handlers. A source declaration alone
does not establish a call context. Inactive directions give `rule_not_found` with the context.
The `handlers` count retains source-manager declaration roles; extension-owned handlers are
added only in effective call contexts. `kind=handler` lists effective roles, so its length can
differ from the source count.

`ed_locate(file_id=…)` chooses a `source_files` entry. Hook lines point to
`Слой/<id>/Перехват/<имя>`. Extension file IDs are `<layer-id>:<path-from-extension-root>`;
the base keeps its original `file_id`. Agent paths remain in `path` and `source_files.path`;
layer lists contain IDs, names and fingerprints.

Unknown `layer` gives `invalid_argument`; unknown `entity_id` gives `rule_not_found`.
Repeated extension paths or duplicate extension names are rejected.
Without layers, `direction=send/receive` and `headers_only=true` give `invalid_argument`;
`headers_only=true` is also unavailable for manager interfaces 1 and 2.

| `ed_open` | `composition_status`, `layers` (`total,items,has_more`, up to 16 rows), `contexts`, per-context `effective_counts`, `changes_summary` (`added,changed,deleted`), `skipped_summary` (`total,by_reason`); no operation text |

### Layer validation

`ed_validate` runs existing checks on each selected effective document and adds `ed.layer.*`.
`direction=null` equals `both`; identical issues across contexts appear once.
For layer-route checks, pass an `ed_routes` `route_profile_id` with the same base dump and
ordered extensions. A mismatch gives `invalid_argument`; omitting it puts route checks in
`skipped`. Base-only snapshots reject `route_profile_id`.

Layer validation is cached by snapshot, schema, structure, context and route profile.
Filters/pages reuse the full report. Closing a snapshot or dependency invalidates its reports.
Invalid binding signatures retain `resolution=invalid_signature` and an empty `target_id`
in `ed_get`; layer validation explains the call error.

`complete` means the static composition after filling and resolved event/procedure bindings.
Handler bodies remain opaque; `handler_execution_note` in `ed_overview`/`ed_validate` states
the runtime limitation. `fields.body_changes` on bindings identifies standard-handler hook kind,
layer, file and annotation line. Unmodeled hooks appear in `layer_unknown`/`skipped` with the
target name/class; function dispatchers produce an unknown function chain.
`ed.layer.handler.touches_rules` is only a lexical hint about rule access in an owned body/helper;
it does not reduce parse status or certainty.

Unsupported code returns success with skips; unavailable layer files give `ed_read_error`.
Authoring against layered snapshots gives `invalid_argument`: reopen the manager with
`extensions=[]`. All lists use `offset≥0`, `1≤limit≤200`; summaries contain counts and bounded
source lists.

### Validation reports

Call `ed_validate(project_id)` after opening. Link checks report inconsistent handlers,
dispatcher branches and local definitions; such errors may prevent a handler call or compilation.
Configuration checks report absent static metadata references. Supply `schema_id` for format names,
paths and values, `structure_id` for configuration objects/attributes/types, and both for type matching.
The open schema supplies the version and active namespaces; BSL is not executed.

`summary` covers the whole report before filters and names unchecked groups.
`level`, `check_prefix` and `address_prefix` filter the `issues` page with
`offset`/`limit`/`has_more`. Address matching is case-insensitive and uses an exact address or
a `/` boundary: `ПКО/Товар` matches `ПКО/Товар/ПКС/Код`, not `ПКО/ТоварПрочее`.
Empty prefixes disable filtering. Default `section=issues` includes `skipped` counts
(`total`/`by_check`) without reason text. `section=skipped` returns a page of unchecked records,
without `issues`; address filtering applies when a skip reason contains an address.
Without filters, repeated `ed.schema.required_unfilled` warnings occupy one row with `count`.
Use `section="issues",check_prefix="ed.schema.required_unfilled"` for all individual details.
Paging totals count displayed rows; `summary.by_check` always counts individual issues.

Code references are available through `ed_get(children_kind=reference)`.
Computed names count as unparsed, not errors. `ed_overview` diagnostics describe parse completeness;
`ed_validate` issues describe links and declarations. Skips include unchecked groups and opaque
conditions/sources, so no issues or a compact skip summary does not establish full coverage;
read reasons in `section=skipped`.

| Conversion, ПКО, ПОД, ПКПД | `Конвертация`, `ПКО/<Имя>`, `ПОД/<Имя>`, `ПКПД/<Имя>` |
| Header ПКС | `ПКО/<Имя>/ПКС/<Свойство>` |
| ПКТЧ and its ПКС | `ПКО/<Имя>/ПКТЧ/<Группа>`, `ПКО/<Имя>/ПКТЧ/<Группа>/ПКС/<Свойство>` |
| Search and ПКПД values | `ПКО/<Имя>/Поиск/<номер>`, `ПКПД/<Имя>/Значение/<номер>`; numbers start at 1 |
| Code | `Алгоритм/<Имя>`, `Обработчик/<Имя>`, `Служебный/<Имя>`, `Диспетчер/<Имя>`, `Событие/<Имя>`; one method can have several addresses |
| Parameter and unknown fragment | `Параметр/<Имя>`, `Неизвестное/<file_id>/<start-line>-<end-line>-<start-character>` |
| Version mention and diagnostic | `Версия/<entity_id>`, `Диагностика/<entity_id>` |

ПКО/ПОД names come from assigned literals; without one, the procedure name is temporary and a
diagnostic is added. Properties/groups use the nonempty format-side name, then configuration-side
name, then `~empty`. Segment characters `% / # ~` and control characters use UTF-8 percent encoding;
other Unicode stays unchanged. Casefold collisions give every address `#1`, `#2`, etc. in source
order. An unqualified collision gives `ambiguous_address` with `candidates: Page`; no first-match
selection occurs. Suffixes are stable only within an unchanged snapshot. Service children
(bindings/guards) use `<kind>/<entity_id>`; pass returned addresses directly to `ed_get`.

`Page = {items,total,offset,limit,has_more}`. Defaults: `offset=0`, `limit=50`.
Limits: `1≤limit≤200`, `offset≥0`. Entities follow source order; invalid bounds are rejected,
not clamped.

casefold. `Метаданные.Справочники.Имя` normalizes to `Справочник.Имя`; other metadata kinds
follow the same pattern. ПКС/ПКТЧ inherit ПКО sides. Unknown sides do not match; algorithms
without rule sides do not pass side filters.

group's ПКС. Child kinds: ПКО `pks,pktch,search,binding,extension`; ПКТЧ `pks`;

method `formal_parameter`; search set `field`; ПКС `argument,argument_presence`.
Dispatchers also have `case`; rules/methods have their owned `unknown`.
Handler/algorithm/event `reference` rows: `kind,name,form,access,direction,line_start,line_end`;
computed names add `unparsed=true` and `raw` capped at 160 characters.
Other entities reject `reference`; any child kind unavailable for its parent gives `invalid_argument`.

All five collections use the same offset/limit.

`span={file_id,line_start,line_end,char_start,char_end}`: lines start at 1, character positions at 0.
Tag text is not expanded automatically with its containing rule.
`TextPage={text,total_chars,offset,limit,has_more}` uses Unicode characters, defaults
`text_offset=0`/`text_limit=2000`, range `1≤text_limit≤8000`. Source text is absent without
`include_text`. Scalars over 2000 characters become `{preview,truncated:true,total_chars}`;
raw expressions also include `span`.

`associated` rules. Comments outside entities give an empty page with `classification=trivia`.
The line must lie within the selected file; base-only snapshots need no `file_id`.

ED errors: `ed_read_error` for missing/unavailable files, directories or unsupported encodings;
`ed_format` for empty/unrelated modules or unsafe BSL boundaries; `ed_resource_limit` above
32 MiB or 1,000,000 lines. Common errors: `project_not_found`, `rule_not_found`,
`ambiguous_address`, `invalid_argument`.
Multi-file managers are unsupported; a sign of splitting in a single module gives
`split_module_required` and `parse_status=partial`.

## EnterpriseData format schema

Workflow: `ed_schema_open` → `ed_schema_types` → `ed_schema_type` → `ed_schema_close`.
Use exactly one mode: `path` to `XDTOPackages/<имя>/Ext/Package.bin` or
`XDTOPackages/<имя>.xml`, or `project` + exact `package`.
Project `configuration` defaults to `full`; configuration extensions are not overlaid.
`format_version` is required and checked against the standard ED URI version (e.g. `1.8`).
Package name/revision (e.g. `EnterpriseData_1_8_6`), caption and format URI are separate;
no package/version is selected automatically. XSD is unsupported.

`imports` maps namespace URIs to local paths; project mode adds package descriptions from the
selected configuration. URIs are not downloaded. `extensions` lists ordered active format
extension packages, each importing the selected base. An import alone does not activate an extension.

`ed_schema_open` returns `schema_id,base_namespace,format_version,package` (description name
or null), `counts` for XML constructs across the closure including local types,
`status` (`complete`/`partial`), `diagnostics_summary,reused,source_changed`.
Snapshots stay in memory; edited files do not update an open snapshot. Reread with close/open.
A missing import gives `partial` and `unresolved_import`; malformed supplied XML is rejected.
Unresolved types/imports explain partial status in `diagnostics_summary`.

`ed_schema_types` returns `items,total,offset,limit,has_more` filtered by `namespace`,
`kind` (`object`/`value`) and `text`. Rows: `qname,kind,base,property_count` (including inherited
properties), `enum_count,status`. Named types include format objects (`Справочник.…`,
`Документ.…`), key properties and enumerations.

`ed_schema_type` accepts a short name (`Справочник.Валюты`, searched in base and active extensions),
Clark `{URI}Имя` or a local type ID from a `type` field. Imported types require full names.
It returns type data and a `properties`, `values` or `facets` page.
Properties expand key/common properties, giving the XML path and effective rule name;
rows contain `physical_path,effective_path,type,lower,upper` (null is unbounded),
`nillable,form,explicit_attributes,status,reference,table_row`.
`origin`/`origin_graph` and property `origin` are omitted unless `include_origin=true`.
Property provenance uses node IDs in the page's shared `origin_graph`; nodes contain
`role,namespace,span` (`source_id,line,xpath`), `via`. All physical candidates remain represented.
Pages contain at most `limit` rows (1–200), also capped at 20,000 UTF-8 JSON bytes.
Continue by adding the actual returned row count to `offset` while `has_more=true`.

For profile validation: `ed_open` → `ed_schema_open` → `structure_load_project`
(or `structure_load_xml`/`structure_load_md83exp`) →
`ed_validate(project_id, schema_id, structure_id, direction="both")`.
Schema/structure are optional: their missing groups appear in `skipped`; type matching needs both.
The schema supplies version/active URIs; `ed_validate` has no separate version/URI arguments.
`profile` contains `schema_id,structure_id,format_version,active_namespaces,direction` and
`fingerprints`: SHA-256 of `module`, `schema` (whole closure), `structure` (cache input hash).
Absent inputs are null; repeated calls use the existing snapshots.

`coverage` contains `checked,not_applicable,opaque_conditions,handler_may_supply,unresolved_schema`.
`both` merges identical issues; coverage and skip-reason counters count unique
“check × declaration” instances, without doubling direction passes.
Aggregated `skipped.reason` contains reason code, count and up to five addresses.
Unknown conditions, dynamic expressions and possible handler-supplied values cause skips.
`summary`/`coverage` cover the full report; issues filters affect only the issues page and keep
the complete skip summary without reasons. Facets/values preserve repeats and empty strings;
regular expressions are not executed. `ed_schema_close` returns `schema_id,closed`; repeated close
returns false.

Errors: `ed_schema_not_found`, `ed_schema_type_not_found`, `ed_schema_read_error`,
`ed_schema_format` (including XSD, DTD, entities, XInclude), `ed_schema_conflict`,
`ed_schema_ambiguous_import` (several descriptions of one URI; resolve with explicit `imports`),
`ed_schema_profile_mismatch`, `ed_schema_resource_limit`, `invalid_argument`, `project_config`.
Limits: 32 MiB per file; 128 MiB/128 files per schema; 200,000 types/2,000,000 properties;
XML/resolution depth 128; registry 256 schemas/512 MiB source bytes, without eviction.

The MCP SDK rejects arguments outside the input schema before calling the service
(e.g. `limit>200` or a missing required parameter). Example:
`validation error … Input should be less than or equal to 200`. Its error text has no JSON `code`
(verified via an MCP client on 2026-10-01).
Exceptions inside a tool are wrapped in JSON: `Kd2Error`/`ValueError` use the error table;
others use `internal` with exception text and a traceback in the server log.

## EnterpriseData format version routes

Open base dumps with `ed_routes` and pass their `profile_id` to `ed_route_compare`.
Select plans explicitly when several exist.
`ed_routes` accepts exactly one of `project`, `path`, `profile_id`.
Only `configuration=full` is allowed with path/profile selectors; `profile_id` cannot combine
with `force` or `extensions`. Project configuration supplies extensions unless replaced explicitly;
`null` uses settings, `[]` disables layers. `summary` returns the snapshot header;
`plans`, `versions`, `variants`, `packages`, `skipped` return pages.
`plan` narrows plans/versions/variants case-insensitively; responses preserve configuration spelling.
Omitting the name leaves all plans selected.

Without `force`, reopening reuses the snapshot and marks `stale` if sources changed.
`force` rereads sources; an existing ID remains until eviction, and unchanged bytes keep the same ID.
Snapshots stay in memory; reopen after restart/eviction. There is no close tool.
The registry holds up to 32 snapshots/128 MiB and evicts by age.

`ed_route_compare` context `plan` uses the node's map; `without_node` uses the global map,
forbids plan selectors and leaves the message URI unknown.
Pages: `issues`, `versions`, `schema_diff`, `skipped`. `summary` and skips cover the whole report.
Unknown check prefixes return empty issue pages without changing the summary.
Version pages show map key, manager, package and setting provenance.
`schema_diff` compares schemas sharing one URI, with up to 20 changes per row and full
`added_total,removed_total,changed_total,changes_total` counters.
`ed_open`/`ed_schema_open` fields contain ready arguments when the path/package is unambiguous;
otherwise they are null with a reason. Package name, map key and manager interface are separate.

`ed_routes.status` is parse completeness; `ed_route_compare.profile.status` is
`statically_compatible`, `blocked` or `unknown`. Skipped checks cannot establish compatibility.
Filters and offset/limit affect the requested page only.
Errors: `invalid_argument` (selector/section/context/plan/page), `ed_route_profile_not_found`,
`ed_route_read_error`, `ed_route_format`, `ed_route_resource_limit`,
`rejected` (project/configuration not found). Failure to read the selected URI's schema becomes
`skipped` with pair status `unknown`, rather than a comparison tool error.

## EnterpriseData authoring

`ed_authoring_candidates` lists unused attributes/format properties without automatic choice.
`ed_authoring_build` previews decisions and checks, then writes a validated kit to the workspace.
It updates only unchanged files it owns; manual instructions come from the same model.
MCP does not start the configurator or connect to an infobase for installation.

### Targets and operations

The `target` parameter above lists selectors and open snapshot IDs; choose a schema for the
selected version. Candidates require explicit `project`/`configuration`; build supplies them once per call.
An operation includes `target`, `configuration_attribute`, `format_property` and optional
`new_attribute` (`name,synonym,primitive`: `string`/`boolean`/`number`/`date`,
`qualifiers` within the closed authoring profile).
Omitting `kind` means `add_header_property` and retains legacy v1 IDs, hashes and bytes.
Other operation kinds use the same target:

| `kind` | Additional fields |
|---|---|
| `set_object_handler` | `event`: `ПриОтправкеДанных` / `ПриКонвертацииДанныхXDTO` / `ПередЗаписьюПолученныхДанных`; `body` without a procedure declaration; required `expected_previous` (empty for an empty event); `chain`: `none` / `after_existing` |
| `preserve_missing_header_property` | `property_operation_id` of a direct receive ПКС in this kit; the server generates the preset body |
| `add_algorithmic_header_property` | `configuration_attribute`, `format_property`, `handler_operation_id`, optional `conversion_rule` (default empty); the attribute must exist; receive currently gives `ed.author.not_supported` pending pilot acceptance |

For dependencies, first get the canonical `operation_id` from preview `section=operations`,
then pass the dependent operation in a new preview.
`drop_operations` explicitly removes previous-manifest operations; remove/replace dependent ones
separately. To change a body, drop its previous ID; list order does not establish precedence.
Bodies normalize CRLF/CR to LF and one final LF.
New/mixed kits use manifest v2; v1→v2 migration appears in `summary.migration` and `changes`.
Removing the last handler does not downgrade v2.

With an existing kit, `operations=[]` reloads its manifest decisions and revalidates current inputs,
including after restart. Empty operations may accompany `drop_operations`; dependent decisions
must be removed explicitly. Without a previous kit, operations must be nonempty; the final set
must always remain nonempty.

Candidate compatibility requires `configuration_attribute` or `format_property`;
without a pair, `compatible=null`. Candidate rows contain only `name,path,type,compatible,reason`;
`auto=false` applies to the whole response. `text` is a case-insensitive name/path substring.

### Preview, write and identity

Acknowledge scope explicitly with `version_scope=manager`; null fails core preconditions.
Other versions of that manager generate separate notices; “no new issues” applies to selected profiles.
Delivery forms are `extension` and `manual`; `extension_with_load` is reserved for the loading script.
Preview creates no files. Write requires `expected_preview_hash` equal to current preview
`build_hash`, and all exact `required_acknowledgements` IDs in `acknowledged_notices`.

The preview hash binds input hashes, canonical decisions, delivery form and generated manifest files.
The manifest retains the original core preparation hash.
The `instruction.md` header uses `manifest.build_hash` (shared for several managers), which differs
from the preview hash incorporating the validation report and generated files.

`rebuild=true` means inputs changed since the previous build (`changed_input_groups`:
configuration, structure, routes, schemas, extensions or manager files).
New operations or `drop_operations` with unchanged inputs do not set it.

For manifest v2, `extension/Configuration.xml` extension `Версия`
(`Properties/Version` after `Vendor`) uses the first 12 characters of the final decisions
fingerprint (`decision_hash`, not `build_hash`), also stored as `extension_version`.
V1 keeps `extension.version`; migration changes only that XML line.
The instruction probe reads `РасширенияКонфигурации.Получить` and `Версия`.

### Build responses and pages

Build returns `status` (`ready`/`written`/`unchanged`), `build_hash`, agent `output_dir`,
`written`, `runtime_verified`, short `runtime_unverified` IDs, `scopes`, `change_counts`,
`validation`, `required_acknowledgements` and an `items` page for the chosen `section`.

`changes` is the delta from the previous kit (empty without one):
`schema_version` with `from/to`; `operation_added/operation_removed` with ID/kind/target;
`binding_added/binding_removed` with ПКО/direction/event/procedure/module;
`procedure_added/procedure_removed/procedure_changed` with name/module.
`change_counts` counts the full result, not this delta.

- `summary` (default): authoring notices (`kind=notice`), `issue_new`/`issue_disappeared`,
  operation-relevant `skipped_new` and `file` rows (name, size, SHA-256).
  Unchanged old issues are counts. Skips in unselected profiles collapse to
  `skipped_new_count` (`check,reason,count`); details remain in `skipped`/`validation.json`.
  Required acknowledgements appear first; their complete messages remain in header
  `acknowledgement_notices` regardless of pagination, with IDs in `required_acknowledgements`.
  Scope summary contains manager, directions, plan count and version keys per plan, excluding
  variants, sources and call chains. `validation` contains final before/after errors/warnings/skips,
  selected-profile delta, checked profiles and other-version status counts.
  Other-profile new issues remain in `items`; per-check details are in issue sections.
- `issues_before`/`issues_after`: full stage issue pages with validation profiles.
  Filters: `level` (`ошибка`/`предупреждение`), `check_prefix`, `address_prefix`.
- `scopes`: route rows with manager, plan, variant, version key, state and source location;
  no call chains.
- `skipped`: before/after skip pages with profiles and unchecked runtime conditions.
  Supports `check_prefix`/`address_prefix`.
- `operations`: canonical operations including retained previous ones.
  Rows: `operation_id,kind,target,dependencies`; ПКС adds attribute/property names;
  bindings add `event,handler_name,runtime_verified=false`; bodies add `body,body_sha256`;
  algorithmic ПКС adds `conversion_rule`; new attributes add `new_attribute`;
  `body_origin` is `agent` or `preset`. Inapplicable fields are omitted.
  Several presets for one event show their shared generated body.
  Pagination uses `offset,limit,has_more,next_offset`.

V2 adds compact `summary`: `handlers,presets,algorithmic_properties,runtime_verified`,
`bindings`/`body_unparsed` counts, manifest version/migration, and
`layer={certain,unknown_lines,unresolved_dispatch,new_issues}`.
`template_evidence` describes preset pilot evidence, not execution of this kit.
Bodies appear only in operations pages and kit files, never summaries, refusals or service logs.
Preview composes the generated module with the base manager and explicitly listed project
extensions through the layer reader. New link/layer issues cause `ed.author.new_issues`.

All summary fields cover the full result; filters/pages do not change them.
`summary` does not filter `items`, to keep required notices visible.
`mode=write` permits only `section=summary`.
Precondition refusal remains `ed_authoring_precondition` with `failures`.
Full details in `validation.json`/`instruction.md` do not depend on page/section choices.
Static checks do not verify runtime exchange.

Build/candidate pages stop at whole rows within a soft 4 KB UTF-8 JSON budget with indentation,
matching MCP SDK text output. The budget covers only `items,offset,limit,total,has_more,next_offset`,
not the fixed header. `limit` caps row count; continue with `next_offset`, not `offset+limit`.
Summaries, acknowledgement IDs and individual rows are not truncated; a large indivisible row
or required summary can exceed the budget.

### Limits, output paths and errors

Limits: 100 operations/call, 16 managers, 64 version profiles, 1000 files/32 MiB output;
at most 100 final handler slots; each body ≤64 KiB UTF-8 and ≤2000 lines, all bodies ≤1 MiB.
Exceeding them gives `ed_authoring_resource_limit`.
An operations row may exceed the soft page budget but not body limits.
`offset≥0`, `1≤limit≤200`; at most 200 mixed-kind rows per page.
Input cache: up to 32 entries/128 MiB source text, evicted by age.
Overlay authoring has no persistent project or `draft_id`; manager projects use `ed_create` below.

Build reads the previous manifest from the computed
`workspace/ed-authoring/<name>-<first-8-base-configuration-UUID-characters>/` directory and
preserves decisions, UUIDs and one interceptor per manager.
Foreign/changed content blocks writes. Other `output_dir` values, `rules_dir`, symbolic links and
junctions are forbidden. Publication failure preserves the previous kit.
A human installs it following the instructions.

Errors: `invalid_argument`; `project_not_found`/`ed_schema_not_found`/`structure_not_found`
for snapshot dependencies; `ed_authoring_precondition` with
`failures[{id,address,message,source:{file,line}}]` and `summary`;
`ed_authoring_ack_required` with `required_acknowledgements`/`preview_hash`;
`ed_authoring_stale` for changed inputs, preview hashes or previous kit during writing;
`ed_authoring_path` for foreign files/directories, links or paths outside workspace;
`ed_authoring_resource_limit` with `resource/limit/actual`; `ed_authoring_io` for reading/publication.
An unread other-version schema remains `other_version_unverified`; core failures retain IDs
and origins. JSON shape/enums give `invalid_argument`; handler/dependency preconditions give
`ed_authoring_precondition` (IDs in [checks.md](checks.md)).
Acknowledge exact notice IDs, including `ed.author.preserve_absence_keeps_value` and body notices.
The new hash includes canonical bodies, bindings and the full layer report; an old preview
cannot authorize changed decisions/inputs. Manual edits to owned bodies block rebuild with
`owned_content_changed`; directory changes during publication give `ed_authoring_stale`.

## Writing a manager module

`scope="manager"` writes a complete interface-2 manager. Calls without `scope` retain
the overlay contracts above. Operations cover ПКО, ПОД, direct/reference/algorithmic header ПКС,
identification/search, ПКПД/value pairs, parameters, handlers, conversion events and algorithms.
Reserved kinds refuse with `unsupported_form`.
No BSL executes during authoring; installation and live exchange are separate steps.

Manager validation/build also report two live-exchange risks. `ed.schema.reference_type_partial`
warns when a direct send reference ПКС targets a ПКО covering only part of the configuration
attribute's composite type; key properties are identified explicitly. Use an algorithmic ПКС
to choose the ПКО by the value's type. ПКПД and algorithmic properties are excluded.
`ed.handler.format_enum_as_string` warns when editable receive code compares an XDTO enumeration
structure with a string or passes it to `СтрНайти`/`ВРег` without extracting `.Значение`.
It follows direct reads, literal subscripts, `ДанныеXDTO.Свойство` output variables and arguments
passed to local algorithms. Imported preserved bodies are exempt; without a schema it skips with
`schema_required`. Both warnings require build acknowledgement. See pitfalls 22–23.

The kit's “Проверьте данные перед первым обменом” block is a single section. Subheading
“Обязательные незаполненные свойства” lists count queries for sources whose `FillChecking`
is not `ShowError`. Subheading “Ключевые свойства ссылочных типов” lists read-only queries
for declared sources of mandatory reference-type keys, including attributes with `ShowError`:
data-exchange loading mode can bypass fill checking. The same object and attribute appears
in one query. Unmapped algorithmic sources cannot be inferred.

1. Load the host structure and open its XDTO schema with `ed_schema_open`.
2. Call `ed_create` with an explicit `project_id`, host (`project,configuration` from
   `project_list` or `configuration_path`), `plan`, one `format_version` route key,
   and optional `schema_id,structure_id`. `extensions` is the ordered list of host extensions.
   Catalog extensions apply by default; an explicit empty list excludes them.
   `reference_manager={name,path}` identifies the typical manager for this exact route key.
   If null, adjacent `reference_manager_reason={id,message}` explains the unavailable route/source.
   A missing plan refuses with a paged `plan_candidates` list of ED plans.
3. Query `ed_authoring_candidates(scope="manager",kind="objects")`, then `kind="properties"`
   for a selected pair. Both accept `reference_document_id="auto",target.project_id` to load
   that route's typical manager and reveal semantic renamings. Choose each mapping explicitly.
4. Preview `ed_apply` with the current revision. Read canonical operations, changes and
   notices through pages; apply with its `preview_hash` and confirmations, omitting `operations`.
5. Navigate the returned `document_id` with `ed_overview`, `ed_list`, `ed_get`, `ed_locate`.
   `ed_validate` adds `ed.writer.*`, `ed.handler.unknown_name` and `writer` metadata.
   Pass open schema/structure IDs for the existing schema and metadata checks.
6. Preview `ed_authoring_build(scope="manager")`, review notices/files, then write with
   its `build_hash` and all required acknowledgement IDs.
7. `ed_close(project_id)` deletes the durable manager snapshot and its current read-only
   document; written kits remain. Closing just `document_id` closes only that reader snapshot.

`ed.handler.unknown_name` is an error in editable handler/algorithm/conversion-event bodies:
it reports the code address, body line, unknown name and actual formal parameters.
On a receive ПОД, use `ДанныеXDTO`; `ОбъектОбработки` is an executor-wrapper key, not a local name.
Scope includes parameters, declared/assigned locals, loop variables, module methods, configuration
common modules and platform globals; strings/comments do not count. Assignment introduces a name
after its right-hand side. Without an XML structure's common-module inventory, the check skips with
`structure_required`. Only `authored/editable` bodies are checked; `imported_opaque` and `retained`
bodies are exempt. This lexical check does not execute code
or prove assignment in every control-flow branch. Errors block build and cannot be acknowledged.

The kit instruction's ПКС total and runtime probe both count header properties plus all table-part
properties, including the initialized reference property on each send ПКО.

### Creation, import and recovery

```json
{
  "project_id": "positions",
  "mode": "new",
  "project": "HostProject",
  "configuration": "full",
  "plan": "ПланФормата",
  "format_version": "1.20",
  "interface_version": 2,
  "schema_id": "<open-schema-id>",
  "structure_id": "<loaded-structure-id>",
  "identity": {"name": "кд3м_Менеджер", "prefix": "кд3м_", "module_name": "МенеджерОбмена"}
}
```

An explicit `identity.name` takes precedence and preserves its UUID seed. New projects default
to `кд3м_Менеджер_<project-suffix>`, where the suffix is the first 32 characters of `project_id`
with characters outside Latin/Cyrillic letters, ASCII digits and `_` replaced by `_`,
followed by `_` and a 12-character hash of the full ID. Stored names of existing projects stay unchanged.
The name is at most 59 characters; different project IDs receive different kit directories and
UUID namespaces, including IDs that coincide after sanitizing or truncation.
Other identity defaults are those in this example, with `synonym="Менеджер обмена ED"`,
`version="0.1"`, `compatibility_mode=null` (inherit the host compatibility mode).
For import, use `mode="import",document_id="<ed_open-project-id>"` plus the same host/route
inputs. A standalone module inside the host `CommonModules` can supply its host path.
The source file stays intact. Imported text renders in `preserve` mode;
new managers render from the template. Layered reader snapshots cannot be imported.

Create returns `project_id,revision,existing,document_id,counts,executor_profile,notices,
import_report`. `counts` covers rule kinds; `import_report` includes kind/state counts,
diagnostic count and a page of diagnostics (`kind="diagnostic",code,address`) followed by
entries (`kind,address,logical_id,state,reason`). Repeat creation with `offset,limit` to
read further pages (`limit=20` by default); these controls do not enter project identity.
`section="import_report"` is the default; `notices`, `differences` and error `plan_candidates`
select their continuation pages. Offset applies only to the selected section; sibling pages start at 0.
`executor_profile={profile_id,verified,mismatches}` comes from a fresh comparison of host
executor modules and explicitly selected extensions. A mismatch permits creation but returns
`executor_profile_unverified`; the same live comparison runs on validation and build.
An extension intercepting the executor invalidates confirmation of its profile.

Projects persist in `workspace/.ed-projects/`. Repeating creation with the same inputs,
including resolved identity, schema/structure IDs and import source ID, returns `existing=true`
and the current revision. Omitted identity keeps the stored resolved identity on reopening.
Different arguments (including mode, host/project/configuration, plan, version, interface,
explicit identity and schema/structure IDs) refuse with `creation_arguments_changed` and
`differences[{field,existing,requested}]`.
`extensions` differences distinguish omission (`null`) from an explicit empty list (`[]`);
internal bookkeeping names are not exposed. Windows paths that would exceed the project file limit
refuse with `ed_authoring_path` before writing. Rebind file-write failures use `ed_authoring_io`;
The next request recovers the transaction journal. With the same arguments, changed input contents return
`existing=true` and a `creation_inputs_changed` notice with differences and a rebind hint;
the model keeps its original bindings. Apply/build refuse changed fingerprints until rebind.
Difference pages use `section="differences",offset,limit` and expose `difference_count,next_offset,has_more`.
After restart, reopen bound inputs before repeating `ed_create`. Missing schema/structure
snapshots refuse quickly with `ed_authoring_precondition`, failure `manager_inputs_not_open`,
`missing_inputs[{kind,id}]` and executable `reopen_calls[{tool,arguments}]`.
For catalog projects these are `ed_schema_open(project,configuration,package,format_version)` and
`structure_load_project(project_id,configuration_id,structure_id)`; dump projects receive
stored package/import paths and `structure_load_xml(configuration_path,extension_paths,structure_id)`.
Rebind refusals include the same calls; missing saved parameters are named explicitly.
No inputs are loaded implicitly. If restored IDs differ, use `ed_create(mode="rebind")`.
Once inputs are open, `ed_create` restores navigation.
The project retains schema source hashes, the host structure fingerprint and the configuration
dump fingerprint (the same export markers used by structure loading) for stale checks.
There is no additional manager-list tool.

Use `ed_create(mode="rebind",project_id=...,schema_id=...,structure_id=...)` to accept fresh
bindings. Reopen changed schemas with `ed_schema_close/open` first. Omitted host, route,
identity and binding IDs keep their previous values. With `project`, omitted `extensions` uses
that catalog configuration's current extension list; `extensions=[]` explicitly disables it.
With a dump path, omitted extensions retain the stored list and its checked status.
Rebind preserves rules, source text,
existing operation decisions and receipt files, adds a service binding decision and changes
revision. It detects the executor again and returns `rebound=true`, validation counts and
validation notices on the new inputs; notices do not discard the model. A successful rebind
does not return `creation_inputs_changed`. Rebind uses a durable journal: after an interrupted
write, the next operation commits the new inputs if their model was saved, or rolls back to
the old inputs otherwise, before allowing another apply. Recovery returns
`rebind_recovered` with `outcome="committed"|"rolled_back"` on reopening; this notice remains
in stored metadata until the next successful rebind. Rules and receipt history survive recovery.
The compact response includes `validation.issue_count` and up to ten validation notices;
read the full report with `ed_validate(document_id,schema_id,structure_id)` and its pages.
Import without a catalog project or an explicit `extensions` list reports
`extensions_unverified`, even if the base executor matches. Pass `extensions=[]` to state
that no extensions apply. Manager IDs have no reserved reader-shaped pattern: creation refuses
an already open reader ID, and `ed_open` refuses a computed ID owned by a durable manager
(`document_id_owned_by_manager`), including after restart. Ordinary reader IDs of any length
can be closed with `ed_close`.
`ed_close` also removes damaged projects and unfinished `creation.json` snapshots;
an unfinished creation with other arguments refuses with `differences`.

### Preview and apply responses

`ed_apply` preview returns `project_id,revision,future_revision,preview_hash,applied=false,
counts,operation_count,change_count,failures,skipped,required_confirmations,confirmation_count` and a page.
W2 changes operations/changes/notices; top-level keys stay.

| Response | Contract |
|---|---|
| `operation_count` | Includes failures; failed resolution/application has empty `result_id`. |
| `failures`, `skipped` | Page objects; rows respectively `reason,address,message,references` and repeated `client_id`. |
| `section` | `summary`: notices, changes, compact operations; `operations`: `operation,operation_hash,result_id`; `changes`: before/after; `notices`: code, locations, `notice_hash`. |
| Confirmations | Header holds ten; `confirmation_count,confirmations_has_more,confirmations_next_offset` cover the rest. Read notice pages. |
| Paging | `offset,limit,total,has_more,next_offset`; continue by `next_offset`, even below limit. `truncated_by="size"`: whole rows shortened to budget. Offset applies only to the requested `section` (also `failures`, `skipped`); sibling pages start at 0. Applies to build/import pages. |
| Creation notices | `notice_count,notices_offset,notices_has_more,notices_next_offset`, optional `notices_truncated_by`; repeat creation with `section="notices"` and the next offset. |
| Preview | Saves packet; model/reader unchanged; no `document_id`. |
| Apply | Atomic, `section="summary"` only; saved revision + live `document_id`. Changed model: `applied=true`, former document closes. |
| No change | `applied=false,reason="no_operations"` (empty) / `"already_applied"` (all decisions repeated); current revision in both modes. |
| Receipt replay | `replayed=true,applied=false,reason="already_applied"`; paged summary/skipped, current revision/counts/document; survives restarts/later packets. |

Apply: omit `operations`; pass `expected_revision,expected_preview_hash,confirmations`.
Last eight previews persist across restarts; input/revision/hash/confirmation checks apply.
Explicit unchanged packets also work.

| Recovery code | Action |
|---|---|
| `preview_packet_missing`, `preview_packet_corrupt` | Resend operations; preview again if inputs changed. |
| `receipt_page_unavailable` | One-page receipt; navigate current document. |
| `ed_authoring_stale` | Snapshot superseded; reopen current project/document. |
| `ed_authoring_precondition` + `project_busy` | Preview while another process holds the project lock; retry. |

### Manager candidates and delivery

Candidate target:
`{schema_id,structure_id,direction:"send"|"receive"}`; property queries add
`configuration_object,format_type`. Object pages contain `candidate_id,configuration,format_type,
namespace,direction,confidence,reason,auto=false`. Property responses have separate pages for
matched properties, unmatched format/configuration properties and table parts, as produced by
the manager candidate library. IDs bind the input contents; requery after input changes.
Both plain and reference object pages expose `offset,limit,total,has_more,next_offset`.
Add `target.project_id` to check that the structure comes from the manager's configuration
dump and exactly its selected extensions; this applies to both candidate kinds, even when
the manager has no bound structure ID. An unknown project ID refuses.

Property class `needs_pkpd` means a configuration enumeration meets a format enumeration:
create a predefined-data rule explicitly. These rows have `needs_rule=true`, `auto=false`,
`value_pairs[{configuration,format}]` for equal value names and
`unmatched_configuration_values,unmatched_format_values` for values still needing a decision.
No value mapping is chosen automatically.

For object candidates, optional `reference_document_id` adds semantic pairs from a typical
manager's ПКО with `confidence="reference",reason="так в типовом модуле",auto=false`
and `origin={document_id,address}`. The XML structure source establishes the host configuration;
Manager projects require XML structures; a foreign structure refuses with `ed.author.snapshot_mismatch`.
The reference snapshot must be inside that host's `CommonModules`. Pairs already suggested by names stay single rows;
rules definitely inapplicable to the selected version/direction are excluded.
For property candidates, the same parameter adds separate `class="reference_module"` rows
only for pairs not already suggested by names, with `confidence="reference"`, the same
reason/origin and `auto=false`. Equal configuration names (case-insensitive), physical XDTO
paths and namespaces merge into one name-based row with `references`:
`[{property_kind,rule_name,origin:{document_id,address},applicability}]`.
Multiple typical declarations remain separate entries in this evidence list.
`property_kind` is `direct`, `reference`, `pkpd`, `algorithm` (or `unresolved` for a missing target);
`rule_name` is the conversion target's name or null. Handler bodies are excluded.
Name-based pairs remain visible beside different pairs declared by the typical manager.
Manager property responses fit 8 KB by reducing the common window of all four sections.
Follow the response's top-level `next_offset` while `has_more=true`; `limit` is an upper bound,
and `truncated_by="size"` explains reduction. Each section also gives its total and continuation.
An indivisible oversized response refuses with `candidate_row_too_large`.
Use `reference_document_id="auto"` with `target.project_id` to resolve the exact plan/version
map and open its typical manager automatically; the returned `origin.document_id` is an
ordinary reader snapshot. Without a project, auto requires XML provenance and a unique ED
plan serving the schema version and extension paths stored in its source metadata. Extension
names alone cannot recover paths: `structure_extension_paths_unavailable` asks for
`target.project_id` or an explicit `reference_document_id`. An empty page without a reference
includes a hint to use auto.
If a previously opened typical snapshot changed, auto refuses with `ed_authoring_stale` and
its `reference_document_id`: close that snapshot with `ed_close`, then repeat auto.
An unavailable or ambiguous route refuses with `reference_manager_unavailable`; inspect
`ed_routes` and pass an explicit snapshot. Any own common-property group beneath root `КлючевыеСвойства`
is expanded, including `ДанныеКлассификатораБанков`; group names are unrestricted.
Groups that are references or another object's key-properties type stop expansion of their
whole subtree. Fields outside the own-key subtree retain the reference/classifier filter.
Manager-project primitive ПКС validation uses candidate compatibility, including string facets.
Ordinary snapshots and overlay reports retain their previous atomic type-check boundary.
Owner handlers no longer suppress declared direct ПКС type/range checks in either direction.
An obligatory format property without a rule remains a warning with a sending handler:
the handler may fill it, so verify its code. Manager builds require acknowledging this warning.
For manager-project snapshots, `ed.schema.value_range` warns when a sending string attribute
can exceed the format's `maxLength` (including unlimited strings) or cannot guarantee `minLength`:
the value will not export (XDTO:6103–6109). Build requires acknowledging these warnings.
Sending numeric limits remain `level="info"`, specifying which values will not export.
Receiving wider format values gives `info` about truncation, precision loss or failed writes;
fixed-length/date-part risks remain `info`. Messages name direction, both limits and the ПКС address.
`summary.info` counts information; filter by `level="info"`. Incompatible primitive types remain
warnings. Build checks bound types, ranges and required sources again, including after restart.
Review values or supply an algorithm.
Manager skipped pages retain machine-readable reasons and add a `hint` with the next action:
`non_atomic_type` requires a reference ПКО or algorithm, `qualifiers_unavailable` requires
updated structure/schema qualifiers, and `handler_may_supply` requires reviewing handler code.
For a table part with no format side, children report `empty_format_side`:
there is no format side to check. Configuration columns are still checked against the structure;
reopening the schema does not resolve this case.

and `acknowledged_notices` containing all required IDs. Only `section="summary"` is accepted.

are checked again before atomic publication. Owned files/UUIDs follow `render_manager_kit`;
foreign or edited kit contents block overwriting. Writes stay under `workspace/ed-authoring`.
Manager manifest schema v1 includes `project_id` and `creation_fingerprint`.
Every ПКО configuration object is checked against the bound exchange-plan content.

for that object. Unknown objects, unsupported event types and objects with a ПКО refuse.
The list is deduplicated and must be supplied in both preview and write. These objects enter
the plan content and registration event sources; they do not create conversion rules.
Existing plan members are also checked for registration coverage. Each missing object/event
produces `ed.plan.registration_unsubscribed` with a required acknowledgement. The kit adopts

The manifest exposes `registration_subscription_additions` (subscription name, base UUID,

content and listed in `subscription_adopted_objects`; an unadopted source type refuses.

`null` means subscription data is unavailable. `registration_retarget` adds acknowledged
`registration.plan_registration_unsubscribed` notices for active rules whose objects belong
to the plan but lack event coverage, with the same registration-only object advice as membership notices.

does not protect empty values. Writing requires acknowledgement. The instruction includes
source-data count queries to run before exchange; the server does not execute them. Missing
structure yields an explicit skip. Missing `FillChecking` is a skip only when the check
found no warnings; otherwise `ed.schema.required_unfilled.partial` (`info`) names the skipped
objects (at most ten, then “и ещё N”) and the check is not listed as skipped. Reload old XML

manager projects to refresh input fingerprints. MD83Exp lacks this field.
Common validators retain data preflight on direct, cached and layered paths.
Overlay delivery reports omit it; the data-check instruction belongs to manager kits.
Schema/structure absence returns `reopen_calls` with saved source parameters, as with
`manager_inputs_not_open`; missing source parameters appear in `missing_reopen_parameters`.
`ed_validate` and manager build share the semantic readback check: `ed.writer.read`
reports the first differing entity address and field. Delivery additionally uses
`ed.author.model_invalid` for readback and required-frame/report preconditions.
Opaque bodies are compared as exact text. Existing authored snapshots recover generated
frames and derived dependency indexes on load; rule IDs and body text remain intact.
A kit owned by another project refuses with `kit_owned_by_other_project`, naming both owners
and suggesting `identity.name`; acknowledgements cannot bypass ownership. An unreadable
manifest also refuses. The same project ID with changed creation inputs requires the
`kit_creation_inputs_changed` acknowledgement. Updates to the project's own kit remain supported.

Errors retain JSON `code`: `invalid_argument` for shape/enums; `project_not_found`,
`ed_schema_not_found`, `structure_not_found` for dependencies; `ed_authoring_precondition`
with `failures` for `unsupported_form`, `model_invalid`, `creation_arguments_changed`,

`ed_authoring_stale` with current `revision`/`preview_hash` or `build_hash` for stale

for unconfirmed notices; `ed_authoring_path`, `ed_authoring_resource_limit`, `ed_authoring_io`
for workspace safety, bounds and I/O failures. An unsupported interface never creates a project.

### Delivery into a user extension

`ed_authoring_build(scope="manager")` and `registration_retarget` accept
`delivery={"mode":"new_extension"}` (default) or
`delivery={"mode":"user_extension","extension":"Name"}`. For registration, the existing
`own_attributes` and `extension={name,prefix}` decisions remain required; the delivery name
selects the destination dump rather than the generated kit identity. The destination must be
listed in the host configuration's `extensions` and `writable_extensions` in projects.yaml.

Preview returns `delivery.files`: relative `path`, `action` (`create`, `change`, `unchanged`),
`size`, `sha256_before` (null for new files), `sha256_after`, and `changes` (added entries).
It writes nothing. Write requires the current preview hash and all ordinary acknowledgements.
The manifest, `instruction.md` and copies remain in `workspace/ed-authoring/<kit>`.
The manifest's `delivery` records the destination and file hashes before/after; original writer
decisions remain available. Rebuilds preserve prior entities and refuse changed own modules.
The extension's UTF-8 BOM and newline style come from its `Configuration.xml`.

The merger adds missing ChildObjects, PropertyState, plan content, Source types and node attributes;
it preserves existing entries and shared code. A foreign manager route for the same format version,
an occupied common module or an edited owned file causes `delivery_conflict`.
Other refusal codes: `delivery_unknown_extension`, `delivery_not_writable`,
`delivery_invalid_extension`, `delivery_compatibility`, `delivery_missing_object`, `delivery_stale`.
All files are staged before replacement; an exception rolls back replacements, including kit copies.
Installation and runtime verification follow the team's normal repository/storage workflow.

When the target is also an input layer of the manager or registration project, `delivery_inputs` records the
exact input fingerprint after writing. Only that recorded state is accepted without rebind;
later input changes retain the normal stale-input refusal. The receipt is published with the
same rollback transaction. It does not refresh the structure cache or prove runtime behavior.
