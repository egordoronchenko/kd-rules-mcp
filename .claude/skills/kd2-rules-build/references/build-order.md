# Порядок построения: ПКО → ПКС → ПВД → ПРО

Читать перед созданием правил: шаги с разбором ответов инструментов, реквизит в существующее ПКО, против какой конфигурации писать код обработчиков, ответы правок.

## 2. Порядок построения: ПКО → ПКС → ПВД → ПРО

1. **Выбор объекта.** `match_objects` **всегда с `text`** (и `kind`): стандартных объектов в двух типовых
   конфигурациях сотни, без фильтра ответ не влезает в лимит клиента. Или `structure_objects(text=…)` по обеим
   структурам. Проверьте, что ПКО для объекта ещё нет (`rules_list pko`).
2. **ПКО с ПКС** — `pko_create_from_candidates`: включены пары «точно» и «синоним КД», свойства приёмника без
   пары — выключенные ПКС. Разберите ответ:
   - `unresolved` — ссылочные свойства без однозначного ПКО: задать код существующего ПКО (`rule_update`
     поля `КодПравилаКонвертации`), создать нужное ПКО или выключить (`Отключить: true`) с причиной;
   - `not_applied` — пары с `auto: false` («примитив → ссылка», «по синониму»): только решением агента;
   - составные ссылочные поля с десятками типов (доп. реквизиты, наборы доступа БСП) обычно выключаются.
   Флаги ПКО (`СинхронизироватьПоИдентификатору`, `ПродолжитьПоискПоПолямПоискаЕслиПоИдентификаторуНеНашли`)
   и `Поиск` у ключевых ПКС — по образцу соседних ПКО правил. Обработчик `ПоследовательностьПолейПоиска` —
   с оглядкой на `kd2-exchange-pitfalls/references/search.md` (параметры при поиске, варианты, пустой ИНН).
3. **ПКЗ** для перечислений — `match_values` и `rule_create kind=pkz` (owner — код ПКО).
4. **ПВД** — `rule_create kind=pvd`: `ОбъектВыборки` (тип источника), `КодПравилаКонвертации` (новое ПКО),
   `СпособОтбораДанных` — по образцу существующего ПВД; обработчик — только если он действительно нужен.
   В обмене через план обмена ПВД только пропускает тип в выборку зарегистрированных изменений: способ отбора и
   `Отказ` в `ПередОбработкойПравила` не действуют, на тип работает первый ПВД (`references/pvd.md`).
5. **ПРО** — отдельный проект правил и свой файл:
   - `structure_plan_content(структура источника, план)` — состав плана обмена и авторегистрация; объект не в
     составе — добавить в состав в конфигурации (правилами это не чинится);
   - `registration_build(structure_id источника, exchange_plan, rules_project_id=…)` — объекты из ПВД, или явный
     список `objects` с отборами (`plan_filters`, `object_filters`); объект вне состава — предупреждение;
   - `rules_validate(project_id ПРО, source_structure=<структура источника>)` — приёмник не нужен;
     затем `rules_save` (`RegistrationRules.xml`). Группы отборов «И/ИЛИ» инструмент строит
     (`references/pro.md`, «Отборы в `registration_build`»); обработчики — правкой файла по
     `references/pro.md`, «Ручная правка файла» (порядок элементов, `Валидное="true"`, булевы
     `true`/`false`, без CDATA и комментариев, побайтово); правила конвертации руками не правятся.
6. **Обратное направление** — `correspondent_draft(project_id, codes, target_structure=<структура источника
   исходных правил>)`: только черновик; что делать с `handlers`, `disabled`, `notes` — `references/correspondent.md`.

### Реквизит в существующее ПКО

1. `rules_get(kind=pko, key=<код>)` — какие ПКС уже есть, флаги, обработчики; соседние ПКС — образец
   оформления. ПКС есть, но выключено — `rule_update` с `Отключить: false`, а не новое. У ПКО флаг
   `НеЗамещать` — найденные в приёмнике объекты новый реквизит не получат: решение человека или рецепт
   `references/pko.md` под `НеЗамещать`.
2. `match_properties(source_structure, target_structure, source_object, target_object)` — пара для реквизита и
   путь ПКС (`path`, у табличной части — `<группа>/<свойство>`); `auto: false` — только решением агента.
3. `rule_create(kind=pks, key=<путь>, owner=<код ПКО>, fields={"Источник": {…}, "Приемник": {…}}, …)` со
   структурами обеих сторон. Ссылочному реквизиту — `КодПравилаКонвертации` существующего ПКО (без ПКО для
   типа значение молча не уйдёт — `references/pks.md`); реквизит-ключ — `Поиск`.
4. `rules_validate` — нет новых замечаний. `pko_create_from_candidates` здесь не подходит: создаёт новое ПКО.

### Код обработчиков — против какой конфигурации писать

| Фаза | Обработчики | Где выполняется |
|---|---|---|
| выгрузка | ПВД; ПКО `ПередВыгрузкой`, `ПриВыгрузке`, `ПослеВыгрузки`, `ПослеВыгрузкиВФайл`; все ПКС и группы ПКС; события конвертации выгрузки | база-источник |
| загрузка | ПКО `ПередЗагрузкой`, `ПриЗагрузке`, `ПослеЗагрузки`, `ПоследовательностьПолейПоиска`; события конвертации загрузки; `ПослеЗагрузкиПараметра` | база-приёмник |
| алгоритм | по флагу `ИспользуетсяПриЗагрузке` | база своей фазы |

Где и когда вызывается обработчик, его переменные, что делает `Отказ`, почему ошибка прерывает обмен и почему
правку загрузки вносят и в правила корреспондента приёмника — `references/handlers.md`. Источники для кода:
переменные события — `handlers_export` (обёртка с точным набором параметров, как у КД); образцы —
`references/handlers-templates.md` и обработчики типовых правил того же плана обмена (`rules_open` макета →
`handlers_export`); API конфигурации — сервер кода проекта (`code_mcp`): выгрузочный — источника, загрузочный —
приёмника; платформа, БСП и шаблоны — общие серверы (`shared_mcp`). **Перед первым вызовом этих серверов
прочитайте `references/mcp-1c.md`.** Синтакс-чекер ловит синтаксис, смысл проверяет только живой обмен.

Ответы правок: `address` — что изменено; `skipped` — «правка применена, проверка по структуре не выполнена»
(передайте `source_structure`/`target_structure`); ошибки — JSON с `code` (`dangling_reference`,
`duplicate_rule`, `unknown_field` …).
