# Вторая сторона обмена

Обмен связывает две базы. Выгрузочные обработчики пишутся против источника, загрузочные — против приёмника, а
проверять результат нужно в обеих базах. Поэтому агенту нужны метаданные, код и данные **обеих** сторон.

## Что откуда брать

| Что | Откуда |
|---|---|
| Пара проектов обмена | `project_list` → `exchanges` (план обмена и два проекта) |
| Метаданные обеих сторон | `kd-rules-mcp`: `structure_load_project` для каждого проекта, `structure_object` |
| Код второй стороны | её сервер кода и метаданных; без него — файлы выгрузки конфигурации в папке проекта (`folder` из `project_list`) |
| Данные второй стороны | её сервер данных, только песочница и только с согласия человека в этой задаче |
| Какой файл работает в каком направлении | таблица «Направления» в `KD-EXCHANGE.md`; без неё — так: выгрузка и регистрация — `ExchangeRules.xml` и `RegistrationRules.xml` источника, загрузка — `CorrespondentExchangeRules.xml` приёмника (почему — `handlers.md`, «Где лежат правила загрузки») |
| Совпадают ли копии правил у сторон | `rules_diff` двух файлов; хеш файла не годится — концы строк в репозиториях сторон бывают разными |

Трасса по копии правил корреспондента (`rules_trace`) пропускает правила регистрации чужой конфигурации и
называет их в `registration.skipped`. Пустой `registration.items` при непустом `skipped` значит «ПРО источника
здесь нет», а не «ПРО нет»: правила регистрации источника — в комплекте источника.

Перед первым вызовом серверов 1С — `mcp-1c.md`.

## Папка обмена

Правила обмена удобнее всего править из **папки обмена**. Это отдельная папка вне папок проектов баз, где
подключены `kd-rules-mcp` и серверы обеих сторон. Её собирает `build_packs.py --dest <папка обмена>
--side <имя>=<папка проекта> --side <имя>=<папка проекта>` (из папки клона сервера).

- `KD-EXCHANGE.md` в корне папки показывает, какой сервер чьей стороны. Свои серверы стороны имеют префикс
  `<имя>-`, а общие (одинаковые у обеих сторон: синтакс-чекер, справка, БСП) — без префикса.
- Когда имена сторон совпадают с проектами из `project_list`, префиксы совпадают и с `code_mcp_server` проектов.

## Сеанс в папке одной базы

Серверов второй стороны в сеансе нет, и субагент их тоже не увидит: он получает серверы родительского сеанса.

1. Метаданные второй стороны берите из `kd-rules-mcp` (`structure_*`). Для них её серверы не нужны.
2. Код второй стороны (обработчик, общий модуль, который он вызывает) читайте из файлов её выгрузки по пути из
   `project_list`. Чего не нашли, то в отчёте отмечайте как «не проверено».
3. Проверку запросом на данных второй стороны вслепую не заменяйте: попросите человека или предложите папку обмена.
4. Если работы со второй стороной много, предложите человеку завести папку обмена. Серверы второй стороны в
   `.mcp.json` проекта базы не дописывайте: они мешали бы в каждом сеансе работы над проектом.
