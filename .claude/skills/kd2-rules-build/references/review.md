# Ревью готовых правил
Читать, когда просят проверить чужие или давно живущие правила («проверь правила», «что здесь не так») и перед
доработкой незнакомых правил. Сравнение с типовым макетом — `rules_diff(left=<макет плана из dump>, right=<живые
правила>)`: сводка по разделам показывает, что доработано (добавленные ПКО и ПКС, изменённые флаги и обработчики),
без шума XML; большой дифф — по разделам (`section`) и страницами.

Ссылки `стр. N` — модуль объекта `КонвертацияОбъектовИнформационныхБаз` (БСП 3.1.12); `РЕГ, стр. N` — модуль
объекта `ЗагрузкаПравилРегистрацииОбъектов` той же БСП. Идентификаторы проверок — `checks.md`, раздел 4.
Ревью ничего не меняет и не сохраняет: правки — отдельной задачей, по согласию.

## Порядок

1. `rules_projects` → `rules_open(<файл>)` → `rules_overview(project_id)`: вид, источник и приёмник из
   заголовка, число правил по разделам. Сверить, что стороны — те конфигурации, о которых речь: файл
   корреспондента — правила второй базы, по которым эта загружает (`ОбменДаннымиСервер`, стр. 10001–10083).
2. Структуры обеих сторон (`structure_load_project`) → `rules_validate(project_id, source_structure,
   target_structure)`; без структуры стороны её проверки в `skipped` — итог неполный
   ([structure.py:160-165](https://github.com/egordoronchenko/kd-rules-mcp/blob/main/src/kd_rules_mcp/validation/structure.py#L160-L165);
   `checks.md`, §2).
   Сначала `by_check`, затем ошибки по `check_prefix` постранично.
3. `rules_list` по разделам: `pko` (выключенные, ПКО без источника), `pvd` (ПВД на каждый тип, который база
   выгружает сама; на тип работает первый ПВД — стр. 18363), `algorithms` (флаг `ИспользуетсяПриЗагрузке` —
   фаза, стр. 6455–6469), `parameters`, `queries`, `pod` (в обмене БСП не выполняются — стр. 7409–7430).
4. ПКО с поиском — объекты, которые могут быть заведены в обеих базах (контрагенты, номенклатура,
   классификаторы): `rules_get kind=pko` — флаги поиска и `НеЗамещать` у ПКО и у его ПКС, ПКС с `Поиск`
   (только они уходят в `<Ссылка>`, стр. 790–826), обработчик `ПоследовательностьПолейПоиска` по скиллу
   `kd2-exchange-pitfalls/references/search.md` (параметры с «Поиск», варианты различаются, пустой ключ).
   - Флаги ПКО (`НеЗамещать`, `СинхронизироватьПоИдентификатору`, флаги поиска) сверять с типовым макетом плана,
     не только обработчики: `rules_open` макета (`dump` в `project_list`,
     `<dump>\ExchangePlans\<план>\Templates\ПравилаОбмена\Ext\Template.txt`) → `rules_get kind=pko` той же ПКО.
   - Правила из `rules_dir` — `git log` по папке → `git show` последних коммитов правил: что меняли кроме нового
     правила, прежде всего флаги ПКО и ПКС (перенос `НеЗамещать` с ПКО на ПКС — строка таблицы ниже).
5. Обработчики — `handlers_export` → синтакс-чекер → `handlers_locate` (`mcp-1c.md`), затем глазами по
   чек-листу `handlers-templates.md`. Синтакс-чекер обязателен, если его сервер подключён к клиенту
   (`shared_mcp` в `project_list`): по всем файлам `handlers_export` пачкой, подряд (`mcp-1c.md`, «Проверка кода
   обработчиков»); не прогонялся — причина в отчёте.
6. Правила регистрации — `rules_open` своего файла, `rules_validate` со структурой источника (`registration.*`);
   правила с `Отключить` или без `Валидное` проверка пропускает, как и читатель (РЕГ, стр. 282–293), — их
   смотреть глазами.
7. Комплект — `rules_pack(folder=…)` в рабочую папку: `warnings` — корреспондент не зеркален, регистрация для
   другой конфигурации ([pack.py:133-151](https://github.com/egordoronchenko/kd-rules-mcp/blob/main/src/kd_rules_mcp/authoring/pack.py#L133-L151)).

## Трасса объекта и код обработчиков

Для вопроса «что происходит с документом» начните с
`rules_trace(project_id, object="Документ.Пример", depth=2)`. Вместо полного имени можно передать
код ПКО или ПВД; `direction="import"` ищет объект по приёмнику того же файла, стороны файла не меняются.
Метаданные регистра и тип его записи сопоставляются одинаково; код правила не зависит от регистра букв.
Для неизвестного объекта ответ содержит `found=false`, `status="not_found"`.
Разделы `registration`, `branches`, `pko`, `calls`, `cascades`, `events` листаются через общие
`offset`/`limit`: отдельного курсора для каждого раздела нет.
`depth_limited` требует повторить трассу с большей глубиной, максимум 10.

- `registration`: открытые ПРО из папки комплекта, в том числе несохранённые, либо соседний
  `RegistrationRules.xml`; для макета — соседний макет «ПравилаРегистрации». Смотрите отборы,
  `disabled`, `Валидное`, `РеквизитРежимаВыгрузки`. Режим узла неизвестен статическому серверу:
  значение его реквизита берётся из базы, а не из правил (РЕГ:309–311). Правило без `Валидное`
  или с `Отключить` загрузчик пропускает (РЕГ:282–293).
- `branches`: порядок документа и `first_for_type`. Это первая включённая ветка при условии,
  что тип входит в состав плана: выбор через `Найти` берёт первую строку
  (БСП:6768, БСП:17931, БСП:18361–18367). Без структуры `plan_membership="unknown"`.
  При произвольном способе отбора и `ВыборкаДанных` смотрите уже существующие замечания
  `handlers.pvd_arbitrary`, `handlers.pvd_selection`: обмен через план читает изменения узла
  (БСП:18173, БСП:18210–18236), а не произвольную выборку ПВД.
- `calls`: адрес, обработчик, `file` и `line`; цепочка `chain` даёт строку обращения к алгоритму
  и строку вызова внутри него. Это узлы DAG с `id`/`next`, общие пути объединены;
  `callers` перечисляет адреса вызывающих правил. `kind="field"` — поле правила,
  `branch_properties` — выбор по свойствам ветки, а не строка BSL (БСП:6977–6997).
  По умолчанию используется последнее ПКО типа в файле: загрузчик перезаписывает менеджер
  и не читает `Отключить` ПКО (БСП:5845, БСП:6947). Флаг группы ПКО/ПВД не выключает
  дочернее правило (БСП:6768, БСП:6868–6882). Комментарии и отключённые ПКС
  не становятся вызовами. Это статические места вызовов, исполнение условной ветки не доказано.
  `type_lookup` — ПКС без кода ПКО, чей атрибут `Тип` источника позволяет выбрать последнее
  ПКО типа (БСП:12908, БСП:12985–12991, БСП:13131–13158). Проверяйте такие связи и в каскадах:
  отсутствие кода у ПКС само по себе не означает недостижимость ПКО. В общем алгоритме трасса
  оставляет маршруты из обработчиков текущих объектов; чужие вызывающие не добавляются.
- `pko.validation_evidence` — места вызовов общего графа проверок и трассы, с полными адресами
  ПКС. Простое упоминание кода в комментарии, запросе или сообщении вызовом не считается.
  `reference_only` и `cascades.validation_mode` используют тот же граф `structure.pko_ref_only`: ПКС передаёт
  ссылку, если обработчик не потребовал объект целиком (БСП:12784, БСП:12822, БСП:12924–12949).
  Только свойства поиска попадают в узел ссылки; прочие свойства ПКО тогда не выполняются
  (БСП:790–826, БСП:13170–13196). Режим регистрации способен потребовать полный объект
  (БСП:3393–3437), поэтому `registration_override="unknown"` требует сверки с узлом.

Код читайте без экспорта: `handlers_read(project_id, address, handler, offset=0, limit=50)`.
`line` совпадает со строкой обёртки `handlers_export`; `handler_line` — строка тела с единицы.
После изменения снимка повторите экспорт перед сопоставлением с прежним результатом синтакс-чекера.
`handlers_search(project_id, query="ВыгрузитьПоПравилу", kind="substring")` ищет по всем
обработчикам, алгоритмам и общим событиям; `kind="regex"` включает регулярное выражение.
Регистр букв не учитывается; `rule` — точный адрес (с дочерними ПКС), `handler` — точное имя обработчика.
Поисковое выражение ограничено 256 символами; жёсткого тайм-аута регулярных выражений нет.

Для запроса в найденном обработчике:
`handlers_queries(project_id, address, handler)` либо `handlers_queries(project_id, file=...)`.
Ответ содержит части пакета с индексами с нуля, `temporary_tables`, зависимости `dependencies`,
параметры с выражениями и строками, `executions` и обращения `results`.
`complete=false` означает динамический или повреждённый текст; причина возвращается явно.
Для `Запросы.<Имя>` текст берётся из раздела правил «Запросы», имя сохраняется в `query_name`.
Если текст присваивается в нескольких ветках, общие параметры и выполнение привязаны ко всем
вариантам, причина неполноты — `branching_text`. Аргументы `СтрЗаменить` и других построителей
не выдаются за части запроса. Произвольный `.Текст` сообщения не считается запросом.
Один текст внутри `Если` остаётся полным; несколько вариантов `Попытка/Исключение` объединяются
так же, как `Если/Иначе`. Обращение к общей переменной результата после ветвления связывается
с выполнениями обеих веток. Явная выгрузка по правилу из обработчика ПКС по умолчанию требует
целый объект, в отличие от обычной передачи значения ПКС (БСП:321–330, БСП:12784, БСП:12822).
Строковые фрагменты не заменяют полный запрос, `undefined` не заменяйте догадкой об индексе.
Это чтение синтаксиса без исполнения BSL и запросов; ни результат запроса, ни фактический маршрут
объекта в базе этим не подтверждаются. Ревью завершается отчётом и перечнем непроверенного.

## Дефект или особенность

| Находка | Вывод | Почему |
|---|---|---|
| `format.*` уровня «ошибка»: повтор кода ПКО, имени алгоритма, висячий `КодПравилаКонвертации` | дефект | повтор перезаписывает первое правило (стр. 6135, 6467), висячая ссылка — протокол 45 и флаг ошибки (стр. 341–349) |
| `structure.pko_target`, `structure.pks_target` на объектах, которых нет в структуре приёмника | расхождение конфигураций, не дефект правил, пока не проверено на выгрузке настоящего приёмника | подмена или другая версия приёмника (`checks.md`, §3); тип источника, которого нет у отправителя (`structure.pko_source`), — наоборот, ошибка 11 при чтении правил (стр. 5847–5850) |
| `structure.pkz_coverage` | дефект при выгрузке такого значения, обычно не к текущей задаче | значение без ПКЗ — ошибка 71 (стр. 748–764) |
| ссылочное ПКС без `КодПравилаКонвертации` и без ПКО для типа (`structure.pko_missing`) | дефект | значение молча не уходит, протокол пуст (стр. 13154–13162) |
| ПКО справочника без свойств поиска и без синхронизации по идентификатору | дефект | `<Ссылка>` не пишется, приёмник каждый раз создаёт новый объект (стр. 788–791, 10617–10671) |
| флаги ПКО, которые БСП не исполняет (`ВыгружатьОбъектТолькоПриНаличииНаНегоСсылки`, `ИспользоватьБыстрыйПоискПриЗагрузке`, …) | особенность; дефект, если на флаг рассчитана логика | веток чтения нет или значение не используется (стр. 5751–6037; `pko.md`, «Флаги КД, которые БСП 3.1.12 не исполняет») |
| ПКО без `НеЗамещать`, у его ПКС — `НеЗамещать` (рецепт `pko.md`, «у найденного объекта обновлять только новое свойство») | особенность с риском; дефект, если среди ПКС без флага есть свойства, которые заполняют в приёмнике | найденный объект целиком пропускается только при `НеЗамещать` у ПКО (`ПрочитатьОбъект`, стр. 10780–10785, 10829–10834), иначе пишется при каждом приходе; у найденного пропускаются только свойства с флагом (стр. 10677, 10686–10693), остальные получают значение из сообщения без проверки на пустоту (стр. 10711) — пустое в источнике затирает заполненное в приёмнике |
| `Отказ` в `ПередОбработкойПравила` ПВД, `Отключить` у группы ПВД | дефект, если на них рассчитан отбор | не проверяются в обмене через план (стр. 18369–18404, 6868–6888) |
| ПОД с обработчиками | особенность, мёртвый код | ПОД в обмене БСП не выполняются (стр. 7409–7430) |
| алгоритм вызывается не в своей фазе (`algorithm.wrong_mode`) | дефект | при выгрузке видны только алгоритмы без `ИспользуетсяПриЗагрузке`, при загрузке — только с ним (стр. 6455–6469) |
| ПРО без `Валидное="true"` или с `Отключить="true"` | дефект, если правило нужно | такие правила читатель не загружает (РЕГ, стр. 282–293) |
| запись в базу в выгрузочном обработчике | дефект | выгрузка меняет источник; при ошибке выгрузки транзакция откатывается (стр. 18515–18521) (вывод) |
| запрос в цикле, реквизиты через точку в обработчиках ПКО и ПКС | замечание к производительности | обработчик ПКО выполняется на каждый выгружаемый объект и ссылку (`ВыгрузитьПоПравилу`, стр. 557–595), цена умножается (вывод); `handlers.md`, «Стандарты кода для обработчиков» |
| правила корреспондента приёмника расходятся с правилами отправителя | дефект | загрузку исполняет копия в приёмнике (`ОбменДаннымиСервер`, стр. 10001–10083; `handlers.md`, «Где лежат правила загрузки») |

## Форма отчёта

- **Что проверено:** файлы и их источник (путь, коммит), `project_id`, структуры (идентификатор, откуда,
  расширения), какие ступени лестницы прогнаны (`checks.md`) — непрогнанная не пройдена.
- **Итог `rules_validate`:** `by_check`; каждая ошибка — адрес, вывод (дефект / расхождение / особенность),
  причина. Предупреждения `structure.pko_unreachable` и `structure.pko_ref_only` — обязательно своими словами:
  что это значит для обмена (объект не выгружается сам; уходит только ссылкой — работают лишь поля поиска),
  какие ПКО из них классификаторы, которые приёмник находит по полям поиска (это штатно), и какой выход у
  остальных (ПВД и правило регистрации, объект в составе плана; либо `ВыгрузитьОбъект = Истина` в
  `ПередВыгрузкой` ПКС). Человек не читает идентификаторы проверок.
- **Дефекты:** адрес правила (`ПКО X`, `ПКО X / ПКС Y`), что не так, чем доказано, как исправить, чем грозит
  живому обмену. У каждого дефекта ссылка обязательна: процедура и строки БСП (из таблицы выше, скилла
  `kd2-exchange-pitfalls` или выгрузки конфигурации, где правила исполняются) или строка файла правил; к ней —
  проверка `rules_validate` или обмен в песочнице, если были. Без ссылки — не дефект, а подозрение.
- **Особенности:** что работает не так, как в КД, но обмену не мешает.
- **Не проверено и почему:** нет структуры приёмника, синтакс-чекера (или он не прогонялся — причина), песочниц,
  правил корреспондента, данных песочницы (нет согласия человека).
