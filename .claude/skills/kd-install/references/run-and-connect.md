# Шаги 5–6: запуск и подключение агента

## 5. Запуск

**Образ.** Выбранная версия без `v` вместо `X.Y.Z`; в `projects.local.yaml` — абсолютные пути хоста.

```powershell
docker run --rm -v "${PWD}:/work" ghcr.io/egordoronchenko/kd-rules-mcp:X.Y.Z setup
docker compose pull
docker compose up -d --no-build
docker compose exec -T kd-rules-mcp python scripts/check_server.py http://127.0.0.1:8060/mcp
```

Для sh: `docker run --rm --user "$(id -u):$(id -g)" -v "$(pwd):/work" ghcr.io/egordoronchenko/kd-rules-mcp:X.Y.Z setup`.
Для cmd: `-v "%cd%":/work`. Без `--user` файлы на Linux принадлежат root: setup предупреждает;
с `--user` — указанному uid. Проекты вне `/work` подключить также в setup томами только для чтения,
например `-v "D:/Repos/bp:/inputs/bp:ro"`, и передать `--project-mount bp=/inputs/bp`:
это позволяет собрать их MCP и логины; override сохранит хостовый путь `D:/Repos/bp`.
Без дополнительных томов setup предупреждает о недоступных внешних настройках; существование
`rules_dir` и `writable_extensions` проверить на хосте до up. Рабочая папка должна быть доступна uid 1000 сервера.
Команда проверки через exec выше — для локальной установки без `token`; при токене проверить MCP
в клиенте после одобрения. Одноразовой подкоманды `check` нет: loopback должен относиться к работающему серверу.

**Клон.**

```powershell
uv run python scripts/setup_local.py
docker compose up -d --build
uv run python scripts/check_server.py
```

Проверка: `setup_local.py` печатает контейнер, порт и том — те, что задумали на шаге 4; `check_server.py`
печатает число инструментов (полный список — `docs/tools.md`) и «папка видна» у каждого проекта; код выхода 0.
Первая сборка образа — пара минут. Поменяли `port`, `instance` или `bind` позже — снова `setup_local.py` и
`docker compose up -d`.

## 6. Подключить агента

Для пути образа: скачать ZIP **того же релиза** `kd-rules-mcp-skills-claude-X.Y.Z.zip` или
`kd-rules-mcp-skills-agents-X.Y.Z.zip` (одну упаковку). После согласия на правку проекта перенести
`.claude/skills` либо `.agents/skills` и `KD-RULES.md` (agents). В `.mcp.json` объединить только
запись `kd-rules-mcp` с существующими серверами, указать свой `server_url` и заголовок при токене;
файл целиком из ZIP не заменять. Для Cursor аналогично `.cursor/mcp.json`. Проверка: файлы
скиллов и запись своего сервера есть, затем перезапуск клиента и первая загрузка как ниже.
Скрипт `build_packs.py --dest` ниже — альтернатива из клона.

Клиент читает `.mcp.json` только при запуске: **в этой сессии инструментов `kd-rules-mcp` не будет**. Не искать
их и не вызывать сервер в обход клиента (правило «Инструменты сервера — только через клиент»): сервер в этой
сессии уже проверен `check_server.py` шага 5.

- **В папке этого репозитория** `.mcp.json` и `.cursor/mcp.json` уже записал `setup_local.py`. Сказать человеку:
  перезапустить `claude` в папке и разрешить серверы (проверка — `claude mcp list`: `kd-rules-mcp … Connected`),
  в Cursor — включить сервер в настройках MCP.
- **В папке проекта 1С** (спросить, нужно ли: это правка чужого репозитория) — из папки сервера:

  ```powershell
  uv run python scripts/build_packs.py --dest <папка проекта> --client claude
  ```

  Ставит скиллы сервера (имена `kd-`, `kd2-` или `kd3-`) в `.claude\skills\` проекта (их читают Claude Code, Cursor и OpenCode) вместе со
  справочниками и правилом серверов 1С, добавляет `kd-rules-mcp` в `.mcp.json` проекта (и в `.cursor\mcp.json`,
  если он есть), чужие серверы не трогает; адрес — `server_url` из `projects.local.yaml` (другой —
  `--server-url`). Человек работает в Cursor — добавить `--cursor`: Cursor `.mcp.json` проекта не читает, и
  скрипт создаёт `.cursor\mcp.json` (если его нет) с `kd-rules-mcp` и переносит в него HTTP-серверы 1С из
  `.mcp.json` проекта; stdio-серверы он только перечислит — человек добавляет их сам в настройках MCP Cursor
  (передать ему список). `.cursor\mcp.json` уже был — с `--cursor` скрипт дописывает в него недостающие
  HTTP-серверы 1С и не меняет существующие записи; без флага не переносит их и сообщает, каких серверов 1С
  в файле нет. Без флага и без файла человек добавляет сервер сам в настройках MCP Cursor (сказать ему).
  Клиент, который `.claude\skills` не читает (Codex), — `--client agents`: скиллы в
  `.agents\skills\`, в корне проекта `KD-RULES.md` — порядок работы и какой файл когда читать; строку о нём в
  `AGENTS.md` проекта добавляет человек (скрипт её напечатает). Обе упаковки в один проект не ставить — Cursor и
  OpenCode увидят скиллы дважды; скрипт откажет. Проект должен быть в `projects.local.yaml` (шаги 4–5).
  Проверка: скрипт печатает число файлов упаковки и «kd-rules-mcp добавлен» (или «уже подключён»).

Затем **закончить ход**: сказать, что и куда поставлено, и попросить человека перезапустить клиент в нужной папке
(проекта 1С или этого репозитория) и одобрить сервер `kd-rules-mcp`. Работа с правилами — тоже после перезапуска.

Итоговая проверка — **в начале следующей сессии**, после одобрения (в `docs/INSTALL.md` это «первая задача —
проверка всей цепочки»): вызвать инструменты сервера `project_list`, затем `structure_load_project` для одного
проекта. Ответ с числом объектов — установка готова. Первая загрузка большой конфигурации — до пары минут.
