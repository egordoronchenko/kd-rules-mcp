# Перенос правил регистрации с плана обмена КД 2 на план универсального формата

Читать, когда обмен переводят с правил «Конвертации данных 2» на универсальный формат и нужно, чтобы объекты
попадали в очередь на отправку по тем же условиям, что и раньше (дата начала, организации, флаги узла, код
обработчиков регистрации). Правила конвертации при этом переносятся отдельно (`writer.md`); здесь — только
регистрация изменений.

Параметры и ответы инструмента — `kd2-rules-build/references/tools.md`, раздел «Retargeting registration rules».
Строки ниже — БСП 3.1.12; в другой версии сверь по выгрузке конфигурации.

## Почему это вообще возможно

- **Исполнитель правил регистрации один для всех планов обмена.** `ОбменДаннымиСервер.ПолучитьПравилаРегистрацииОбъектов`
  (стр. 8326–8382) собирает общую таблицу из записей регистра `ПравилаДляОбменаДанными`: правила из файла или
  макета хранятся уже зачитанной таблицей, правила из менеджера регистрации заполняются вызовом его модуля. Дальше
  исполняются одинаково. Поэтому файл `ПравилаРегистрации` формата КД 2 можно загрузить и для плана
  универсального формата.
- **Но не как есть.** Загрузчик сверяет имя плана в файле с планом, для которого загружают
  (`ЗагрузкаПравилРегистрацииОбъектов.ВыполнитьПроверкуНаличияПланаОбмена`, стр. 983–988), а отборы по свойствам
  узла ссылаются на реквизиты узла **старого** плана — у нового плана они называются иначе или отсутствуют.
- **Запись правил относится к плану, а не к узлу** (`ПравилаДляОбменаДанными.ЗагрузитьПравилаРегистрацииОбъектов`,
  модуль менеджера регистра, стр. 249–286). Загруженный файл заменяет правила регистрации для всех узлов плана.

## Порядок работы

1. **Открыть правила регистрации** действующего обмена: `rules_open` файла `ПравилаРегистрации`. Если правила
   взяты из макета конфигурации — тот же текст лежит в макете плана обмена в выгрузке.
2. **Узнать реквизиты узлов обоих планов**: `structure_object` плана старого и нового (структура из XML-выгрузки
   конфигурации). Составь отображение «реквизит узла старого плана → реквизит узла нового». Ключи: `Имя` — реквизит
   шапки, `[ТабличнаяЧасть]` — табличная часть, `[ТабличнаяЧасть].Имя` — её реквизит.
3. **`registration_retarget` в режиме `preview`.** Ответ: сколько правил и отборов затронуто, неприменённые ключи
   отображения, замечания, список файлов комплекта.
4. **Разобрать замечания:**
   - *реквизита нет у нового плана* — либо ты ошибся в отображении, либо у нового плана такого реквизита
     действительно нет. Во втором случае его добавляет расширение: передай `own_attributes` и `extension`
     (сейчас — только булев реквизит шапки). Табличную часть, реквизит-дату, режим выгрузки расширение из комплекта
     не добавляет — такой отбор остаётся блокирующим: решай с человеком, что с ним делать;
   - *тип не подходит* — отбор сравнивает реквизит с значением другого типа; после загрузки такое правило либо
     ломает запись объектов, либо молча перестаёт регистрировать. Исправляется отображением, не подтверждением;
   - *старое имя в коде* — обработчик правила регистрации или алгоритм значения обращается к старому плану или
     реквизиту по имени. Сервер код не переписывает: прочитай место, реши, что с ним делать, и только потом
     подтверждай. С таким подтверждением в начале инструкции комплекта появится блок «Перенос неполон».
5. **`write`** с `expected_preview_hash` и подтверждениями. Комплект — в рабочей папке сервера: файл правил,
   расширение (если нужны свои реквизиты), инструкция. Исходные правила не меняются.
6. **Отдать человеку** комплект. В инструкции — порядок (сначала расширение, потом настройки узлов, потом файл
   правил), как вернуть прежнее состояние и чем проверить.

## Что сказать человеку — это не очевидно

- **После загрузки файла настройки узла «что отправлять» перестают управлять регистрацией.** В типовых
  конфигурациях правила регистрации плана универсального формата привязаны к режимам отправки документов и
  справочников узла (посмотри отборы типовых правил — `rules_open` макета правил регистрации плана); в
  правилах КД 2 таких условий нет. Регистрацией управляют перенесённые правила — так и должно быть при переносе
  «как было», но человек должен об этом знать.
- **Дату начала и отбор по организациям нельзя просто записать в узел.** В типовых конфигурациях модуль объекта
  узла плана универсального формата при записи сам пересчитывает эти поля по настройкам «правила отправки» и
  стирает записанное напрямую (прочитай обработчик «перед записью» в модуле объекта плана своей конфигурации).
  Значения переносят выбором этих настроек (инструкция комплекта описывает как); после записи узла — проверить,
  что они остались.
- **Правило, отключённое в файле, не действует** (загрузчик его пропускает,
  `ЗагрузкаПравилРегистрацииОбъектов`, стр. 282–286), а объект без правила регистрации регистрируется **на всех
  узлах плана** (`ОбменДаннымиСобытия`, стр. 1598–1611). Перенос «как было» сохраняет отключённое правило
  отключённым — не «чини» его по дороге.
- **Если по плану идут другие обмены**, новые правила заменят регистрацию и для них. Спроси, прежде чем
  собирать.
- **Возврат** зависит от того, откуда правила брались раньше — из макета или из менеджера регистрации; команда
  «использовать типовые правила» всегда выбирает макет. Инструкция комплекта описывает оба случая.

## Чего сервер не проверяет

Комплект в базу не ставится, код обработчиков не исполняется. «Записано без замечаний» значит: имена реквизитов
узла существуют у нового плана (или их добавит расширение), типы сравнений совместимы, старых имён в коде нет
или они подтверждены. Что объект действительно попадает в очередь нужного узла и не попадает в лишний —
показывает только проверка обычной записью объекта в тестовой базе (шаг 5 инструкции комплекта). В отчёте
человеку «проверено сервером» и «проверено в базе» не смешивай.
