# Приёмы доработки обмена через универсальный формат: что на самом деле делает исполнитель
Читать, когда задачу нельзя решить прямым свойством: свой поиск объекта, отказ от загрузки, проведение
документа, данные вне формата, один объект формата в несколько объектов базы, поведение по варианту настройки.

Приёмы взяты из практики доработки типовых синхронизаций и сверены с исполнителем: ссылки `XDTO:N` и остальные
обозначения — как в `executor.md` (БСП 3.1.12). Всё прочитано по коду, обменом не проверено, если не сказано
иначе. Ниже — **обычный путь** получения; объектная конвертация узла ведёт себя иначе, это оговорено в каждом
разделе.

## 1. Порядок получения одного объекта (обычный путь)

`СтруктураОбъектаXDTOВДанныеИБ`, XDTO:1802–2100:

1. В сообщении есть ссылка и вариант идентификации с УИД — объект ищется через регистр публичных
   идентификаторов, затем по УИД; найденный **сразу** читается из базы (XDTO:1815–1822).
2. Первый этап: прямые ПКС и прямые ПКТЧ (XDTO:1856) → `ПриКонвертацииДанныхXDTO` (XDTO:1869) → второй этап
   (XDTO:1879).
3. Объект по УИД не найден и вариант идентификации с полями поиска — поиск по полям, затем `АлгоритмПоиска`
   (XDTO:1892–1937).
4. Полная загрузка и есть обработчик — `ПередЗаписьюПолученныхДанных` (XDTO:1962–1980).
5. Что писать: `ДанныеИБ` не найден — пишется `ПолученныеДанные`; найден — `ПолученныеДанные` переносятся в
   `ДанныеИБ`, пишется он; оба `Неопределено` — выход без записи и без ошибки (XDTO:1984–1995).
6. Публичный идентификатор записывается до записи объекта (XDTO:2001); запись, для документа — отдельная ветка
   (XDTO:2034–2098).
7. После всего сообщения — удаления, `ПослеЗагрузкиВсехДанных`, отложенное проведение и отложенная запись,
   **только если не взведён `ФлагОшибки`**: одна ошибка по любому объекту отменяет эти шаги для всего сообщения
   (XDTO:2172–2221, 7592–7594).

## 2. Свой поиск объекта — событие ПКО `АлгоритмПоиска`

- **Когда вызывается** (XDTO:1892–1916): объект не найден по УИД, правило не регистр, вариант идентификации —
  «по полям поиска» или «сначала по УИД, потом по полям поиска». Вызывается после поиска по полям при любом его
  результате; сами поля поиска могут быть пустыми — решает вариант идентификации. При варианте «по УИД» и для
  объекта, уже найденного по УИД, **не вызывается**.
- **Параметры** (XDTO:8697–8703): `ДанныеИБ` (ссылка, найденная по полям, или `Неопределено`),
  `ПолученныеДанные`, `КомпонентыОбмена`. `ДанныеXDTO` не передаётся — всё нужное для поиска должно уже лежать в
  `ПолученныеДанные`.
- **Что вернуть:** найденную **ссылку** в `ДанныеИБ` — дальше исполнитель сам вызывает `ПолучитьОбъект()`
  (XDTO:1918–1935). Ошибка в обработчике перевыбрасывается (XDTO:8707–8722).
- Вызывается и для объекта, пришедшего только ссылкой (значением свойства), при вариантах с полями поиска.
- **Объектная конвертация** это событие не вызывает вообще: там поиск только по ключевым полям.
- Обработчику нужна ветка диспетчера, как любому другому (`pitfalls.md`, п. 1).

## 3. Отказ от загрузки объекта («не создавать, если не найден»)

Настройки ПКО «не создавать новый объект» в правилах нет: в таблице правил такой колонки нет (XDTO:3254–3286).
Делается обработчиком `ПередЗаписьюПолученныхДанных`:

- **Не создавать новый:** `Если ДанныеИБ = Неопределено Тогда ПолученныеДанные = Неопределено; КонецЕсли;` —
  для нового объекта этого достаточно (XDTO:1984–1995).
- **Не трогать найденный:** обнулить **оба** — `ПолученныеДанные` и `ДанныеИБ`. Если обнулить только
  `ПолученныеДанные`, найденный объект всё равно запишется: с него **снимается пометка удаления**
  (XDTO:2028–2032), проведённый документ распроводится и встаёт в очередь отложенного проведения (п. 4), объект
  получает публичный идентификатор и попадает в отложенное заполнение. Распространённый рецепт «загрузка только
  новых: обнулить `ПолученныеДанные` у найденного» поэтому неполон.
- **Обнулить только `ДанныеИБ`** — запишется `ПолученныеДанные` как новый объект: при поиске по полям это дубль.
- При отказе публичный идентификатор не пишется, ошибки нет, обмен продолжается.
- **Ссылки на отказанный объект** из других объектов сообщения разрешаются независимо от отказа: при варианте «по
  УИД» получится ссылка без объекта, при вариантах с полями поиска объект будет создан из ключевых свойств
  (`pitfalls.md`, п. 3). Если отказываемый объект уже был создан по ссылке раньше в этом сообщении, исполнитель
  удаляет его до вызова обработчика (XDTO:1965–1972) — после отказа ссылки на него битые.
- **В `ПриКонвертацииДанныхXDTO` штатного отказа нет:** `ПолученныеДанные = Неопределено` там даёт исключение на
  втором этапе, ошибку по объекту и `ФлагОшибки` для всего сообщения.
- При **отправке** штатный отказ — `ДанныеXDTO = Неопределено` в `ПриОтправкеДанных` (XDTO:1259–1261).
- Объектная конвертация: отказ (оба `Неопределено`) фиксируется как отказ (КОС:243–248).

## 4. Проведение документа при получении

Распространённый совет «выставить `Проведен = Истина`, чтобы документ записался проведённым без отложенного
проведения» **неверен**. Если у объекта для записи `Проведен = Истина`, исполнитель сбрасывает его в Ложь,
записывает документ (у уже проведённого — отменяет проведение) и ставит в очередь **отложенного** проведения
(XDTO:2040–2060). `Проведен = Ложь` — документ записывается непроведённым, существующий проведённый —
распроводится (XDTO:2062–2072).

- `Проведен = Истина` — это и есть запрос отложенного проведения; другого способа провести документ исполнителем
  нет.
- Отложенное проведение выполняется после всего сообщения и только без `ФлагОшибки` (п. 1, шаг 7); если
  проведение упало, ошибка регистрируется, документ остаётся записанным и непроведённым.
- У найденного объекта `Проведен` переносится из `ПолученныеДанные`, только если на это поле есть ПКС; иначе
  значение задаёт обработчик.
- Объектная конвертация: новый проводимый документ проводится сразу, независимо от `Проведен`.

## 5. Данные вне формата — `AdditionalInfo`

- Свойство объявлено не в пакете формата, а в пакете сообщения обмена, у базового типа объекта; большинство типов
  объектов формата его наследуют, но не все — проверяй конкретный тип (`ed_schema_type`).
- **Отправка:** значение кладётся в `ДанныеXDTO.AdditionalInfo` в `ПриОтправкеДанных`, сериализуется платформой;
  пустое не уходит (XDTO:986–993, 1031). С объектом, выгружаемым только ссылкой, не уходит: передаются лишь
  ключевые свойства (XDTO:1263–1268).
- **Получение:** читается в `ДанныеXDTO.AdditionalInfo` (XDTO:6232–6235); доступно в `ПриОбработке` ПОД и в
  `ПриКонвертацииДанныхXDTO`. В `АлгоритмПоиска` и `ПередЗаписьюПолученныхДанных` недоступно — туда `ДанныеXDTO`
  не передаётся: нужное переложи в `ПолученныеДанные` или их дополнительные свойства на этапе конвертации.
- Типовая практика: структура с простыми значениями и таблицами, идентификаторы объектов — строкой, а не
  ссылкой. Какие типы переживут сериализацию и что станет со ссылками — поведение платформы, по коду не
  проверено.

## 6. Один объект формата — несколько объектов базы

Обработчик `ПриКонвертацииДанныхXDTO` сам ищет, создаёт и пишет объекты; стандартную запись основного объекта
отключают в `ПередЗаписьюПолученныхДанных` (п. 3; в самом `ПриКонвертацииДанныхXDTO` отключить нельзя). Цена
приёма по коду исполнителя — объекты, записанные обработчиком сами:

- не получают публичного идентификатора (он пишется только основному объекту, XDTO:2001) — повторная загрузка
  того же объекта без собственного поиска даёт дубли;
- не попадают в отложенное заполнение и отложенное проведение, пока обработчик сам не добавит их в
  `КомпонентыОбмена.ДокументыДляОтложенногоПроведения`;
- не входят в общую транзакцию: транзакции на сообщение нет, каждая запись — своя;
- пишутся без режима загрузки от узла-отправителя, если писать их в обход процедуры записи исполнителя
  (XDTO:2612–2653) — регистрация к выгрузке и проверки при записи сработают как при обычной записи (вывод);
- удаление объекта формата удаляет только основной объект.

Прежде чем применять — проверь, нельзя ли обойтись отдельным ПКО на каждый результат (у ПОД несколько
`ИспользуемыеПКО`).

## 7. Поведение по варианту настройки и версии формата

- **Вариант настройки** узла в `КомпонентыОбмена` отдельным ключом не лежит. Есть `УзелКорреспондента` и, только
  при получении, `УзелКорреспондентаОбъект`. Типовые способы: прочитать реквизит узла в `ПередКонвертацией` и
  положить в `ПараметрыКонвертации`; либо читать `УзелКорреспондентаОбъект.<реквизит>` с проверкой на
  `Неопределено`.
- **Версия формата** в обработчике — `КомпонентыОбмена.ВерсияФорматаОбмена`: при получении — из сообщения, при
  отправке — из узла (`executor.md`, §1).
- **ПОД `ПриОбработке`** управляет набором правил через структуру `ИспользованиеПКО` (`executor.md`, §3). При
  **получении** значение `Ложь` для ПКО с синхронизацией по УИД — не «пропустить», а **удалить или пометить на
  удаление** существующий объект (XDTO:7486–7497). Пропустить без удаления — убрать ключ из структуры. Параметра
  отказа у обработчика нет: объект пропускается только из-за исключения, а оно взводит `ФлагОшибки`.

## 8. Удаление и пометка удаления

**Правило для любого обмена, который ты строишь или переносишь: физического удаления в обмене нет.** Удалённый
на источнике справочник на получателе помечается на удаление; документ — распроводится и помечается на удаление.
Так уже работает исполнитель — твоя задача не сломать это и честно назвать границы человеку.

**Физическое удаление на получателе — только по отдельному прямому подтверждению человека.** Если человек
просит, чтобы объекты на получателе удалялись физически (или чтобы удаление обходило закрытый период, шло для
проведённых документов без отмены проведения и т. п.), не делай этого по общей формулировке задачи. Задай
отдельный вопрос именно про это действие и назови последствия: удалённое не восстановить, на объект могут
ссылаться другие данные получателя, движения документа исчезнут, закрытый период изменится. Строй только после
явного «да» на этот вопрос; согласие на перенос обмена «как было» или на «сделай всё» таким подтверждением не
считается. В отчёте запиши: что сделано по прямому решению человека, его формулировку и что это отступление от
правила.

Что делает исполнитель при получении информации об удалении (после всего сообщения и только без `ФлагОшибки`,
XDTO:2172–2178):

- объект, пришедший в том же сообщении обычным изменением, из списка удаляемых исключается; отсутствующий в базе —
  пропускается (`ПрименитьУдалениеОбъектов`, XDTO:3455–3498);
- **закрытый период:** если загрузка объекта запрещена датой запрета, объект не трогается — ни отмены
  проведения, ни пометки (`ПриУдаленииОбъекта`, XDTO:8734–8741; отказ — переход к следующему объекту, XDTO:3475–3480). Обмен при этом не падает; расхождение «в
  источнике удалён, в получателе живой и проведён» остаётся, пока период закрыт. Скажи это человеку заранее;
- у проведённого документа отменяется проведение; если отмена не удалась — пометка **не** ставится, документ
  остаётся как был (XDTO:8751–8772);
- затем ставится пометка удаления, физически объект не удаляется (вызов с `УдалитьНепосредственно = Ложь`,
  XDTO:8779; `УдалитьОбъект`, XDTO:7962–8002); предопределённые элементы не помечаются (XDTO:7988–7995);
- событие менеджера `ПередОбработкойУдаляемогоОбъекта` вызывается до этого, но исключение в нём проглатывается
  (XDTO:8743–8748) — проверку, которая должна остановить удаление, туда класть нельзя.

Границы, о которых надо знать до того, как обещать:

- **Объект собственного типа формата** (тип из расширения формата, не из типового пакета): информация об его
  физическом удалении **не отправляется вовсе и без ошибки**. Отправитель пишет удаление, только если тип ссылки
  есть среди ссылок типового `УдалениеОбъекта` (`ЗаписатьУдалениеОбъектаXDTO`, XDTO:5488–5510); для своего типа
  цикл просто заканчивается. Не строй обходов сам — скажи человеку: для таких объектов передаётся только пометка
  удаления, а физическое удаление на источнике получатель не увидит.
- **Пометка удаления обычным изменением прямой ПКС не переносится.** При записи полученного объекта исполнитель
  сам снимает пометку (XDTO:2030–2032), проведение документа обрабатывает отдельно (п. 4). ПКС на реквизит
  `ПометкаУдаления` в правиле получения ничего не даст: объект придёт непомеченным.
- **Как передать пометку удаления: превратить её в штатное удаление на отправке.** В `ПриОбработке` ПОД отправки
  для помеченного объекта выставь `Ложь` всем ключам `ИспользованиеПКО` — исполнитель вместо объекта выгрузит
  информацию об удалении, а получатель обработает её как описано выше: дата запрета, отмена проведения, пометка.
  Обработчики на получателе не нужны. Условия и последствия, все из кода:
  - у ПОД должно быть **не меньше двух** ПКО в `ИспользуемыеПКО` и включён признак выгрузки очистки данных
    (`ОчисткаДанных`, если колонка есть в таблице ПОД): с одним ПКО удаление не выгружается, объект просто
    молча не уходит (XDTO:791–792, 805–814);
  - на получателе удаление применяется только для правил с идентификацией по УИД или «сначала по УИД, потом по
    полям» (XDTO:7945–7957); у правила с поиском только по полям удаление молча пропускается;
  - пока объект помечен, его остальные изменения не уходят — уходит только удаление;
  - сняли пометку на источнике — объект снова уйдёт целиком, получатель снимет пометку сам (XDTO:2030–2032), но
    проведение документа вернётся, только если правило его переносит (п. 4);
  - для объекта собственного типа формата приём не работает по причине из предыдущего пункта.
- **Не ставь пометку сам в `ПередЗаписьюПолученныхДанных`.** Проверка даты запрета загрузки стоит после этого
  обработчика (вызов — XDTO:1975, проверка — XDTO:2018–2028): объект, записанный или помеченный в обработчике,
  пройдёт мимо неё и изменит закрытый период. Свой обработчик состояния на получателе — только если приём выше
  не подходит, с собственной проверкой запрета и живым обменом: пометка, снятие пометки, проведённый документ,
  документ в закрытом периоде. Сервер такой обработчик не порождает и не проверяет.
- **Перенос с КД 2.** В правилах КД 2 ту же политику обычно задаёт обработчик конвертации
  `ПриПолученииИнформацииОбУдалении` (пометка вместо удаления). В универсальном формате его переносить не нужно —
  это поведение исполнителя; переносить нужно только то, что обработчик делал сверх пометки и отмены проведения.

В отчёте человеку по удалению — три строки: что произойдёт с удалённым на источнике объектом каждого вида; что
произойдёт в закрытом периоде; для каких объектов удаление не передаётся.
