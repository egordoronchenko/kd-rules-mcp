# Доработка обмена расширением: свой реквизит в существующем объекте

Сервер умеет одну доработку обмена через универсальный формат: добавить **прямое правило конвертации свойства
шапки** в существующее правило объекта — так, чтобы типовой модуль не менялся. Он выпускает расширение
конфигурации: заимствованный модуль менеджера обмена с перехватчиком `&После("ЗаполнитьПравилаКонвертацииОбъектов")`
и, если реквизит новый, заимствованный объект с этим реквизитом. В базу сервер ничего не ставит.

Чего сервер не порождает: новые ПКО и ПОД, обработчики, табличные части, ссылочные свойства, свои поля формата и
пространства имён, правила регистрации. Попросили такое — скажи человеку, что это правка руками.

## Порядок

1. **Цель.** План обмена, версия формата обмена пары (`executor.md`, §1), направление, ПКО. Обмен между двумя
   базами — **две** доработки: отправка в источнике и получение в приёмнике, у каждой свой проект и свой комплект.
2. **Снимки.** `ed_open` модуля менеджера, `ed_schema_open` пакета выбранной версии, `structure_load_project`
   той же конфигурации — три идентификатора идут в `target` операции вместе с `plan`, `format_version`,
   `direction` (`send` / `receive`), `pko_address`.
3. **`ed_validate`** со схемой и структурой — замечания «до»; критерий доработки — нет новых.
4. **Куда положить значение.** `ed_authoring_candidates(target, kind="format")` — свободные свойства формата типа
   этого ПКО; `kind="configuration"` — свободные реквизиты объекта. Кандидат — не решение: соответствие по смыслу
   и тип нового реквизита предлагаешь человеку ты. Порядок поиска свойства формата — `SKILL.md`, §3.
5. **`ed_authoring_build(mode="preview")`**: `extension` (имя и префикс — у нового реквизита имя начинается с
   префикса), `operations`, `version_scope="manager"`. Ответ `summary` компактный: статус, что изменится,
   замечания «до» и «после» счётчиками, новые замечания, `required_acknowledgements`. Старые замечания модуля —
   разделы `issues_before`, `issues_after`; маршруты — `scopes`.
6. **Прочитай замечания авторинга человеку** (ниже) и получи решение. Затем `mode="write"` с
   `expected_preview_hash` (`build_hash` просмотра) и `acknowledged_notices` — всеми идентификаторами из
   `required_acknowledgements`. Подтверждать за человека нельзя: это его риск.
7. **Отдай комплект**: каталог из `output_dir` ответа (рабочая папка сервера) — `extension/` (выгрузка расширения
   в файлы), `instruction.md`, `modules/` (текст перехватчика для ручной вставки), `manifest.json`,
   `validation.json`.
   Инструкцию не дописывай от себя. `delivery="manual"` — без папки `extension`, для вставки в уже существующее
   расширение проекта.
8. **Установка и проверка в базе** — по `instruction.md`, человеком или тобой в базе роли «песочница» с его
   согласия. Пока не было обмена, в отчёте пишешь «не проверено обменом»: `runtime_verified` в ответе — ложь.
   Обмен одного объекта между двумя песочницами одной командой — скрипт `kdbase/ed_exchange_check.py`, запускается
   из клона сервера (https://github.com/egordoronchenko/kd2-rules-mcp): по файлу случая он проверяет, что
   перехватчик виден при заполнении правил на обеих сторонах, пишет значение, выгружает новое сообщение, находит
   в нём свойство и сверяет значение в приёмнике; провал стадии не превращается в успех следующей.

## Что значит ответ

- **`version_scope="manager"`.** Перехватчик не знает версию обмена: доработка действует во всех версиях формата
  и планах, которые обслуживает этот модуль менеджера, а не только в выбранной. Без этого согласия — отказ.
- **`ed.author.other_version_incompatible`** — в перечисленных версиях у типа нет этого свойства формата. При
  отправке значение в этих версиях просто не передаётся; при получении свойство не приходит. Критерий «нет новых
  замечаний» относится только к выбранной версии.
- **`ed.author.missing_value_clears`** (получение, имена реквизита и свойства разные) — если свойства в сообщении
  нет, реквизит найденного объекта очищается (подтверждено обменом): исполнитель не переносит только те реквизиты,
  чьи **имена** совпали с именами отсутствующих свойств формата (`pitfalls.md`, п. 4–5). Источник при пустом
  значении не пишет свойство вовсе (`pitfalls.md`, п. 16) — для приёмника «очистили в источнике» и «источник без
  доработки» неразличимы. Сохранить прежнее значение прямой ПКС нельзя — нужен обработчик, то есть правка руками.
  Это обычный путь получения. Если у узла включена объектная конвертация, всё наоборот: отсутствующее и пустое
  значение реквизит **не** меняют (`pitfalls.md`, п. 4) — очистить его прямой ПКС там нельзя. Какой путь у узла —
  данные базы, спроси человека.
- **`ed.author.value_range`** — источник шире приёмника (длина строки, разрядность): значение может не поместиться.
- **Отказ `ed_authoring_precondition`** — список `failures` с идентификатором `ed.author.*`: свойство формата уже
  занято другой ПКС, реквизит уже участвует в правиле, ПКО не действует в этом направлении или версии, типы не
  совпадают, чужое расширение перехватывает ту же процедуру, чтение модуля неполно в нужном месте. Это не дефект
  обмена, а граница инструмента: либо меняй решение, либо правка руками.
- **`rebuild: true`** — в каталоге уже лежит комплект, а конфигурация с тех пор изменилась: все операции
  перепроверены на текущих входах. Прежняя операция больше не проходит — отказ с её идентификатором; убрать её из
  комплекта — `drop_operations`, решение человека.
- **`ed_authoring_stale`** — входы изменились между просмотром и записью, или файлы комплекта правили руками:
  перечитай снимки (`ed_close` / `ed_open`) и повтори просмотр.

## Грабли установки (подтверждены на стенде)

- **Безопасный режим.** Расширение, загруженное из файлов конфигуратором, создаётся в безопасном режиме, и
  перехватчик тогда **молча** не действует: применимость и проверка модулей проходят, ПКС не добавляется
  (`pitfalls.md`, п. 12). Режим снимает администратор; значение видно только в новом сеансе.
- **Другое расширение на то же свойство формата.** Перехватчик добавляет ПКС, только если на это свойство формата
  у правила ещё нет ПКС. Если её раньше добавило другое расширение — этот перехватчик молча ничего не сделает.
  Проверяй в базе не число ПКС, а пару «реквизит ↔ свойство формата».
- **Новый сеанс.** Расширение подключается при старте сеанса: после установки и после снятия безопасного режима
  проверяй в новом сеансе, в старом эффекта не будет (`pitfalls.md`, п. 18).
- **Регистрация изменений** комплектом не меняется; регистрируется ли объект при изменении одного только нового
  реквизита — зависит от правил регистрации плана. На стенде элемент справочника при обычной записи
  зарегистрировался на узле сам; для своего объекта проверь это прогоном, а не предположением. Перед таким
  прогоном сними с узла прежнюю регистрацию объекта: без ответных сообщений она не снимается, и объект уйдёт в
  сообщение независимо от последней записи (`pitfalls.md`, п. 17).
- **Повтор того же сообщения** обновление не проверяет (`pitfalls.md`, п. 13): выгружай новое.

## Что проверено обменом, а что нет

Проверено живым обменом между двумя конфигурациями на БСП 3.1.12, версия формата 1.20, менеджеры интерфейса 2:
порождённое расширение отправки загружается конфигуратором без правок; перехватчик добавляет ровно одну ПКС и не
трогает другое направление; повторное заполнение её не задваивает; значение нового строкового реквизита
справочника доходит до того же объекта приёмника без дубля; изменённое значение следующим сообщением обновляет тот
же объект; сообщение без свойства (источник с пустым реквизитом) очищает реквизит приёмника. Не проверено:
менеджеры интерфейсов 1 и 3; новые реквизиты других типов и документов; путь объектной конвертации; права
пользователя обмена на новый реквизит.
