# Грабли обмена через универсальный формат

Симптом → причина → как проверить → что делать. Каждая причина подтверждена кодом исполнителя БСП 3.1.12
(обозначения строк и оговорки — `executor.md`); живым обменом случаи не воспроизводились, если не сказано иное.
Диагноз человеку — с именем процедуры БСП и адресом правила, а не «так устроено».

## 1. Обработчик есть в модуле, но не выполняется

**Причина.** Обработчики правил вызываются через диспетчер модуля менеджера по имени из правила; диспетчер —
цепочка условий без «Иначе». Нет ветки с этим именем — вызова нет, ошибки тоже (`executor.md`, §3).
**Проверить.** `ed_validate` → `ed.handler.missing` (ошибка): адрес правила, событие и имя. Замечание не говорит,
есть ли сама процедура: проверь `ed_list(kind="handler", text=<имя>)` (и `kind="algorithm"`). Ветка есть, а
процедуры нет — `ed.dispatcher.target_missing`.
**Что делать.** Процедура есть — добавить ветку в `ВыполнитьПроцедуруМодуляМенеджера`. Процедуры нет (в типовых
модулях встречается: правило называет обработчик, которого в конфигурации нет) — либо убрать имя из правила, либо
написать и процедуру, и ветку; что из двух задумано, решает человек. В «Конвертации данных 3» ветки пишет
генератор при выгрузке модуля; обработчик, добавленный в модуль руками, ветку сам не получает.
**Побочный эффект для отложенного обработчика** (`ПослеЗагрузкиВсехДанных`): обмен не прерывается, но каждый
загруженный объект такого правила записывается второй раз — вызов прошёл вхолостую, а признак «объект изменён»
остался включённым (XDTO:7196–7207).

## 2. Отложенный обработчик (`ПослеЗагрузкиВсехДанных`) не срабатывает, хотя ветка есть

**Причина.** При получении в режиме объектной конвертации (реквизит узла `ОбъектнаяКонвертацияXDTO`) отложенное
заполнение не запускается вовсе (XDTO:2172–2180); `ПередОтложеннымЗаполнением` — тоже. В обычном пути обработчик
не вызывается только для объекта, который к концу загрузки так и не записан (XDTO:7174–7176); объекты, созданные
этой загрузкой и записанные, обрабатываются.
**Проверить.** Режим узла — в данных базы (только песочница и только с согласия человека); записан ли объект.
**Что делать.** Логику, которая нужна в обоих режимах, не держать только в отложенном обработчике.

## 3. В приёмнике «битая» ссылка: объект не создан

**Причина.** Объект пришёл только ссылкой из другого объекта, у его ПКО идентификация `ПоУникальномуИдентификатору`,
в базе такого объекта нет — исполнитель возвращает ссылку без создания (XDTO:1838–1843). Полный объект создаётся
только своим ПОД. При идентификации `СначалаПоУникальномуИдентификаторуПотомПоПолямПоиска` и `ПоПолямПоиска`
исполнитель идёт дальше — ищет по полям (XDTO:1896–1907) и создаёт объект.
**Проверить.** `ed_validate` → `ed.identity.uid_without_pod` (предупреждение): ПКО получения по уникальному
идентификатору, для объекта формата которого нет ПОД получения. Замечание на типовом модуле может быть намеренным
(объект в этом обмене передаётся только ссылкой) — смотри обработчик ПКО.
**Что делать.** Либо ПОД на объект формата (объект будет приходить полностью), либо идентификация с поиском по
полям — решение человека.

## 4. Реквизит найденного объекта не обновился или «откатился»

**Причина.** В найденный объект переносятся только реквизиты с ПКС шапки (XDTO:7022, 7047). Обработчик
`ПередЗаписьюПолученныхДанных` выполняется до переноса (XDTO:1975, 1988): записанное им в `ДанныеИБ` по
реквизитам с ПКС будет затёрто полученным значением. Если у узла включена объектная конвертация, переносятся
только реквизиты, чьи ПКС сконвертированы успешно (`ПеренестиПоляШапки`, КОС:3444–3483): свойства нет в
сообщении **или значение пустое** — реквизит остаётся прежним (КОС:3192–3196). Отсюда второй симптом: на
объектном пути прямой ПКС нельзя ни очистить реквизит, ни записать в него `Ложь` или `0`. Объектный путь проверен
обменом только для отсутствующего свойства; для пустого значения — чтением кода.
**Проверить.** `ed_get` ПКО → ПКС реквизита есть? `ed_get(адрес обработчика, children_kind="reference")` — что
обработчик пишет и куда; текст — `include_text`.
**Что делать.** Реквизит без ПКС в найденный объект из `ПолученныеДанные` не переносится — добавить ПКС либо
заполнять его прямо в `ДанныеИБ` в обработчике «перед записью» (перенос трогает только реквизиты с ПКС). Реквизит
с ПКС — наоборот: менять значение в `ПолученныеДанные`, правку в `ДанныеИБ` перенос затрёт.

## 5. Табличная часть существующего объекта очистилась

**Причина.** Для каждой табличной части из ПКТЧ исполнитель делает `Очистить()` и `Загрузить()` (XDTO:7051–7062;
на объектном пути — `ПеренестиПоляТабличныхЧастей`, КОС:3485–3508), не проверяя, была ли она в сообщении. Защиты
«нет в сообщении — не трогать» у табличных частей нет вообще: она есть только у реквизитов шапки на обычном пути,
сравнивает имя свойства формата с именем реквизита (XDTO:6753–6765, 7031–7047) и не срабатывает, когда имена
разные, у ключевого свойства и у ПКС с алгоритмом.
**Проверить.** ПКТЧ объекта (`ed_list(kind="pktch", metadata_object=…)`), имена сторон; что реально пришло в
сообщении.
**Что делать.** Не полагаться на «пустое не затирает»: строки, которые должны остаться, сохранять обработчиком.

## 6. Правило есть в модуле, но объект не выгружается и не загружается

**Причина.** Типа из `ОбъектФормата` нет в пакете версии формата, по которой идёт обмен: исполнитель молча удаляет
ПКО (XDTO:4146–4158), при получении — и ПОД (XDTO:3946–3950). Вторая причина — обмен идёт по другой версии, чем
ты думаешь (п. 8), и работает другой модуль менеджера.
**Проверить.** `ed_schema_open` пакета нужной версии → `ed_schema_type(<ОбъектФормата>)`: `ed_schema_type_not_found`
— типа нет. Проверка по схеме в `ed_validate` — `ed.schema.type_missing`, если сервер её уже умеет (иначе в
`skipped` стоит `ed.schema`).
**Что делать.** Для новой версии формата — правило с типом этой версии; для своего объекта — расширение формата.

## 7. Свойство из расширения формата не читается или не выгружается

**Причина.** При получении свойство из пространства имён, которое не активно, пропускается (XDTO:6193–6197).
У правила расширение должно быть объявлено вызовом `ИнициализироватьРасширениеПравилаКонвертацииОбъекта`
(XDTO:4808–4817), а пространство имён — быть в расширениях формата обмена. При выгрузке то же условие: свойства
расширения добавляются к обходу типа, только если расширение объявлено в правиле и его пространство имён есть в
расширениях формата (`ДополнитьСвойстваПакетаИзРасширений`, XDTO:9903–9932); иначе свойство молча не пишется.
**Проверить.** `ed_validate` → `ed.extension.uninitialized` (у свойства указано пространство имён, а у ПКО
расширение не объявлено) и `ed.extension.unused`.
**Что делать.** Объявить расширение в правиле; проверить, что пакет расширения есть в обеих базах.

## 8. Обмен идёт по старой версии формата

**Причина.** У узла пустая `ВерсияФорматаОбмена`: при выгрузке берётся минимальная поддерживаемая версия
(XDTO:3612–3623). Обычно версия проставляется максимальной общей при настройке и при каждом получении
(XDTO:3650–3670, 8163–8189); пустой она остаётся, например, у узла, созданного программно без этого реквизита и
ещё ничего не получавшего (вывод).
**Проверить.** Реквизит узла — в данных базы (песочница, с согласия); карта версий — модуль менеджера плана
обмена и переопределяемый модуль (`executor.md`, §1): какой модуль менеджера назначен этой версии.
**Что делать.** Создавая узел программно (тесты, песочницы), задавать версию явно.

## 9. При получении ошибка «Не найдено ПКО с именем…»

**Причина.** Имя правила не существует: у ПОД получения в `ИспользуемыеПКО` (XDTO:7455–7475), у ПКС
(XDTO:6813–6827) или в инструкции из обработчика (XDTO:6799–6810). При выгрузке отсутствующее правило из
`ИспользуемыеПКО` молча пропускается (XDTO:794–799) — та же ошибка в текстах проявляется только на принимающей
стороне.
**Проверить.** `ed_validate` → `ed.reference.pod_pko_missing`, `ed.reference.property_rule_missing`,
`ed.reference.code_rule_missing` (у последней — строка модуля).
**Что делать.** Исправить имя; имя, вычисляемое кодом, проверка не видит (`references.unparsed` в ответе) —
читать обработчик.

## 10. Объект молча пропущен, обмен «с ошибками» — или сообщение не сформировано вовсе

**Причина.** Ошибка в обработчике `ПриОбработке` ПОД не даёт исключения: исполнитель ставит отказ по объекту
(XDTO:8450–8466). Частый случай — обращение к `ИспользованиеПКО.<Имя>` с именем, которого нет в
`ИспользуемыеПКО` этого ПОД (XDTO:8402–8414). Дальше — по направлению:
- **получение:** объект пропущен, обмен идёт дальше; но взведённый `ФлагОшибки` отменяет отложенные шаги всего
  сообщения — отложенное заполнение, проведение, удаления (XDTO:2172–2221, 7592–7594);
- **отправка:** отказ по объекту взводит `ФлагОшибки` (XDTO:779–787, 903–905), и после обхода всех объектов
  исполнитель бросает исключение — **сообщение не формируется целиком** (XDTO:654–664). Так же действует ошибка в
  обработчике ПКО при выгрузке и незаполненное обязательное свойство формата (проверка по схеме). Исключение — узел
  с настройкой «пропускать объекты с ошибками проверки по схеме»: объект пропускается и регистрируется заново
  (XDTO:696–705), итог обмена — «с предупреждениями».
- Объект, который входит в состав плана обмена, но не имеет ПОД отправки, — исключение «Не найдено ПОД для объекта
  метаданных» и срыв всей выгрузки (XDTO:8344–8357).
**Проверить.** `ed_validate` → `ed.reference.pod_usage_key_missing` с видом «использование ПКО»;
`ed_get(адрес обработчика, children_kind="reference")`; журнал регистрации базы-отправителя.
**Что делать.** Привести имя в обработчике к имени из `ИспользуемыеПКО`; у объекта, который не должен уходить, —
убрать из состава плана или дать ПОД; обязательные свойства формата заполнять всегда.

## 11. Ошибка при обработке удаления не видна

**Причина.** `ПередОбработкойУдаляемогоОбъекта` вызывается в `Попытка` с пустым `Исключение` (XDTO:8743–8748): любая
ошибка внутри процедуры проглатывается, удаление идёт стандартно.
**Что делать.** В этой процедуре ошибки записывать самому (журнал регистрации), на исключение не рассчитывать.

## 12. Доработка обмена в расширении не действует, ошибок нет

**Симптом.** Правила доработаны расширением конфигурации (заимствован модуль менеджера обмена, перехватчик
`&После("ЗаполнитьПравилаКонвертацииОбъектов")` добавляет ПКС); расширение применилось, модули компилируются, а
свойство в сообщение не попадает и при получении не читается. В журнале пусто.
**Причина.** Расширение работает в безопасном режиме: загрузка расширения из файлов пакетным конфигуратором
создаёт его с признаком «Безопасный режим». Проверено живым обменом (платформа 8.3.27, БСП 3.1.12): в безопасном
режиме перехватчик эффекта не даёт, после снятия признака — работает. Механизм по коду не установлен; проверка
применимости расширения и синтаксический контроль модулей этого не ловят.
**Проверить.** Свойство расширения «Безопасный режим» (список расширений конфигурации в базе); значение видно
только в новом сеансе.
**Что делать.** Снять безопасный режим у расширения, которое дорабатывает обмен, — решение человека: это
расширение получает права основной конфигурации.

## 13. Повторная загрузка того же сообщения ничего не делает

**Причина.** Сообщение с номером, который узел уже принял, исполнитель не загружает: «было ранее принято», при
обмене через файл или строку — исключение (`ОбменДаннымиСервер`, получение сообщения; `XDTO:7835–7849`).
Проверено живым обменом.
**Что делать.** Чтобы проверить повторное получение объекта (нет ли дубля, не затёрлись ли значения), выгружай
новое сообщение с тем же объектом, а не подавай старый файл.

## 14. Подменённый модуль менеджера работает не для всех сообщений

**Причина.** Модуль менеджера выбирается по версии формата — ключу карты «версия → модуль»
(`МенеджерОбменаВерсииФормата`, XDTO:3566–3578). При получении версия берётся из сообщения (XDTO:2386–2397), при
отправке — из узла. Свой модуль, подставленный в карту для одной версии, сообщения других версий не обрабатывает.
Для узла карта берётся только из настроек плана обмена, переопределяемый модуль действует лишь без узла
(XDTO:9043–9047); настройки плана кэшируются на сеанс (ОДПовт:156–158).
**Проверить.** `ed_routes` двух сторон → `ed_route_compare` (`ed.route.manager_missing`,
`ed.route.map_sources_differ`); версия узла — в данных базы.
**Что делать.** Подставлять модуль для каждой версии, по которой реально идёт обмен. Доработка перехватчиком в
заимствованном модуле менеджера (так делает авторинг сервера) к ключу версии не привязана.

## 15. Объект не регистрируется или регистрируется не на тот узел после смены настроек

**Причина.** Ответ на вопрос «какие узлы проходят условие правила регистрации» кэшируется на сеанс по значениям
свойств объекта и тексту запроса (`ОпределитьМассивУзловПоЗначениямСвойств`, ОДСоб:2098–2137;
`ОДПовт.МассивУзловПоЗначениямСвойств`). Кэш сбрасывается при интерактивной смене реквизитов-отборов узла, при
обновлении правил регистрации и смене префикса (поиск вызовов `СброситьКэшМеханизмаРегистрацииОбъектов`); запись
узла с `ОбменДанными.Загрузка` и запись при обмене его не сбрасывают (ОДСоб:658–691). Перечень сбросов установлен
чтением кода, обменом не проверен.
**Проверить.** Инструментами сервера не проверяется. Правила регистрации плана: условия по реквизитам узла,
`ИспользоватьКэш` в обработчике «При обработке» (он может кэш отключить, ОДСоб:2109–2117).
**Что делать.** После программной смены реквизитов узла, по которым отбирают правила регистрации, начинать новый
сеанс (или менять узел интерактивно).

## 16. Обработчик отправки вставил значение, а в сообщении его нет (или есть без ПКС)

**Причина.** Сообщение собирается обходом свойств **типа формата**, значение берётся из структуры по имени
свойства (`ОбъектXDTOИзДанныхXDTO`, XDTO:923–1018, 946–954) — есть ли для него ПКС, не проверяется. Поэтому
значение, вставленное обработчиком `ПриОтправкеДанных`, уходит и без ПКС, если ключ совпал с именем свойства типа
в пакете версии обмена. Не уходит: ключа нет в типе этой версии; значение пустое (`Ложь`, `0`, пустая строка —
пропускаются; при признаке «может быть пустым» пишется пустой элемент, XDTO:986–995); объект выгружается только
ссылкой из другого объекта — тогда берутся одни ключевые свойства (XDTO:1263–1268).
**Проверить.** `ed_get(адрес обработчика, children_kind="reference")` — что пишет обработчик;
`ed_schema_type(<ОбъектФормата>)` пакета версии обмена — есть ли свойство и обязательно ли оно.
**Что делать.** Имя ключа — точно как в типе формата нужной версии. Пустое значение как «очистить у получателя»
передать можно только свойству с признаком «может быть пустым».

## 17. Объект уходит в каждом сообщении

**Причина.** Выгрузка регистрацию не снимает. Она снимается, когда от корреспондента приходит сообщение с номером
принятого (`ReceivedNo`, XDTO:2360–2364): `ОбработатьПолучениеПодтвержденияОтКорреспондента`, XDTO:9341–9351
(`УдалитьРегистрациюИзменений`), и только при квитировании. Пока ответного сообщения не было, каждый
зарегистрированный объект выгружается снова.
**Следствие для проверок.** Объект в сообщении не доказывает, что его зарегистрировала последняя запись: на
одностороннем стенде (ответных сообщений нет) перед опытом сними регистрацию объекта с узла и только потом
записывай объект.

## 18. Расширение обновили, а обмен работает по-старому

**Причина.** Обновлённое расширение конфигурации видно только новому сеансу — это поведение платформы, в коде БСП
его нет. Сама БСП правила не кэширует: таблицы правил заполняются из модуля менеджера при каждой инициализации
обмена (XDTO:3415–3420). Проверено живым обменом: сеанс сервиса, через который выполняется код в базе, живёт,
пока к нему обращаются, — частый опрос держит старый сеанс со старым расширением.
**Что делать.** После обновления расширения дождаться нового сеанса (перестать обращаться к базе на время жизни
сеанса сервиса) или запускать обмен в новом сеансе; в протоколе проверки фиксировать, что расширение в сеансе
новое (например, контрольной функцией расширения).

## 19. Объект зарегистрирован, но в сообщении его нет, ошибок нет

**Причина.** Отправляется только пересечение двух списков: что своя база умеет отправлять и что корреспондент
объявил к получению (`ЗаполнитьПоддерживаемыеОбъектыXDTO`, XDTO:3849–3895); объект формата вне пересечения молча
пропускается при выгрузке (XDTO:797–803). Список «принимаю» база строит **только по ПОД получения**
(XDTO:9465–9484) — ПКО без ПОД в него не попадает. Список хранится **по версиям формата**: объект может быть
объявлен для одних версий и отсутствовать для версии обмена этого узла. Список корреспондента обновляется, только когда от него
приходит сообщение (XDTO:8194–8199): правило, добавленное в приёмник, источник «увидит» лишь после следующего
сообщения от приёмника. Проверено обменом на стенде: получение новых объектов заработало после первого сообщения
из базы-получателя.
**Проверить.** Есть ли в приёмнике ПОД получения для этого объекта формата в версии обмена узла; был ли после
его добавления обмен в направлении «приёмник → источник». Что источник знает о корреспонденте сейчас — в базе
источника (песочница, с согласия человека): экспортная функция исполнителя
`ОбменДаннымиXDTOСервер.ПоддерживаемыеОбъектыФорматаКорреспондента(Узел, "ОтправкаПолучение")` (XDTO:2971–2990)
возвращает таблицу «объект формата, версия, отправка, получение» — нужна строка объекта **для версии обмена
узла** с признаком получения.
**Что делать.** Добавить ПОД получения (и ПКО); первым после доработки выполнить обмен из базы, которая должна
начать получать новые объекты.

## 20. `ПослеЗагрузкиВсехДанных` не видит данных, переданных через дополнительные свойства

**Причина.** В отложенное заполнение дополнительные свойства переносятся из **записанного** объекта
(XDTO:7191–7196). У нового объекта это `ПолученныеДанные`; у найденного пишется `ДанныеИБ`, а перенос
`ПолученныеДанные` → `ДанныеИБ` дополнительные свойства не копирует (`ЗаполнитьДанныеИБПоПолученнымДанным`,
XDTO:7013–7064).
**Что делать.** В `ПередЗаписьюПолученныхДанных` для найденного объекта переложить нужные ключи из
`ПолученныеДанные.ДополнительныеСвойства` в `ДанныеИБ.ДополнительныеСвойства` — так делает типовой код.

## 21. Доработка правил регистрации не действует: правила — не файл, а модуль

**Причина.** У плана обмена через универсальный формат правила регистрации бывают двух видов: XML-макет
`ПравилаРегистрации` (формат тот же, что у КД 2) либо общий модуль «менеджер регистрации», чьё имя задаёт
настройка плана; исполнитель вызывает его `ИнициализацияПравилРегистрации` (`ОбменДаннымиСервер`, ОДСер:8353–8368).
Правка XML при втором виде ничего не меняет, и наоборот.
**Проверить.** В модуле менеджера плана обмена — задано ли имя менеджера регистрации; есть ли у плана макет
`ПравилаРегистрации`.
**Что делать.** Править тот вид, который действует. `registration_build` сервера строит только XML.

## Как пополнять

Новый случай — сюда, если подтверждён кодом исполнителя (процедура и строки) и не привязан к одной конфигурации:
без имён баз, организаций и людей. Случай, проверенный только чтением, так и помечается.
