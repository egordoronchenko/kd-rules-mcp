# Собственный модуль правил обмена: построить с нуля или взять типовой за основу

Читать, когда типовых правил нет или они не подходят целиком: нужен обмен объектами, которых в типовом модуле
нет, или свой набор правил для версии формата. Если нужно добавить реквизит к объекту, который уже ходит в
типовом обмене, — это `authoring.md`: там доработка поверх типового модуля, здесь — **свой модуль вместо
типового**.

Параметры и ответы инструментов — `kd2-rules-build/references/tools.md`, раздел «Writing a manager module».

## Что получится и чем это отличается от доработки

Сервер собирает общий модуль менеджера обмена целиком и комплект для установки: расширение с этим модулем и
строкой, которая подключает его к версии формата. После установки база по узлам с этой версией формата берёт
правила **только из нового модуля**:

- типовые правила этой версии перестают действовать **все** — объекты, для которых в новом модуле правил нет, по
  этим узлам ходить перестают;
- подмена действует на все узлы плана с этой версией формата, а не на один;
- расширения, которые дорабатывали типовой модуль для этой версии, перестают на неё влиять.

Скажи это человеку до начала работы. Если ему нужно «как было, плюс одно поле» — это не сюда.

Что сервер умеет в модуле сейчас: правила объектов (ПКО), прямые свойства шапки, идентификацию и поля поиска,
правила обработки данных (ПОД), заголовок модуля. Остальное — ссылочные свойства, предопределённые данные,
обработчики, табличные части — операция отклонит с причиной `unsupported_form`; в импортированном модуле такие
места сохраняются как есть, но не правятся.

## Порядок работы

1. **Входы.** `structure_load_project` конфигурации, для которой строится модуль (структура нужна из XML-выгрузки,
   не из MD83Exp); `ed_schema_open` нужной версии формата. Обмен между двумя базами — два модуля, по одному на
   каждую конфигурацию: всё ниже делается дважды.
2. **`ed_create`** с явным `project_id` (имя задачи: `zup-positions`, `bp-contracts`), проектом и конфигурацией
   из `project_list`, планом обмена и версией формата. Два режима:
   - `mode="new"` — пустой модуль, правила создаёшь операциями;
   - `mode="import"` — взять за основу существующий модуль: сначала `ed_open` типового модуля (с
     `extensions=[]`), затем `ed_create` с его `document_id`. Исходный файл не меняется. В ответе
     `import_report`: что стало редактируемым, что сохранено как есть и почему.
3. **Прочитать ответ `ed_create`.** `executor_profile.verified: false` или замечание
   `executor_profile_unverified` — исполнитель правил в этой конфигурации отличается от проверенных образцов
   (другая версия БСП либо расширение перехватывает исполнитель): строить можно, но живой обмен обязателен, и
   человеку это надо сказать. `extensions_unverified` — расширения не сверялись: передай их список или
   `extensions=[]`, если их нет.
4. **Кандидаты.** `ed_authoring_candidates(scope="manager", kind="objects")` — какие объекты конфигурации каким
   типам формата соответствуют; с `reference_document_id` типового модуля добавляются пары «так в типовом
   модуле». Затем `kind="properties"` для выбранной пары. У всех кандидатов `auto: false`: сопоставление — твоё
   решение, запиши его в отчёт.
5. **Правки — `ed_apply`, всегда в два шага.** `mode="preview"` с текущей ревизией: прочитай канонические операции,
   изменения и замечания (страницами). Затем тот же пакет с `mode="apply"`, `expected_preview_hash` и
   подтверждениями замечаний. Пакет применяется целиком или не применяется вовсе. Идентификаторы для ссылок
   между операциями бери из ответа preview (`result_id`), а не из `ed_list`.
6. **Смотреть результат** — по `document_id` из ответа apply теми же `ed_overview`, `ed_list`, `ed_get`,
   `ed_locate`, что и типовой модуль. После каждой правки `document_id` новый.
7. **`ed_validate(document_id, schema_id, structure_id)`** — обычные проверки модуля плюс `ed.writer.*`: правило
   объекта, до которого нет пути ни из одного ПОД; обязательная процедура отсутствует; имя длиннее допустимого.
   Критерий — нет ошибок; каждое предупреждение разобрано.
8. **Комплект — `ed_authoring_build(scope="manager")`**, тоже preview → write с `build_hash` и подтверждениями.
   Комплект пишется в рабочую папку сервера; в ответе путь. В базу сервер ничего не ставит.
9. **Отдать человеку** папку комплекта и сказать, что в `instruction.md`: установка расширения либо перенос руками
   (общий модуль **и** строка подключения к версии формата — две вещи, вторую забывают), проверка «база берёт
   правила из нового модуля», первый обмен, возврат к типовым правилам.

## Что нужно знать, чтобы не ошибиться

- **Проект живёт на сервере между сеансами.** Повторный `ed_create` с теми же аргументами возвращает его
  (`existing: true`); с другими — отказ со списком различий: это защита от того, чтобы принять старый проект за
  новый. Закрыть и удалить — `ed_close(project_id)`; комплекты на диске остаются.
- **Конфигурацию обновили.** `ed_create` вернёт замечание `creation_inputs_changed`, а правки и сборка откажут,
  пока проект не перепривязан: перезагрузи структуру и схему, затем `ed_create(mode="rebind")`. Правила и история
  сохраняются; в ответе — что новые входы сломали. Удалять проект не нужно.
- **Имя расширения.** По умолчанию оно получает приписку от `project_id`, поэтому два модуля для одной
  конфигурации не сталкиваются. Задаёшь `identity.name` сам — задавай разное для разных обменов: одинаковое имя
  означает одно и то же расширение в базе, и сервер откажет записать комплект поверх чужого
  (`kit_owned_by_other_project`).
- **Комплект руками не правят.** Сервер сверяет файлы с описью и не станет собирать следующую сборку поверх
  изменённых. Правка — операцией в проекте, затем новая сборка.
- **Версия формата сравнивается буква в букву**: `1.20` и `1.20.0` — разные ключи. Бери ту, что записана у узлов
  (`executor.md`, §1).
- **Сервер не исполняет код 1С.** «Комплект собран без замечаний» значит: модуль читается, правила связаны,
  обязательные процедуры на месте. Что обмен действительно пройдёт, показывает только живой обмен в тестовой
  базе; в отчёте человеку «проверено сервером» и «проверено обменом» не смешивай.

## Отчёт человеку

Что строили и для каких конфигураций → какие объекты и свойства включены, какие нет и почему (решения по
кандидатам) → замечания `ed_validate` и подтверждённые замечания сборки → путь к комплекту каждой стороны → что
не проверено: живой обмен, регистрация изменений (правила регистрации — отдельная задача), права пользователей,
другие расширения в базе.
