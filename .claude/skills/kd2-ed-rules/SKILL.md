# Обмен через универсальный формат: разбор и проверка

Правила такого обмена — не XML, а код: общий модуль менеджера обмена (например,
`МенеджерОбменаЧерезУниверсальныйФормат`), который генерирует «Конвертация данных 3» и исполняет БСП. Сервер
`kd2-rules-mcp` читает этот модуль **без исполнения**, раскладывает на правила (ПКО, ПКС, ПОД, ПКПД, обработчики,
алгоритмы), проверяет их связность и сверяет со схемой формата. Типовой модуль сервер не правит: ты разбираешь,
объясняешь и проверяешь. Доработку существующего правила объекта он выпускает сам — расширением: прямое правило
свойства шапки (в том числе с новым реквизитом), обработчик события ПКО с твоим кодом (поверх пустого события или
после типового обработчика), сохранение значения реквизита при отсутствии свойства в сообщении, алгоритмическое
свойство отправки (`references/authoring.md`); остальное вносит человек (или ты — в файл расширения, по правилам
проекта).

Термины — `kd2-rules-build/references/glossary.md`; параметры и ответы инструментов —
`kd2-rules-build/references/tools.md`; проверки и их идентификаторы — `kd2-rules-build/references/checks.md`;
серверы MCP для 1С (код, данные) — `kd2-rules-build/references/mcp-1c.md`, прочитать перед первым их вызовом.

| Файл | Когда читать |
|---|---|
| `references/executor.md` | нужно понять, что БСП сделает с правилом: какая версия формата и какой модуль работают, когда вызывается обработчик, что переносится в найденный объект |
| `references/pitfalls.md` | жалоба на живой обмен или ревью: симптом → причина → как проверить → что делать |
| `references/recipes.md` | задача не решается прямым свойством: свой поиск объекта (`АлгоритмПоиска`), отказ от загрузки («не создавать, если не найден»), проведение документа, данные вне формата (`AdditionalInfo`), один объект формата в несколько объектов базы, поведение по варианту настройки |
| `references/authoring.md` | нужно передать свой или существующий реквизит объекта, который уже участвует в обмене: порядок, что значит ответ, грабли установки |

## 0. Что нужно знать до первого вызова

- **Три разные «версии».** Имя пакета формата (`EnterpriseData_1_8_6`), версия формата обмена (`1.8` — ключ карты
  версий и конец URI пакета) и версия модуля менеджера (`manager_version` в ответе `ed_open`). В вопросах человека
  «версия» — почти всегда вторая.
- **Один модуль — несколько версий формата.** Карта «версия формата → модуль менеджера» записана в модуле
  менеджера плана обмена (настройка `ВерсииФорматаОбмена`) и в `ОбменДаннымиПереопределяемый`
  (`ПриПолученииДоступныхВерсийФормата`) — найди оба места сервером кода проекта и сверь. Обмен идёт по
  максимальной версии, общей для двух баз; у узла с пустой версией выгрузка берёт минимальную
  (`references/executor.md`, §1). Пока не знаешь версию — не утверждай, какой модуль работает.
- **Правило в модуле ещё не значит «работает».** ПКО, типа формата которого нет в пакете версии обмена, исполнитель
  молча выбрасывает; обработчик без ветки диспетчера молча не вызывается; при получении есть два пути исполнения
  с разным набором событий. Всё это — `references/executor.md`.
- **Типовой модуль на поддержке не правят.** Доработку вносят расширением конфигурации; если человек просит
  «поправить в модуле» — уточни, где у проекта живёт доработка обмена.

## 1. Порядок работы

1. **Найти модуль.** План обмена и карта версий — сервером кода проекта (`code_mcp` в `project_list`) или по
   выгрузке: `<dump>\ExchangePlans\<план>\Ext\ManagerModule.bsl`, модуль менеджера —
   `<dump>\CommonModules\<имя>\Ext\Module.bsl` (`dump` — из `project_list`). Обмен между двумя базами — два модуля,
   по одному с каждой стороны: отправку читают в источнике, получение — в приёмнике.
2. **`ed_open(path)`** → `project_id`, счётчики правил, `manager_version`, `parse_status`. `partial` — часть
   модуля сервер не разобрал: `ed_overview` покажет диагностики и неизвестные фрагменты; выводы об отсутствии
   чего-либо рядом с таким фрагментом не делай. Снимок живёт в памяти сервера; файл изменился
   (`source_changed: true`) — `ed_close` и снова `ed_open`.
3. **`ed_validate(project_id)` сразу** — замечания «до правок». В типовых модулях они есть: критерий для любой
   доработки — **нет новых**. Запомни `by_check` и адреса.
4. **Смотреть правила**: `ed_list` (вид `pko`, `pod`, `pks`, `pktch`, `pkpd`, обработчики, алгоритмы; отбор
   `text`, `format_object`, `metadata_object`) → `ed_get(address)` — поля правила и его дети страницами (ПКС
   группы — отдельным `ed_get` группы). Текст обработчика — `include_text: true`. От строки модуля (из сообщения
   об ошибке, из диффа) к правилу — `ed_locate(line)`.
5. **Что обработчик трогает** — `ed_get(адрес обработчика, children_kind="reference")`: какие правила он ищет по
   имени, какие ключи `ИспользованиеПКО`, параметры конвертации и свойства читает и пишет. Имя, вычисляемое кодом,
   помечено `unparsed` — такое место читай глазами.
6. **Схема формата** — `ed_schema_open(format_version, project, package)` (или `path` к пакету) →
   `ed_schema_type("Справочник.Валюты")`: свойства типа с именем, под которым их пишут в правиле
   (`effective_path`), обязательностью (`lower`), признаками ссылки и табличной части; перечисление —
   `section: "values"`. Имена пакетов — папка `XDTOPackages` выгрузки.
7. **Проверка по схеме и структуре** — `ed_validate(project_id, schema_id, structure_id, direction)`: `schema_id` —
   из шага 6, `structure_id` — из `structure_load_project(project)` той же конфигурации. Без них проверки этой
   группы попадают в `skipped` — это «не проверено», а не «всё хорошо». Проверяется одна версия формата за вызов:
   свойство, которого нет в версии 1.8, может быть на месте в 1.20 — выбирай пакет той версии, по которой идёт
   обмен.
8. **`ed_close`**, `ed_schema_close` — когда закончил.

## 1а. Обмен доработан расширениями конфигурации

Типовой модуль показывает только типовые правила. Если проект дорабатывает обмен расширениями (заимствованный
модуль менеджера с перехватчиками), открывай модуль **вместе с ними** — иначе ответ «такой ПКС нет» или
«обработчик пуст» будет про типовую конфигурацию, а не про базу.

1. **Открыть со слоями.** `ed_open(project, module)` берёт расширения из настройки проекта (`project_list`);
   по пути — `ed_open(path, configuration_path, extensions=[…])`, порядок списка — порядок применения.
   `extensions=[]` — только типовой модуль. В ответе `composition_status`, список `layers`, счётчики
   `changes_summary` (добавлено, изменено, удалено).
2. **Смотреть действующее.** `ed_list` и `ed_get` показывают правила с учётом расширений: у каждого `state`
   (типовое, добавлено, изменено), `layer_id` и `origins` — какой слой что сделал; история правки —
   `ed_list(kind="change", entity_id=…)`. Что расширение перехватывает — `ed_list(kind="hook")`; текст — адрес
   `Слой/<id>/…` с `include_text`. Отправка и получение — разные контексты: если поля различаются, `ed_get` вернёт
   `requires_context` — повтори с `direction`.
3. **Проверить.** `ed_validate` применяет все прежние проверки к действующему составу и добавляет `ed.layer.*`:
   обработчик назначен, а ветки диспетчера нет; ветка вызывает процедуру с параметрами, которых исполнитель этому
   событию не передаёт; диспетчер расширения не продолжает вызов и глушит типовые обработчики. Критерий доработки
   тот же: сравни с проверкой типового модуля (`extensions=[]`) — **нет новых** замечаний.
4. **Читать границы.** `composition_status: partial` и строки `skipped` — расширение содержит код, который сервер
   не моделирует (перехват типовой процедуры, диспетчер функций, заполнение под условием): состав правил рядом с
   таким местом не утверждай, прочитай перехват глазами (`ed_list(kind="layer_unknown")`). «Прочитано полностью»
   относится к **составу правил после заполнения и связям событий с процедурами**. Что код обработчиков — типовых
   и добавленных — делает во время обмена, сервер не утверждает (`handler_execution_note`); предупреждение
   `ed.layer.handler.touches_rules` — подсказка, что обработчик сам обращается к таблицам правил.
5. **Чего слой не знает.** Подключено ли расширение в базе, в каком порядке и в каком режиме — данные базы
   (`references/pitfalls.md`, п. 12, 18). Сервер читает выгрузку; порядок слоёв — тот, что ты передал.

Авторинг (`references/authoring.md`) работает на снимке без слоёв: открой модуль с `extensions=[]`.

## 2. Как читать `ed_validate`

- **`summary`** — по всему отчёту (`errors`, `warnings`, `skipped`, `by_check`); `level` и `check_prefix` отбирают
  только страницу `issues`.
- **Ошибка** — дефект самого модуля: названный обработчик не будет вызван (нет ветки диспетчера), модуль не
  скомпилируется (вызов несуществующей процедуры), нет обязательной процедуры конвертации. Чинится в модуле.
- **Предупреждение** — риск, исход которого зависит от данных, версии формата или кода обработчика: ссылка на
  несуществующее правило, ПКО получения по уникальному идентификатору без ПОД, свойство, которого нет в выбранной
  версии формата. Разбирай каждое: `ed_get` правила, обработчики, `references/pitfalls.md`.
- **Уровень — про модуль, не про тяжесть для обмена.** Предупреждение `ed.reference.pod_usage_key_missing` у обращения
  к `ИспользованиеПКО` даёт отказ по объекту и результат обмена «Ошибка», когда выполнение дойдёт до этой строки;
  ошибка `ed.handler.missing` у отложенного обработчика обмен не прерывает. В отчёте человеку расставляй
  замечания по последствиям (`references/executor.md`, `references/pitfalls.md`), а не по уровню.
- **`skipped`** — что не проверено и почему (нет схемы, неполное чтение, обработчик может заполнять свойство
  кодом, условие по версии непрозрачно). В отчёте человеку перечисли.
- **`references`** — сколько ссылок из кода обработчиков разобрано и сколько имён вычисляется кодом (`unparsed`):
  вторые проверка не видит.
- Адрес замечания — адрес правила (`ПКО/<Имя>`, `ПКО/<Имя>/ПКС/<Свойство>`, `Обработчик/<Имя>`); строка модуля —
  в сообщении. Дальше — `ed_get(address)`.

## 3. Типовые вопросы

**«Почему реквизит не переносится».** Сторона: отправка — модуль источника, получение — приёмника. ПКО объекта —
`ed_list(kind="pko", metadata_object=…)` (или `format_object`); ПКС реквизита — `ed_get` ПКО. ПКС есть — проверь
свойство формата в схеме версии обмена (шаг 6) и правило конвертации у ссылочного свойства (существует ли ПКО или
ПКПД). ПКС нет или стоит признак алгоритма — значение заполняет обработчик: его текст и ссылки (шаг 5). При
получении в **найденный** объект переносится только то, для чего есть ПКС, и обработчик «перед записью» этому
предшествует (`references/pitfalls.md`, п. 4–5).

**«Объект не доходит или приходит пустой ссылкой».** ПОД объекта с обеих сторон и его `ИспользуемыеПКО`; тип
формата в схеме версии; вариант идентификации ПКО получения (`references/pitfalls.md`, п. 3, 6, 9).

**«Обработчик не срабатывает».** `ed_validate` (`ed.handler.missing`), затем путь получения
(`references/pitfalls.md`, п. 1–2).

**«Что изменится, если добавить реквизит».** Нужны: ПКС в ПКО отправки и получения, свойство в формате, при
необходимости правило для ссылочного типа, регистрация изменений. Простой случай — примитивный реквизит шапки в
свободное свойство формата — сервер выпускает расширением: `references/authoring.md`. Свойство формата ищи в типе
объекта для версии обмена (`ed_schema_type`), по порядку: своё свойство типа, не занятое ПКС; общие свойства объектов формата
(например `Комментарий` — есть не у всех типов и не во всех версиях); таблица дополнительных реквизитов из общих
свойств; `AdditionalInfo` (произвольные данные — заполняется и читается только кодом обработчиков). Ничего не
подходит — расширение формата (свой пакет и пространство имён в обеих базах). Типовой модуль не правят: доработку
вносят расширением конфигурации — перехватчиком после типового заполнения правил; если доработке нужен новый
обработчик, ему нужна и ветка диспетчера (`references/pitfalls.md`, п. 1, 12). Обработчик события ПКО
(отправка, конвертация при получении, перед записью) сервер тоже выпускает расширением — с перехватом диспетчера и
проверкой тела (`references/authoring.md`); как исполнитель поведёт себя после обработчика — `references/recipes.md`.
Новые ПКО и ПОД, свой алгоритм поиска, табличные части, ссылочные свойства и свои поля формата сервер не порождает
— покажет, что есть сейчас, правку вносят руками.

## 4. Данные и границы

- Данные баз (версия у узла, режим объектной конвертации, протокол обмена) — только сервер данных базы роли
  «песочница» и только с согласия человека в этой задаче: спроси одной строкой, какой запрос и зачем; нет
  согласия — «не проверено». Боевую базу не трогать.
- Выводы — по коду: правило (адрес и строка модуля) и процедура исполнителя БСП из `references/executor.md`
  (строки сверь по выгрузке конфигурации человека — в другой версии БСП они сдвинуты). «Проверено чтением» и
  «проверено обменом» в отчёте не смешивай.
- Отчёт человеку: что спросили → что нашёл (правила с адресами, строки модуля) → что сделает исполнитель и почему
  (процедура БСП) → замечания `ed_validate` до и после → что не проверено (`skipped`, данные базы, второй путь
  получения).
